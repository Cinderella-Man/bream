# Busy room member, shared bytes and termination

**Eleventh bounded milestone passed for the declared single-worker profile, 2026-10-08.** This experiment integrates a session that performs sustained admitted computation into the room and immutable-broadcast profile. Its checked program, scheduler, mailbox, relationships and immutable-byte implementation are inherited from [shared-process](../shared-process/README.md); the new application fixture composes their existing contracts. Runtime and compiler source differ only in the experiment's crate names. This is further work on partial G5, not completion of the full build gates. [Milestone tracker](../../docs/milestones.md).

**No speed tests or performance comparisons may run on this machine.** The controls use protocol stages, logical work counts, ownership counters and cleanup observations. Watchdogs detect hangs; elapsed values are not performance evidence. Neither allowance comparisons nor observed work rounds select a production allowance or establish a latency guarantee. Performance qualification requires a separately authorized suitable environment. [Persistent instructions](../../AGENTS.md).

## Application and checked boundary

The [fixture](consumer/src/busy.rs) has one room and two members on one worker. The trusted host creates the busy member so the controls retain its genuine process handle. The room receives that full identity through its startup target, installs a monitor and sends it a share of the room's resident bytes. The room creates the healthy member through checked `spawn_monitor`; that child also monitors the room. The busy member is therefore a participant in the room's broadcast and relationship protocol, rather than an unrelated background task. This remains fixed membership; it does not add a general join API or a collection of process identities.

The trusted host ingests the bytes `[2, 3, 5, 7]`. The room holds a reference and explicitly sends one clone to each member. After receiving its share, the busy member owns a private `Work` record containing the share, an owned four-word scratch buffer and a round counter. Its infinite loop moves this record into an acyclic helper and takes the returned record into the next iteration. The helper reads the bytes, writes and reads scratch values, computes a checksum and publishes a logical round observation. Each stopped computation must retain checksum 62627; this is checked after cleanup, avoiding reliance on simultaneous reads of independent live counters. The loop has no application receive, send, explicit yield, stop test or authored await.

The [checked compiler](macros/src/structured.rs:1097) inserts checkpoints at admitted statement and loop boundaries, including the computation helper. The [runtime checkpoint](runtime/src/lib.rs:199) participates in the existing poll allowance. This makes the native continuation return control to the single worker. The claim covers admitted generated programs; unrestricted Rust loops, arbitrary native calls and user-defined destructors remain outside this boundary.

The healthy member owns a `Reader` record with another share and its startup buffer. Each request moves the same reader into a helper, reads its immutable bytes and returns a checksum in the request's owned words. The room validates the request sequence and checksum before publishing its observation. Helper calls transfer ownership of `Reader` and `Work` without cloning their byte handles. This is a Rust-specific structural opportunity: moving the owning record avoids additional shared-reference increments and decrements on those calls. It is not evidence of a measured speed improvement.

## Progress, stop and ownership oracles

Before each stop scenario, three complete room-to-healthy-member request/reply exchanges must finish while the busy member remains live. Each exchange records an actual room sequence/checksum and observes the busy member subsequently advance beyond a prior round count. The busy process must still have exactly one application receive—the original shared-payload receive—and must not be waiting. These are bounded observations that both protocols progress on one worker; they do not prove a strict scheduling ratio or a universal fairness bound.

The host then queues nineteen additional shared envelopes and three ordinary messages at the busy member. That member stays in computation and never consumes these twenty-two messages. At this settled boundary the single four-byte backing allocation has twenty-three references: the host, the room, two members and nineteen queued envelopes. The expected reference-created count remains twenty-three through further computation and request/reply work, providing an executable check that moving helper state does not acquire new shares.

The fixture covers three scenarios:

| Scenario | Required observations |
|---|---|
| Direct busy-member stop | A host kill is accepted while the member computes. Application receive count remains one. The room accepts exactly the matching monitor reference, full target identity and killed reason. |
| Fatal linked exit | A separate host-created partner is linked to the busy member and killed. The fatal reason propagates through the genuine link. The busy member terminates through the linked-exit path without its own accepted host kill or another application receive. The room validates the same exact Down contract. |
| Active runtime shutdown | Shutdown begins with the busy member computing, the room live, the healthy member waiting and work queued at the busy member. All processes, relationships, queued work and logical timers must settle. |

For the first two scenarios, the busy member's completed cleanup must report all twenty-two queued messages retired in three batches under the inherited eight-event allowance. Its owned scratch allocation is released exactly once. After its held share and nineteen queued shares are released, three references must remain: the host, room and healthy member. Two further request/reply exchanges must succeed through that surviving reader, while the stopped member's application observations remain unchanged.

The room then closes the healthy member with a protocol message. It requires the child's acknowledgement followed by its exact normal Down before returning. The startup allocation moved into that child must be released once. Shutdown completes any remaining retirement. The active-shutdown scenario independently checks the same busy-member queue cleanup without requiring the room to consume a Down during shutdown.

At the final quiescent process-cleanup boundary, only the host reference may remain. The host reads all four bytes directly, then drops the final handle. The receipt must report zero live bytes and references, twenty-three created and released references, and exactly one physical backing-storage destruction. Ordinary request and queued-message receipts must each report exactly one release. A process stop, Down notification and final shared-storage destruction are separate facts: a surviving owner is expressly allowed to retain the backing allocation after another process has stopped.

Checksum checks are bounded content oracles, not collision-free proofs of arbitrary payload equality. Shared receipt fields are independently loaded atomics; exact cross-field assertions are made at established ownership boundaries. They measure the vector's backing capacity and handle obligations, not RSS, allocator retention or every allocation made by the runtime.

## Remaining scope

This bounded single-worker integration does not qualify dynamic membership, unrestricted native Rust, authored byte construction, arbitrary shared Rust types, multiple workers, richer exit reasons, direct checked exit APIs, real-time timer driving or full BEAM conformance. It also does not establish a numeric peer or stop latency target. The existing fixed room conversation, immutable broadcast and this busy-member fixture cover complementary obligations; broader G1–G5 qualification remains open.
