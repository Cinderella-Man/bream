# Execution, resources and runtime embedding

Planning inventory, 2026-10-07. This document enumerates build work and conformance cases; it does not report an implementation or new test execution. The reference is Erlang/OTP `OTP-29.1.1`, commit `ad05823719d77c8faee87348ea39513d4e2f99c5`. Read alongside the [scheduler source trace](../research/11-beam-scheduling-source.md), [memory/native trace](../research/14-beam-memory-native-io-source.md) and [execution gap audit](../research/17-execution-resource-edge-cases.md).

Scope is admitted native Rust processes, ordinary Cargo, initially one Linux x86-64 worker. Engine representation, public signatures, supported types and panic policy remain unselected. Compatible BEAM behavior is the reference, subject to recorded Rust conflicts. In particular, [ADR 0009](../adr/0009-death-and-reclamation-observation.md) requires application execution to stop before `Down`, while tracked reclamation may follow. No elapsed-time guarantee, arbitrary quota, priority API, dirty-job facility or OTP behaviour is added here.

Each case defines a trigger and required observation. “Unresolved” marks a technical contract or proof obligation, not permission to invent behavior. Concurrent winners must be recorded explicitly; a test must accept permitted orderings without accepting unsafe ones. These tables cover the declared feature domains, not every possible Rust program or BEAM configuration. Expand them whenever admission gains an operation, type or resource.

## EXEC-01 — scheduler turns and execution ownership

**Dependencies:** LANG-01 public admission; LANG-03 suspension contract; lifecycle incarnation/terminal arbitration; mailbox wakeups; REF-01/02 oracle and harness.

**Tasks:** EXEC-01.T01 define execution-owner, ready, waiting, stopping and reclamation invariants without assuming particular structs. EXEC-01.T02 implement automatic renewable turns and state-preserving suspension. EXEC-01.T03 integrate control/wakeup handling and an event trace that can demonstrate exclusive execution and permanent stop.

| Case | Trigger / preconditions | Required outcome, permitted race or unresolved point |
|---|---|---|
| EXEC-01.C01 | Empty infinite admitted loop beside a runnable peer | Both repeatedly receive turns without authored yields or cancellation polling; measured latency is not a deadline. |
| EXEC-01.C02 | Nested loops, branches, `continue`, early return and supported recursion | Every admitted execution cycle reaches automatic boundaries; preserved state matches sequential execution. Unsupported syntax remains rejected. |
| EXEC-01.C03 | A process exhausts its turn repeatedly | Renew allowance and resume; quantum exhaustion never becomes lifetime-quota failure. |
| EXEC-01.C04 | Two wakeups arrive while a process is running or already queued | At most one application execution owner; coalescing is allowed only if runnable work remains represented. |
| EXEC-01.C05 | Wakeup races the transition into waiting | Either execution continues or a later turn is scheduled; no state can lose both the wakeup and runnable work. |
| EXEC-01.C06 | Kill reaches an actively executing process | Runtime regains control through the qualified mechanism, permanently stops application execution, then permits `Down`; no concurrent destruction. |
| EXEC-01.C07 | Kill reaches a queued, suspended or waiting process | Prevent every future application resume; remove/invalidate queued execution and wait ownership safely. |
| EXEC-01.C08 | Completion races kill | Exactly one terminal transition; lifecycle rules decide the observable reason. Neither ordering permits post-stop execution. |
| EXEC-01.C09 | Multiple runnable processes plus sustained control work | Application and necessary control progress remain demonstrable in the declared operating range; exact global turn order is unspecified. |
| EXEC-01.C10 | A stale queued entry/wakeup survives process-slot reuse | It cannot resume or retarget the replacement incarnation. |

## EXEC-02 — runtime operations and work budgets

**Dependencies:** LANG-02 operation/type inventory; LANG-03 resumable helpers; EXEC-01; mailbox scanning/payload transfer; REF-01/02.

**Tasks:** EXEC-02.T01 inventory every operation's input-dependent work and transitive callees. EXEC-02.T02 implement accounting and resumable phases where required. EXEC-02.T03 audit ownership at each phase and measure longest indivisible segments under representative load. Choose concrete work units during implementation; copying BEAM's numerical allowance is not required.

| Case | Trigger / preconditions | Required outcome, permitted race or unresolved point |
|---|---|---|
| EXEC-02.C01 | Long straight-line work or an approved helper contains computation | Qualify its full path; caller instrumentation alone cannot establish interruption of a non-returning callee. |
| EXEC-02.C02 | Budget is spent inside runtime work | Preserve operation progress and ownership across rescheduling; charge-after-return is insufficient evidence of schedulability. |
| EXEC-02.C03 | Collection growth, large copy, buffer freeze or fanout | Audit allocation/copy cost and suspension points; exact supported collections and representation remain admission outputs. |
| EXEC-02.C04 | Selective receive scans many nonmatches or expensive guards | Automatic scheduling covers scan and admitted matching work; retain mailbox semantics through suspension. |
| EXEC-02.C05 | Kill interrupts a resumable operation between phases | Release partially constructed state exactly once; never expose incomplete published state. Already completed external effects are not rolled back. |
| EXEC-02.C06 | Many tiny operations or one operation exceeds remaining allowance | Specify accounting granularity and overshoot; neither overflow nor zero-cost repeated work may bypass scheduling indefinitely. |
| EXEC-02.C07 | Runtime control consumes a turn before application dispatch | Account runtime work and retain required progress; no promise that the full allowance belongs to application code. |
| EXEC-02.C08 | An admitted path reaches an opaque native/dependency call | Reject or separately qualify it before admission. Worker offload does not establish forced stoppability. |
| EXEC-02.C09 | Cleanup or allocator work becomes the longest segment | Measure it separately and qualify continuation/offload treatment; a reduction counter cannot interrupt arbitrary allocator internals. |

**Forbidden:** hidden uninstrumented execution, counter wrap bypasses, duplicate operation effects after resume, and unsupported claims of hard real-time bounds. Tests combine large-operation/peer-progress runs with kill at each operation phase. BEAM explicitly treats potentially large GC separately; its final reclamation is not universally sliced. [GC decision](https://github.com/erlang/otp/blob/ad05823719d77c8faee87348ea39513d4e2f99c5/erts/emulator/beam/erl_gc.c#L688-L715). The [trapping-conversion test](https://github.com/erlang/otp/blob/ad05823719d77c8faee87348ea39513d4e2f99c5/erts/emulator/test/binary_SUITE.erl#L1927-L1975) is a crash regression, not a latency proof.

**Blocking gaps:** useful approved helper surface, cost model, resumable ownership and resource behavior of transitive dependencies.

**Performance-source refinements:** [report 37](../research/37-checkpoint-and-continuation-costs.md). All remain planned. Reference-specific representations and optional/later capabilities are conditional; the Rust implementation must preserve the applicable ownership and observable behavior, not copy the storage layout.

| Case | Branch, required treatment and acceptance evidence |
|---|---|
| EXEC-02.C10 | Specialized cheap helper crosses to variable-cost growth, tracing, failure or control work. Re-enter accounted/resumable work before an unbounded operation; qualification covers both sides of each specialization threshold. |
| EXEC-02.C11 | Cached allowance is spilled/reloaded across helper return, suspension and error. No reset, wraparound, duplicate debit or lost debit grants unbounded execution; changing checkpoint frequency requires a new maximum-segment argument. |

## EXEC-03 — cleanup and immutable shared buffers

**Dependencies:** LANG-02/03, EXEC-01/02, mailbox ownership, lifecycle notification ordering, accepted [immutable sharing](../adr/0008-immutable-buffer-sharing.md).

**Tasks:** EXEC-03.T01 define construction/freeze/reference ownership and physical accounting. EXEC-03.T02 implement phased process reclamation and a truthful completion observation, whose API remains unselected. EXEC-03.T03 qualify every owned resource, including failure during acquisition and release.

| Case | Trigger / preconditions | Required outcome, permitted race or unresolved point |
|---|---|---|
| EXEC-03.C01 | Normal completion, explicit exit or forced kill owns resident state | Release every covered ownership exactly once; cause of death does not excuse leaks or invalid access. |
| EXEC-03.C02 | Publisher dies after recipients acquire immutable references | Recipients retain valid immutable bytes; release the publisher's ownership only. |
| EXEC-03.C03 | Final owner releases storage, including simultaneous releases later | Exactly one physical release, after all live owners are finished. |
| EXEC-03.C04 | Kill during construction, freezing or reference publication | Audit each ownership transition; no mutable alias escapes freeze and no half-initialized buffer becomes readable. |
| EXEC-03.C05 | Death has queued, unmatched or partially transferred payloads | Resolve ownership with mailbox acceptance rules; no double release or orphaned payload at any boundary. |
| EXEC-03.C06 | Process has stopped but cleanup remains pending | `Down` may precede final reclamation; counters retain pending work and completion is not reported early. |
| EXEC-03.C07 | Large mailbox/resource graph requires teardown | Preserve peer progress while draining qualified work; distinguish logical release, physical free and allocator RSS retention. |
| EXEC-03.C08 | Native operation still accesses process-associated memory | Never free underneath it or issue stop-certified `Down` while its application computation continues. Such execution is not silently admitted. |
| EXEC-03.C09 | A resource needs user-defined `Drop`, callbacks or borrowed host lifetime | Admission must prove a compatible cleanup contract or reject it; exact supported types remain unresolved. |
| EXEC-03.C10 | Cleanup bookkeeping itself needs allocation or fails | Preserve outstanding ownership and truthful completion; recovery/fatal behavior must be specified with EXEC-04. |

**Forbidden:** destructor execution concurrent with use, premature last-reference free, hidden retained bytes, and equating RSS with logical cleanup. Test ownership counters, retained-recipient reads and deterministic acquisition/release failure points. BEAM's [dirty-NIF regression](https://github.com/erlang/otp/blob/ad05823719d77c8faee87348ea39513d4e2f99c5/erts/emulator/test/dirty_nif_SUITE.erl#L247-L305) demonstrates logical death before native completion; Bream's accepted stop guarantee deliberately excludes that exception.

**Blocking gaps:** resource inventory, construction/freeze implementation, reclamation scheduling and completion semantics. Arbitrary Rust destruction is not approved by the phrase “runtime-managed cleanup.”

**Performance-source refinements:** [report 34](../research/34-message-allocation-and-copy-costs.md). All remain planned. Reference-specific representations and optional/later capabilities are conditional; the Rust implementation must preserve the applicable ownership and observable behavior, not copy the storage layout.

## EXEC-04 — panic, allocation and capacity failures

**Dependencies:** LANG-01/02 allocation/publication inventory; lifecycle/mailbox publication; EXEC-03 accounting; REF-02 failure harness.

**Tasks:** EXEC-04.T01 classify failure sites and distinguish recoverable errors from host-fatal conditions. EXEC-04.T02 define the Rust-specific panic/allocator contract before implementing containment. EXEC-04.T03 add fault injection and verify every partially completed operation. No arbitrary process-memory quota is selected.

| Case | Trigger / preconditions | Required outcome, permitted race or unresolved point |
|---|---|---|
| EXEC-04.C01 | Process-slot capacity is exhausted | Reference is spawn failure, not creation of a usable partial process; Rust error representation remains to specify. |
| EXEC-04.C02 | Allocation fails before or after spawn publication | Distinguish unpublished rollback from published lifecycle failure; cleanup and relationship notifications must agree with the publication point. |
| EXEC-04.C03 | Payload/queue/monitor allocation fails | Define outcome and retained ownership at each site; accepted growing mailboxes do not imply infinite memory. |
| EXEC-04.C04 | Layout arithmetic overflows or a size is unsupported | Reject safely before invalid allocation/access; exact error mapping belongs to the admitted operation contract. |
| EXEC-04.C05 | Admitted helper panics after partial mutation | Panic containment and exit-reason policy remain unresolved; prove consistency before promising process-only failure. |
| EXEC-04.C06 | Panic hook or panic-payload destruction runs code | Include these paths in containment analysis; catching unwind alone does not bound them. |
| EXEC-04.C07 | Abort configuration, fatal allocator failure or runtime invariant failure | Do not advertise process isolation against host termination; define supported build assumptions and report the boundary. |
| EXEC-04.C08 | Cleanup fails while handling another failure | Prevent false completion and double release; determine whether supported cleanup must be non-panicking or needs another explicit strategy. |
| EXEC-04.C09 | Exhaustion races release of capacity | Either operation may win; no over-allocation of a logical slot, stale identity or permanent capacity leak. |

**Forbidden:** claiming all OOM is catchable, inventing bounded mailboxes as the remedy, or continuing with invalid ownership after panic. Run fault-injected paths and host-fatal negative controls in separate watchdog-contained executables. BEAM distinguishes [process-slot exhaustion](https://github.com/erlang/otp/blob/ad05823719d77c8faee87348ea39513d4e2f99c5/erts/emulator/beam/erl_process.c#L12524-L12540) from [fatal allocation helpers](https://github.com/erlang/otp/blob/ad05823719d77c8faee87348ea39513d4e2f99c5/erts/emulator/beam/erl_alloc.h#L199-L215); [repeated process exhaustion](https://github.com/erlang/otp/blob/ad05823719d77c8faee87348ea39513d4e2f99c5/erts/emulator/test/node_container_SUITE.erl#L909-L965) supplies a reference scenario. Rust-specific limitations are documented in [report 17](../research/17-execution-resource-edge-cases.md).

**Blocking gaps:** panic policy, fallible-allocation coverage, publication rollback, diagnostic allocation and fatal-path behavior.

## EXEC-05 — runtime embedding and shutdown

**Dependencies:** LANG-01, EXEC-01/03/04, handle/incarnation model. This is a Rust-library integration contract, not an OTP application lifecycle API.

**Tasks:** EXEC-05.T01 define runtime construction, handle ownership and shutdown states. EXEC-05.T02 implement stop/drain/reclamation coordination with explicit outstanding-work accounting. EXEC-05.T03 qualify host concurrency and partial initialization. Exact synchronous/asynchronous shutdown and `Drop` behavior remain unselected.

| Case | Trigger / preconditions | Required outcome, permitted race or unresolved point |
|---|---|---|
| EXEC-05.C01 | Runtime initialization fails partway | Release acquired resources safely; expose no operational handle into uninitialized scheduler state. |
| EXEC-05.C02 | An ordinary process address is dropped | Address disposal alone does not kill the process; distinguish address lifetime from runtime ownership. |
| EXEC-05.C03 | Shutdown begins with running, waiting and queued processes | Safely stop admitted execution and account cleanup; never free continuations still capable of resuming. |
| EXEC-05.C04 | Spawn/send/kill races shutdown | Specify admission cutoff and permitted winners; accepted work remains owned, rejected work has a defined payload outcome. |
| EXEC-05.C05 | Repeated/concurrent shutdown requests | Coordinate one state transition and truthful results; idempotent API details remain unresolved. |
| EXEC-05.C06 | Host retains addresses or wakeups after shutdown | No dereference of reclaimed runtime state or retargeting into a different runtime; return/no-op/error representation remains unspecified. |
| EXEC-05.C07 | Runtime handle is dropped from process execution or a callback | Qualify reentrancy and self-wait hazards; do not choose blocking `Drop` without proving it cannot deadlock. |
| EXEC-05.C08 | Shutdown encounters pending cleanup or a failed worker | Completion cannot claim unperformed work; escalation/recovery policy remains an explicit technical gap. |
| EXEC-05.C09 | Multiple runtimes coexist, or foreign-runtime handle is supplied | Maintain runtime/incarnation identity separation; cross-runtime communication support is not implicitly promised. |

**Forbidden:** use-after-shutdown, self-join deadlocks, abandoned unaccounted resources and shutdown success while admitted application work continues. Test barrier-controlled shutdown races, retained handles and injected construction/worker failure. BEAM node shutdown is not automatically the specification for an embedded Rust runtime's destructor.

**Blocking gaps:** host ownership model, reentrancy, admission cutoff and shutdown completion/failure contract.
