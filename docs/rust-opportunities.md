# Where Rust can help Bream

**Research map, updated 2026-10-08. No production representation is selected; all earlier speed measurements were removed and require new qualification.** The strongest opportunity is to avoid machinery that BEAM needs for dynamically typed, garbage-collected terms by giving Bream native typed state with enforceable ownership. Rust also helps express and check transitions that the C runtime coordinates manually. Neither opportunity removes the need for a scheduler, runtime-controlled stopping or concurrent lifetime protocols.

Read this with the [new heap](research/38-process-heap-roots-and-rust-ownership.md), [process-table/spawn](research/39-process-table-and-spawn-publication.md), [allocator](research/40-allocator-ownership-and-rust-runtime-storage.md) and [Rust-language probe](research/41-rust-guarantees-and-process-admission.md) reports. Their source references distinguish BEAM behavior, reference implementation details, Rust guarantees and proposed adaptations. [Experiment backlog](performance-plan.md).

These are opportunities to measure on the same process contract, not a request to port the BEAM garbage collector or all allocator policies. Native typed state is a representation choice; treating all native Rust values as automatically admitted would discard the very lifetime control that makes the plan plausible.

## What the probes add

The [isolated Rust fixtures](../evidence/rust-ownership-review/README.md) produced their expected observations in both compiler profiles. They show usable building blocks: consumed-value errors, a borrow boundary, typed-protocol mismatch, nontransferable state rejection, a pinned-move restriction, allocation-preserving `Vec` transfer and ordinary cleanup of one suspended borrowed frame.

They also show why the Bream boundary must be more specific: safe `Send + Sync + 'static` data can share a mutex; a captureless callable can reach a global; `forget` and `ManuallyDrop` suppress destruction; and a `Copy` payload with no drop glue can carry a nonreturning callback. That callback was compiled only. No fixture implements a mailbox, process scheduler or hostile-code boundary.

The language probes answer factual questions we should not ask the user. The remaining question is whether a useful public Bream API can enforce the accepted execution/resource contract. PERF-052/054 turn that into external-consumer and cleanup-bypass work rather than an assumption about marker traits.

The [new atomic projections](research/49-rust-atomic-protocol-observations.md) add a different kind of evidence. Three positive variants completed; four weakened variants exposed stale publication, missing final-owner visibility or a lost wakeup. Every projection uses safe Rust, showing that atomic types alone do not establish a logical protocol. Their small Loom models do not implement pointer reclamation, actual sleep or process kill and cannot certify the ERTS/Bream memory model. Use those counterexamples when reviewing proposed reductions in barriers, refcounting and lock traffic; passing them is only a prerequisite.

## Concrete room/session consequences

An initial useful room holds owned membership state and receives a typed envelope containing application messages and runtime notifications. Its publication path could freeze a byte builder once, retain its own immutable reference and transfer independently owned references to sessions. A session may disappear during fanout; the room's continuation must retain the undelivered ownership and its fanout position. Already delivered messages remain delivered. Killing the room releases its obligations while live sessions retain valid bytes.

That scenario needs neither a tagged Erlang heap nor a full GC by default, but it still needs qualified membership operations, allocation, reference updates, automatic boundaries, monitor cleanup and dead-address behavior. A standard container's hidden growth, hashing, comparison or destructor callback must be qualified before its concise Rust syntax is advertised as process-safe. These are application operations to admit, not new OTP behaviours to implement.

The first useful prototype should therefore exercise three concrete transitions: typed state into a suspended continuation, owned data into a queued message, and runtime-owned resources into tracked cleanup after kill. Include first allocation, partial initialization, lost publication races and forgotten handles. Measure through final cleanup, not only the fast successful send.

When room sessions gain runtime-aware sockets, add a fourth story: a session dies with readiness already detached for delivery, while its descriptor number is about to be reused. Stop application execution, dispose of notification ownership, complete backend access and close the right handle. The [Linux probes](research/45-linux-io-observations-and-rust-boundary.md) demonstrate why those are separate events. Observers of the room may disappear during large snapshots too; their cleanup must not monopolize unrelated process turns.

## How to choose among the alternatives

1. **First prove useful admission.** Extend the public-boundary experiment with typed records/enums, owned bytes, a small membership collection and approved helpers. Use the language probes as controls, not as a substitute for testing the actual macro/API from another crate.
2. **Then compare representations.** Keep the same room protocol and failure observations while comparing individual ownership, process-private regions and stable typed storage. Preserve a simple correct baseline; no region strategy is chosen by this document.
3. **Make ownership transitions visible.** Track obligations at construction, publication, receipt, death and final shared release. Distinguish lost handles from resources the runtime may safely reclaim, and distinguish actual freed storage from allocator retention.
4. **Optimize demonstrated costs.** Remove generic tracing, copying or repeated atomic retention only when the replacement proof is clear. Compare code size, resident memory, peer latency and kill/cleanup tails alongside throughput.

Domain and guard types are particularly useful at the internal runtime boundary: they can prevent ordinary safe callers from confusing record retention, field access and permission to run application code. Keep those guards out of admitted long-running code. For clocks, distinguish a valid deadline from observing it and from servicing it; an active BEAM timer can report integer zero remaining before its final fractional tick is over. Neither a zero reading nor a quiescent worker is a generic completion notification.

The [feature catalogue](build-plan.md) records the additional branch obligations. All older behavior IDs and performance task IDs remain valid. No new ADR is warranted: this pass has not chosen a hard-to-reverse engine, ownership representation or public API.

## Source concerns are investigation tasks

The process-table review found rare branches involving full identity reuse, a rejected link allocation and the absolute maximum-size sentinel/free-ID pool. Their reachability and effects remain unexecuted. Earlier late-buffer installation and timer rearm concerns are also still qualified source questions. They motivate explicit ownership-result types, reduced models and branch-confirmed reference experiments; they are not proof that Rust would automatically fix an upstream defect, nor confirmed production vulnerability claims.

The [new variance controls](research/53-name-routing-reference-and-variance-observations.md) demonstrate a safe covariance conversion that bypasses a constructor's stored type check; an invariant marker rejects the same conversion. These strengthen the type-authority review for named routes without selecting a namespace or mismatch API. The accompanying local BEAM observations check resolution, rebinding, enumeration lifetime and competing registrations; neither set supplies a speedup or full concurrency proof.

## Performance evidence reset

The user ordered all speed-test evidence removed and redone. PERF-091, PERF-100 and PERF-101 have no retained timing conclusions. The [static-payload source](research/56-static-payload-cost-observations.md), [notification models](research/57-worker-notification-models-and-load-observations.md), and broader ownership/checkpoint hypotheses remain useful inputs. Do not infer a speed improvement from fewer reference updates or notification calls. All timing qualification is deferred to an authorized suitable environment.
