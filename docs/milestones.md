The fifteen passed milestones are narrower than completing G1, G2, G3, G4 or G5. They use real native generated code and experimental public boundaries; they are not a published, general-purpose library. Frame layout, consuming ownership transfer and avoiding unnecessary queue-node allocation remain useful structural observations. All earlier speed measurements and derived claims were removed; they must be redone. Correctness progress does not select a production allowance or establish a latency guarantee.

## Next bounded milestone

The user's intervening [termination-boundary claim check](research/59-termination-boundary-observations.md) passed thirty expected Rust/BEAM semantic observations on 2026-10-09. It is a research qualification, separate from the implementation count. It confirms separate obligations for parent/child execution, application invariants and cleanup; it does not qualify arbitrary native termination.

The subsequent [historical green-runtime investigation](research/63-rust-green-runtime-lessons-and-experiments.md) also completed on 2026-10-09: original Rust 0.12 execution plus modern ownership/registration probes passed twenty expected observations. This is research, not another implementation milestone. Its operation-owned storage, callback completion and late-result identity findings motivated milestone fourteen; those research prototypes did not themselves expand the admitted runtime.

Checked self-exit and targeted local exit subsequently passed as implementation milestone thirteen. Its [findings](research/65-explicit-exit-milestone.md) preserve the distinction between uncaught self-exit, direct kill and linked propagation, and document the eager direct-receipt limit.

The subsequent [runtime-owned read milestone](research/67-owned-read-milestone.md) passed as implementation milestone fourteen. It qualifies one-shot endpoint ownership through actor death, result delivery/disposal and host shutdown. The endpoint closes after the first completed read, including a short read.

The subsequent [persistent-read milestone](research/69-persistent-read-milestone.md) passed as implementation milestone fifteen. Successive reads retain the endpoint and give each request a distinct identity. Old cancellation/readiness/completion cannot affect the next request. Stop between reads, retained buffers, captured poll snapshots and shutdown have bounded ownership evidence. Private cancellation remains intent rather than synchronous revocation.

Next, admit bounded persistent-read timeouts using the existing injected logical clock. Derive data/timeout arbitration and cancellation settlement from the pinned BEAM socket and timer paths. Define when a timeout wins against a ready result and when the endpoint becomes usable again; timeout alone must never free a claimed buffer or admit an overlapping read. Preserve one process owner, one application worker and one driver.

Require controlled data-before-deadline and timeout-before-data cases, a permitted-outcome race, and zero/infinite semantics if exposed. Old timer callbacks, request cancellation and late completion must not affect a later request on the same endpoint. Cover request settlement before reuse, retained earlier bytes, peer progress, owner stop, replacement and shutdown with both timer and endpoint obligations pending. Distinguish cancelled delivery from bytes already consumed externally.

This advances partial G1/G2/G3 resource and timer integration. Arbitrary user FFI/futures, writes, endpoint transfer, general membership churn, real-time timers and full resource qualification remain open. Responsiveness remains the user's chosen priority; use logical ordering and correctness assertions only, never elapsed peer/stop latency measurements here.

Source work remains driven by an unresolved obligation in the milestone, not by a goal of reading every BEAM function. Keep the broader source frontier available without expanding it as a substitute for executable progress.

Each future update should say what milestone passed, what failed or changed, which evidence supports it and what remains. The [full build gates](build-plan.md#build-order-and-exit-gates) remain authoritative for broader qualification.
