## What belongs here

Include a mechanism if it governs a process's execution, owned state, identity, addressing, communication, relationships, lifetime, timing or runtime observation. Include native integration where it determines whether a process can stop and reclaim resources. That gives us a process runtime, not an Erlang-distribution port.

Exclude compression/ZIP algorithms, cryptographic algorithms, codecs, regular-expression engines, HTTP clients and similar application libraries. Rust libraries can supply those capabilities. Their scheduling and resource-lifetime **integration** still needs qualification if invoked inside guaranteed Bream process code. We do not need to reimplement the algorithm to recognize an uninterruptible native call or a destructor that can run indefinitely. [Native-library boundary](research/22-process-io-native-boundary.md).

Runtime primitives and OTP behaviours remain separate. An implementation residing in an Erlang module is not automatically an OTP behaviour, and a utility implemented as a BIF is not automatically a process primitive. For example, the preloaded code purger consumes runtime signals and kills, while `gen_server`'s `hibernate_after` option is library policy over runtime hibernation. Neither file location nor the label “built-in” alone determines Bream's scope.

## Findings that change the plan

1. **Run-queue records and execution ownership differ.** Proxy entries can represent one process in more than one scheduling context; the invariant is one application execution owner, not necessarily one physical queue node.
2. **Scheduling priority and priority message reception differ.** The latter can place a later priority item before earlier ordinary items while signal delivery remains ordered, and can redirect an already-progressed receive cursor.
3. **Ordinary repeated links and option changes differ.** The relationship is idempotent, but a later link call can change the caller endpoint's priority-message setting.
4. **Timer service, timer creator and timer recipient are different owners.** A PID-targeted timer follows the recipient's lifetime; registered names are resolved at expiry. Cancellation results do not prove mailbox absence.
5. **Explicit suspension and scheduler preemption differ.** OTP 29 pauses receive/PID-targeted message timers under explicit process suspension. Merely taking away a scheduling turn does not pause deadlines.
6. **Snapshot enumeration and incremental iteration differ.** They intentionally expose different consistency guarantees; the chosen Rust observation API must say which it supplies.
7. **Native cancellation and physical resource release differ.** Poll coordination may postpone safe descriptor closure beyond cancellation and process death.
8. **Access to external state and responsibility for its cleanup differ.** ETS deletion can transfer cleanup ownership to the deleting process so its death cannot orphan unfinished work; port connection and link sets also differ.
9. **Catching an exception and trapping an exit differ.** Language error handlers can resume a process; runtime forced termination cannot be neutralized by them.
10. **Logical death and closing ingress differ.** Previously protected senders may publish into still-open buffer slots; exit owns draining them.
11. **Queue reservation and physical insertion differ.** Parking and notification must retain an accountable enqueue obligation through that interval.
12. **Local cancellation and peer cleanup differ.** Unlink uses correlated completion; demonitor removes notification permission before peer cleanup finishes.
13. **A stale unlink acknowledgment and an old linked EXIT differ.** Relink invalidates the acknowledgment ID; ordinary linked EXIT has no such operation ID and can affect the reactivated link.

Each item is traced and qualified in its report. [Report29](research/29-pinned-reference-observations.md) now records exact-version observations for synthetic flush, paused timer references, dead-target tagged suspension, the 255/256/257 hibernation boundary and a controlled local notification-order setup. It also reproduces a debug-interpreter assertion in the optimized-marker path, with successful unoptimized and release-JIT controls. Untested option/race products remain open; observed discrepancies are not automatically intended Bream contracts.

## What still prevents an exhaustive-coverage claim

The earlier ownership source pass closed named protocol gaps: buffer-slot closure differs from logical process death; direct parking carries MSGQ through inactivity; timer callbacks arbitrate identity before waking; unlink and demonitor have different local cancellation barriers. Two finite abstractions now exercise record retention and direct parking, but exclude weak memory, buffered/timer products and execution claims by another worker. A source-level late-buffer-reinstallation candidate remains unclosed and has not been reproduced as an upstream defect.

The process-facing inventory is substantially wider; the entire implementation is not certified. The [machine-checked dispatch inventory](../evidence/process-deep-review/signal-dispatch-inventory.json) covers all declared control opcodes in the two main dispatchers, not their transitive implementations. Remaining work includes complete multiworker memory-order/reclamation reasoning, all scheduler/dirty/system-task combinations, all GC root/fragment paths, priority/marker products, precise timeout races, every diagnostic item and observer race, full OS polling-backend/error coverage, distributed reconnect/encoding and the full code/literal lifetime machinery. The executable cases, Rust mapping and ownership proof remain distinct from source coverage.

The plan now contains **40 feature groups and 537 stable branch cases**, including conditional reference/extension work. The first deeper pass added 138 cases; the first protocol follow-up added 29; the ownership/wakeup pass added 26; the performance-source pass added 31; the Rust ownership/source pass added 24; the I/O/observation pass added 27; the concurrency/clock pass added 26; the task/code/routing pass added 23; the worker/async-service pass adds 14. The separate [107-task optimization backlog](performance-plan.md) tracks performance candidates. Counts are not completeness percentages or test results. [Current validation record](../evidence/worker-service-review/review-validation.json).

The build sequence remains admission and useful state first, then single-worker execution/kill, messaging, relationships and the room fixture. Newly researched extensions get their own cases and dependencies; they do not make unresolved initial safety gates disappear. Clear BEAM facts remain engineering input, not additional preference questions for the user.

The concurrency/clock pass distinguishes inactive participants from quiescent access, managed-worker blocking from all-reader retirement, and lock ownership from execution permission. It also separates monotonic deadlines from wall-clock offset and timer service. Those distinctions support typed Rust interfaces and concrete tuning experiments, while the complete atomic/reclamation, lock-graph and clock-provider proofs remain open. The seven small Loom invocations are evidence only for their named projections and negative controls.
