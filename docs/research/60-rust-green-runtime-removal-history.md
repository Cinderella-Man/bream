# Rust green threads: what was removed, and what it had actually solved

**2026-10-09. Primary-source history and source inspection.** Original-runtime execution is reported separately in [report 63](63-rust-green-runtime-lessons-and-experiments.md). This review traces Rust's green-thread removal to the accepted proposal, implementation commits, and the earlier linked-failure implementation. It does not treat historical authors' performance assessments as performance evidence for Bream. No benchmarks or measurements were run.

## Finding

Rust's green runtime is a useful design precedent, but it is **not evidence that arbitrary-code preemption and safe termination had already been solved**. The late-2014 implementation explicitly used cooperative scheduling. Its documentation warned that an infinite loop prevents other tasks on the same scheduler from running. Linked failure had been removed a year earlier, with scheduler races and implementation complexity among the stated reasons. These are separate historical changes. [Pre-removal scheduling contract](https://github.com/rust-lang/rust/blob/770378a313a573776b16237a46b75bafa49072c1/src/libgreen/lib.rs#L51-L69), [linked-failure removal](https://github.com/rust-lang/rust/pull/10603).

The useful lesson for Bream is not that Rust cannot support these features. It is that scheduling, cancellation, native interoperability, I/O integration, and runtime shutdown have distinct contracts. Providing a green stack and context switch did not collapse them into one solved problem.

This chronology rules out both “Rust removed green threads because it could not grow stacks in November 2014” and “Rust's 2014 runtime still provided the original linked-kill model.” The underlying work evolved across several years and separate decisions.

## What the 2014 scheduler promised

Immediately before final removal, `libgreen` describes an M:N scheduler: each scheduler is one OS thread, and each task owns a stack and register context. Tasks can migrate within a scheduler pool. Scheduling occurs at communication and I/O boundaries, not at arbitrary native instructions. The documentation separately warns about blocking native code, native thread-local storage, OS-thread-based synchronization, and `fork`. It also explicitly avoids concluding that all native interoperability is hopeless. [Pinned `libgreen` documentation](https://github.com/rust-lang/rust/blob/770378a313a573776b16237a46b75bafa49072c1/src/libgreen/lib.rs#L20-L111).

For Bream, a stackful coroutine offers an ergonomic advantage: synchronous-looking calls can suspend through a runtime-aware operation anywhere down the stack. That alone does not insert scheduling points into a dependency's CPU loop, convert native blocking into task suspension, or provide arbitrary cancellation. This distinction is an inference from the documented architecture, not a historical performance comparison.

## Earlier task killing used controlled delivery, not arbitrary interruption

A source revision before linked-failure removal is especially relevant. In revision `09eca11805fd523b569047d0ec257cfbf439a73c`, `KillHandle::kill` changes atomic state and, when it obtains ownership of a blocked task, returns that task to be rescheduled. It does not inject a signal-driven unwind at an arbitrary program counter. The target's `check_killed` converts a pending request into `fail!`, unless cancellation is inhibited or unwinding is already underway. The scheduler invokes this check after its context-switch cleanup job. [Kill request implementation](https://github.com/rust-lang/rust/blob/09eca11805fd523b569047d0ec257cfbf439a73c/src/libstd/rt/kill.rs#L425-L459), [delivery check](https://github.com/rust-lang/rust/blob/09eca11805fd523b569047d0ec257cfbf439a73c/src/libstd/rt/kill.rs#L630-L671), [scheduler call site](https://github.com/rust-lang/rust/blob/09eca11805fd523b569047d0ec257cfbf439a73c/src/libstd/rt/sched.rs#L608-L627).

The implementation distinguishes killable and unkillable regions. An inhibited request remains pending until killing is allowed again; cleanup and unwinding require special treatment. This is a concrete ancestor of a deferred-cancellation design, not proof that ownership permits arbitrary instruction-level destruction. Some retained linked-failure tests are explicitly ignored at this snapshot, so merely finding them is not evidence they passed. [Design comments](https://github.com/rust-lang/rust/blob/09eca11805fd523b569047d0ec257cfbf439a73c/src/libstd/rt/kill.rs#L24-L52), [retained ignored tests](https://github.com/rust-lang/rust/blob/09eca11805fd523b569047d0ec257cfbf439a73c/src/libstd/rt/kill.rs#L924-L960).

There is unusually direct contemporary evidence of the hard boundary. Issue #8674 reports that linked failure could resume a task blocked in I/O and cause failure that the I/O implementation did not recover correctly. It proposes temporarily making I/O blocking non-interruptible, then admitting interruption case by case. This is not our retrospective speculation about destructors; it is a failure-safety concern raised against the actual runtime. [I/O failure-safety issue](https://github.com/rust-lang/rust/issues/8674).

The initial linked-failure PR review also questioned the combination of linked, supervised, and watched modes; shared bookkeeping around spawn and termination; synchronization needed for interruptible I/O; and the absence of a complete graceful-shutdown solution. The later removal PR cites a complex model, an implementation few people fully understood, known context-switch races, and uncertainty about mapping the semantics to native threads. These are maintainers' stated reasons, not evidence of a Rust-language impossibility. [2013 design review](https://github.com/rust-lang/rust/pull/7858#issuecomment-21224028), [removal rationale](https://github.com/rust-lang/rust/pull/10603).

## Why the dual runtime was removed from the standard library

RFC #230's stated problem was the coupling of native and green execution behind the same standard I/O interface. Supporting both forced APIs to evolve together despite different needs. It also complicated embedding, task-local storage, library maintenance, and binary inclusion. The proposal attributes some allocation and dispatch overhead to the abstraction, but explicitly treats those costs as weak arguments relative to I/O itself. It proposes native standard-library I/O and an external green package, leaving other lightweight concurrency designs open. **None of these claims establishes a present-day Rust-versus-BEAM speed result.** [Accepted RFC](https://rust-lang.github.io/rfcs/0230-remove-runtime.html).

The discussion gets closer to our dependency question than a generic “green threads were slow” summary does. A reviewer points out that libraries perform incidental I/O, including logging: making standard I/O native can make those libraries problematic in alternative execution environments. The RFC author agrees this is a downside, while noting that seemingly innocent operations could already block a green worker under the existing runtime. A later reply says preserving the old green model would require separate I/O, logging, and related functionality. Thus ecosystem compatibility was a recognized integration burden; its existence was not a discovery after extraction. [Incidental-library-I/O concern and response](https://github.com/rust-lang/rfcs/pull/230#issuecomment-55058943), [separate functionality discussion](https://github.com/rust-lang/rfcs/pull/230#issuecomment-55543019).

The acceptance meeting frames the decision as enabling native APIs and exploration of other lightweight threading models, rather than declaring all green runtimes invalid. [2014-09-16 meeting, pinned archive](https://github.com/rust-lang/meeting-minutes/blob/64c85df3b86d2c19183257892294d4ad80cdd0a8/weekly-meetings/2014-09-16.md#removing-io-runtime-abstractions).

The final-removal PR also changed during review. Its discussion considered ending the whole OS process when main returned, then restored outstanding-task bookkeeping for that stage. Process-wide exit is not isolated cancellation of each other task, and an early PR comment is not the final merged contract. This report does not use those early comments as evidence of safe actor killing. [PR #18967 discussion and final diff](https://github.com/rust-lang/rust/pull/18967).

## What happened to the external package

The extraction route was real. `green-rs` has a documented Cargo dependency, a `green` package, and separate `rustuv` I/O. The initial import is August 20, 2014. The latest reachable default-branch commit inspected on October 9, 2026 is `b7e17fc19bb90d0bb53914e66251e68cc15594e4`, dated November 19, 2014. Its source still uses pre-1.0 interfaces including `native`, `std::task`, and public runtime internals. The snapshot predates final in-tree green/native removal. [Initial import](https://github.com/alexcrichton/green-rs/commit/21c3cbcdbc6cb33e564870842ea6060f685f51d1), [last inspected commit](https://github.com/alexcrichton/green-rs/commit/b7e17fc19bb90d0bb53914e66251e68cc15594e4), [README](https://github.com/alexcrichton/green-rs/blob/b7e17fc19bb90d0bb53914e66251e68cc15594e4/README.md), [source imports](https://github.com/alexcrichton/green-rs/blob/b7e17fc19bb90d0bb53914e66251e68cc15594e4/libgreen/src/lib.rs#L209-L230).

That is evidence of an attempted out-of-tree continuation and a historical code archive. It is **not** evidence of a maintained package compatible with modern Rust, nor sufficient evidence to assign a single cause to its lack of later commits. No historical checkout was compiled. The external package's own documentation retains the cooperative scheduling and native-interoperability warnings. [External contract](https://github.com/alexcrichton/green-rs/blob/b7e17fc19bb90d0bb53914e66251e68cc15594e4/libgreen/src/lib.rs#L51-L111).

## Concrete ideas for Bream

These are research recommendations inferred from the history, not historical promises or completed implementation work:

1. **Separate preemption requests from cancellation delivery.** Native interruption could ask the runtime to reschedule, while cancellation remains deliverable only at a boundary with a valid cleanup contract. The earlier `unkillable` regions supply a concrete precedent. This does not imply such regions meet our responsiveness target; their work must also be bounded or explicitly isolated.
2. **Give every pending operation an ownership and quiescence protocol.** The I/O failure report suggests a precise experiment: cancellation races with registration, completion, and deregistration; exactly one participant owns the result or buffer, and late completion cannot access reclaimed actor state. Qualifying ordinary success is insufficient.
3. **Keep the process core separate from I/O providers and opaque native execution.** Rust's standard library had to serve a broad systems-language mandate. Bream can choose a narrower service-runtime contract without making its scheduler and every supported I/O backend co-evolve behind one universal native/green abstraction.
4. **Describe compatibility at operation boundaries before adopting whole-crate labels.** A dependency's hashing loop, logging path, TLS assumption, and blocking call have different effects. Some need inserted checkpoints, some task-aware adapters, some thread affinity, and some offload. “Actor-safe crate” is too coarse until we have tested these effects.
5. **Test thread identity assumptions separately from progress.** A context switch can preserve registers yet still violate a library's expectation of native TLS or mutex ownership. Keeping a task pinned avoids migration-related failures but does not by itself fix same-thread reentrancy or native blocking.
6. **Do not equate linkage with structured shutdown.** Rust's earlier linked/watched/supervised combination shows how much policy can accumulate around spawn and death. Bream should independently specify who receives exit information, who is requested to stop, which children are owned, and when cleanup is complete.

The next useful experiment is not another demonstration that two arithmetic loops can alternate. It is a bounded operation with a pending callback, an explicit cancellation request, and a completion/reclamation handshake, including cancellation before registration, during the wait, and after completion wins. A separate thread-affinity/TLS probe can test whether the intended native scheduling model preserves a dependency's environment. Neither requires a speed measurement.

This history supports the narrow statement that **memory ownership is not a complete scheduling or cancellation contract**. It rejects the premise that Rust's 2014 green threads had already supplied arbitrary preemption and safe kill. It also rejects using their removal as proof that Bream is doomed: the removal addressed Rust's standard-library architecture and maintenance goals, while leaving specialized runtime exploration explicitly open.
