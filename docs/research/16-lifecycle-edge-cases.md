# Lifecycle edge cases: bounded BEAM coverage audit

**Execution follow-up:** [Report 29](29-pinned-reference-observations.md) now records targeted observations on the exact pinned build. The source-only status and hypotheses below describe the original review stage; the follow-up identifies which variants were executed and which remain unresolved.

Snapshot: 2026-10-07; OTP 29.1.1, commit `ad05823719d77c8faee87348ea39513d4e2f99c5`. **We have not established behavior in every edge case.** This audit sharpens 18 local lifecycle cases against pinned documentation, source, and selected upstream tests. It does not execute OTP, execute those tests, or certify Bream's implementation.

The [working rule](../../CONTEXT.md) is to replicate established BEAM semantics rather than ask the user to choose them. “Several outcomes are allowed” is an exact concurrency contract when the operations race; it is not permission to choose any outcome. Implementation mechanisms below explain guarantees without making their data structures part of Bream's API.

Scope: ordinary local process PIDs, ordinary links and one-shot process monitors; no priority messages, aliases, distribution, ports, or OTP behaviours. Each test citation means **test source inspected**, not test passed here.

## Monitors

1. **Monitor self.** The call returns a reference but installs no monitor relationship and produces no runtime DOWN. The local BIF has an explicit self branch; the upstream test checks both PID and locally registered-name forms and verifies absence of monitor entries and messages. Do not create a self-observation cycle in Bream merely because the API returns a token. [implementation](https://github.com/erlang/otp/blob/ad05823719d77c8faee87348ea39513d4e2f99c5/erts/emulator/beam/bif.c#L765-L799); [test](https://github.com/erlang/otp/blob/ad05823719d77c8faee87348ea39513d4e2f99c5/erts/emulator/test/erl_link_SUITE.erl#L236-L253).

2. **Repeated monitors of one target.** Each call creates an independent monitor reference, not an idempotent subscription. Each uncancelled relationship can produce its own one-shot DOWN. Cancelling one must leave the others intact. This differs from repeated link. [documented contract](https://github.com/erlang/otp/blob/ad05823719d77c8faee87348ea39513d4e2f99c5/system/doc/reference_manual/ref_man_processes.md#L713-L727); [multiple-monitor fixture](https://github.com/erlang/otp/blob/ad05823719d77c8faee87348ea39513d4e2f99c5/erts/emulator/test/monitor_SUITE.erl#L287-L299).

3. **Monitor an already-dead local PID.** Return a reference and arrange DOWN with `noproc`; do not synchronously fail with the target's historical reason. “Immediate” in the reference does not make delivery synchronous with the API return. The request and notification are signals. [asynchronous monitor contract](https://github.com/erlang/otp/blob/ad05823719d77c8faee87348ea39513d4e2f99c5/erts/preloaded/src/erlang.erl#L4514-L4536); [dead-target test](https://github.com/erlang/otp/blob/ad05823719d77c8faee87348ea39513d4e2f99c5/erts/emulator/test/monitor_SUITE.erl#L420-L422); [failure conversion](https://github.com/erlang/otp/blob/ad05823719d77c8faee87348ea39513d4e2f99c5/erts/emulator/beam/bif.c#L786-L797).

4. **Monitor races with target death.** Separate spawn then monitor may report the actual exit reason or `noproc`, depending on whether the relationship was established in time. The upstream test explicitly accepts `normal` **or** `noproc` for a short-lived child. Exit cleanup turns an unprocessed late monitor request into `noproc`. Never hard-code one winner or infer death history from a PID lookup. [race and atomic-spawn comparison](https://github.com/erlang/otp/blob/ad05823719d77c8faee87348ea39513d4e2f99c5/erts/emulator/test/monitor_SUITE.erl#L399-L409); [late monitor handling](https://github.com/erlang/otp/blob/ad05823719d77c8faee87348ea39513d4e2f99c5/erts/emulator/beam/erl_proc_sig_queue.c#L7347-L7353).

5. **Default demonitor races with DOWN.** After demonitor returns, no new DOWN caused by that monitor may be placed in the caller's mailbox. A DOWN already there may remain. Removal of the origin entry prevents an in-flight signal from later becoming a message. The regression test permits a queued DOWN immediately after the call, then rejects a later one. [guarantee](https://github.com/erlang/otp/blob/ad05823719d77c8faee87348ea39513d4e2f99c5/erts/preloaded/src/erlang.erl#L2024-L2055); [conversion gate](https://github.com/erlang/otp/blob/ad05823719d77c8faee87348ea39513d4e2f99c5/erts/emulator/beam/erl_proc_sig_queue.c#L6367-L6378); [race test](https://github.com/erlang/otp/blob/ad05823719d77c8faee87348ea39513d4e2f99c5/erts/emulator/test/erl_link_SUITE.erl#L462-L478).

6. **Demonitor with flush.** The documented operation stops observation and removes one matching five-element, reference-bearing mailbox tuple if present; its pattern ignores the first element. For actual runtime DOWN, source supports the intended cleanup guarantee. However, the active-monitor fast path skips the receive helper, so unconditional equivalence for a synthetic matching tuple is **not established**; see the source-predicted edge below. This is neither “drain every DOWN” nor cancel the target. [documented equivalence](https://github.com/erlang/otp/blob/ad05823719d77c8faee87348ea39513d4e2f99c5/erts/preloaded/src/erlang.erl#L2074-L2089); [receive helper](https://github.com/erlang/otp/blob/ad05823719d77c8faee87348ea39513d4e2f99c5/erts/preloaded/src/erts_internal.erl#L523-L534).

7. **Demonitor with info.** `true` means the monitor was found and removed, so its runtime DOWN has not been delivered and will not be delivered. `false` means absent; it is not a current liveness query. In a controlled first-call/no-consumer fixture, the test checks that false corresponds to an already-queued DOWN. That fixture does not establish the same implication after an earlier demonitor or receive. [return contract](https://github.com/erlang/otp/blob/ad05823719d77c8faee87348ea39513d4e2f99c5/erts/preloaded/src/erlang.erl#L2092-L2103); [controlled race test](https://github.com/erlang/otp/blob/ad05823719d77c8faee87348ea39513d4e2f99c5/erts/emulator/test/monitor_SUITE.erl#L363-L394).

8. **Double demonitor; info plus flush.** Default demonitor remains `true` when repeated, and also for a fresh local `make_ref()` with no monitor. With `info`, an absent origin produces `false`. Combining `info` and `flush` preserves that false even if no message remains to remove: the C branch selects the result before calling the flush helper. Therefore it does not report a count or prove an actual removal. Foreign/other-owner references have additional validity rules; this is not “every reference is valid.” [no-op tests](https://github.com/erlang/otp/blob/ad05823719d77c8faee87348ea39513d4e2f99c5/erts/emulator/test/monitor_SUITE.erl#L214-L228); [result and option branches](https://github.com/erlang/otp/blob/ad05823719d77c8faee87348ea39513d4e2f99c5/erts/emulator/beam/bif.c#L598-L654); [reference-ownership caveat](https://github.com/erlang/otp/blob/ad05823719d77c8faee87348ea39513d4e2f99c5/erts/preloaded/src/erlang.erl#L2057-L2059).

## Links

9. **Link or unlink self.** Both return `true`; self-link creates no relationship. The test inspects the link list rather than relying only on the return value. [self-link test](https://github.com/erlang/otp/blob/ad05823719d77c8faee87348ea39513d4e2f99c5/erts/emulator/test/erl_link_SUITE.erl#L106-L112); [self branch](https://github.com/erlang/otp/blob/ad05823719d77c8faee87348ea39513d4e2f99c5/erts/emulator/beam/bif.c#L155-L160).

10. **Repeated link.** An existing active link is not duplicated; one relationship remains. Setup is asynchronous, so return does not certify that the peer has processed a link signal or is still alive. Idempotence describes an existing link, not immunity from a concurrent death. [contract](https://github.com/erlang/otp/blob/ad05823719d77c8faee87348ea39513d4e2f99c5/erts/preloaded/src/erlang.erl#L3878-L3881); [existing-link path](https://github.com/erlang/otp/blob/ad05823719d77c8faee87348ea39513d4e2f99c5/erts/emulator/beam/bif.c#L165-L182).

11. **Link dead target, including the setup race.** If the local target is already absent at the cheap existence check and the caller is **not** trapping exits, `link/1` raises a catchable `noproc` error. A trapping caller takes the signal path and can receive EXIT/noproc. A target that disappears after the early check can also produce a later linked exit, rather than the immediate exception. This is a documented historical distinction, not an implementation freedom to collapse the cases. [documented exception](https://github.com/erlang/otp/blob/ad05823719d77c8faee87348ea39513d4e2f99c5/erts/preloaded/src/erlang.erl#L3866-L3876); [early check and signal path](https://github.com/erlang/otp/blob/ad05823719d77c8faee87348ea39513d4e2f99c5/erts/emulator/beam/bif.c#L159-L182); [error construction](https://github.com/erlang/otp/blob/ad05823719d77c8faee87348ea39513d4e2f99c5/erts/emulator/beam/bif.c#L411-L422).

12. **Unlink absent/dead target or race with death.** An absent relationship is a successful no-op. Once unlink returns, that link has no future effect on the caller unless established again. An already-materialized trapped EXIT can remain; unlink does not flush it. A direct exit signal from the same PID is separate and is not suppressed by unlink. The upstream race test accepts an existing queued EXIT, then rejects later link effects. [contract](https://github.com/erlang/otp/blob/ad05823719d77c8faee87348ea39513d4e2f99c5/erts/preloaded/src/erlang.erl#L6852-L6877); [race test](https://github.com/erlang/otp/blob/ad05823719d77c8faee87348ea39513d4e2f99c5/erts/emulator/test/erl_link_SUITE.erl#L431-L449).

13. **Unlink then relink; crossing operations.** The guarantee above expressly excludes re-establishment. Source resets the unlinking marker on relink; an old acknowledgment deletes the record only when its operation ID still matches. The concurrent link/unlink fixture checks eventual agreement of both endpoints, accepting linked or unlinked according to the interleaving. Do not infer that an old in-flight death signal is always suppressed after relink, or impose one global race winner. [relink](https://github.com/erlang/otp/blob/ad05823719d77c8faee87348ea39513d4e2f99c5/erts/emulator/beam/bif.c#L170-L175); [stale-ack guard](https://github.com/erlang/otp/blob/ad05823719d77c8faee87348ea39513d4e2f99c5/erts/emulator/beam/erl_proc_sig_queue.c#L6758-L6771); [concurrent operations](https://github.com/erlang/otp/blob/ad05823719d77c8faee87348ea39513d4e2f99c5/erts/emulator/test/erl_link_SUITE.erl#L501-L518); [consistency oracle](https://github.com/erlang/otp/blob/ad05823719d77c8faee87348ea39513d4e2f99c5/erts/emulator/test/erl_link_SUITE.erl#L979-L989).

## Exit reasons, self-exit, and creation

14. **Normal/abnormal signals and trap changes.** The receiver's trap-exit state is sampled when the signal is **received**, not when sent. For an active linked exit or ordinary direct exit: normal is ignored when untrapped; other abnormal reasons terminate; eligible reasons become EXIT messages when trapped. A deactivated linked signal is discarded first. If trap policy changes concurrently, both timing-dependent outcomes may be allowed; no send-time snapshot should be invented. [complete receive rules](https://github.com/erlang/otp/blob/ad05823719d77c8faee87348ea39513d4e2f99c5/system/doc/reference_manual/ref_man_processes.md#L657-L705); [normal-to-other test](https://github.com/erlang/otp/blob/ad05823719d77c8faee87348ea39513d4e2f99c5/erts/emulator/test/process_SUITE.erl#L321-L340).

15. **Direct kill.** A processed direct exit signal with reason `kill` terminates an otherwise-live target regardless of trapping, and its exit reason becomes `killed`. This is not a catchable `exit/1` exception. Sending the signal is not a completion acknowledgment; a dead target cannot be retroactively killed, and a competing exit may already have won. Runtime checkpoints and all admitted native helpers must enforce this in Bream. [kill rule](https://github.com/erlang/otp/blob/ad05823719d77c8faee87348ea39513d4e2f99c5/erts/preloaded/src/erlang.erl#L2538-L2542); [send versus completion](https://github.com/erlang/otp/blob/ad05823719d77c8faee87348ea39513d4e2f99c5/erts/emulator/beam/bif.c#L1759-L1771); [classification and irreversible transition](https://github.com/erlang/otp/blob/ad05823719d77c8faee87348ea39513d4e2f99c5/erts/emulator/beam/erl_proc_sig_queue.c#L4740-L4782).

16. **A linked reason named kill.** Uncaught `exit(kill)` terminates its caller with `kill`, which links propagate unchanged. A trapping peer receives EXIT/kill; an untrapped peer terminates with kill. Conversely, direct kill first becomes `killed`, and that resulting reason is propagated normally. Match the operation and link status, not just a reason enum named Kill. [explicit distinction](https://github.com/erlang/otp/blob/ad05823719d77c8faee87348ea39513d4e2f99c5/erts/preloaded/src/erlang.erl#L2496-L2504); [receive behavior](https://github.com/erlang/otp/blob/ad05823719d77c8faee87348ea39513d4e2f99c5/system/doc/reference_manual/ref_man_processes.md#L684-L701).

17. **Three self-exit operations differ.** `exit(Reason)` raises a catchable exit-class exception. Legacy `exit(self(), normal)` terminates an untrapped caller; when trapped it produces a mailbox event. `exit(self(), die)` cannot be caught as an exception. OTP 29's `exit_signal(self(), normal)` follows ordinary signal rules and has no effect when untrapped. These known rules should be preserved for operations claiming those semantics. Rust's representation of catchable process exceptions versus untrappable control remains implementation work. [API distinctions](https://github.com/erlang/otp/blob/ad05823719d77c8faee87348ea39513d4e2f99c5/erts/preloaded/src/erlang.erl#L2564-L2586); [self-exit tests](https://github.com/erlang/otp/blob/ad05823719d77c8faee87348ea39513d4e2f99c5/erts/emulator/test/process_SUITE.erl#L344-L390); [legacy-mode dispatch](https://github.com/erlang/otp/blob/ad05823719d77c8faee87348ea39513d4e2f99c5/erts/emulator/beam/bif.c#L1872-L1889).

18. **Child exits immediately after spawn.** Atomic spawn-monitor/link installs the relationship before making the child runnable. A child whose only action is normal completion produces normal DOWN under spawn-monitor, where separate spawn then monitor can produce noproc. Spawn-link applies the normal trap/exit rules; it does not promise application readiness or that the parent survives an abnormal child exit. Combined link+monitor options install both; do not infer that a dying parent will consume both notifications or promise unexamined ordering between different observation mechanisms. [atomic installation](https://github.com/erlang/otp/blob/ad05823719d77c8faee87348ea39513d4e2f99c5/erts/emulator/beam/erl_process.c#L12908-L12945); [first scheduling](https://github.com/erlang/otp/blob/ad05823719d77c8faee87348ea39513d4e2f99c5/erts/emulator/beam/erl_process.c#L13115-L13121); [spawn-monitor tests](https://github.com/erlang/otp/blob/ad05823719d77c8faee87348ea39513d4e2f99c5/erts/emulator/test/monitor_SUITE.erl#L399-L418).

## Corrections, confidence, and remaining work

### Source-predicted synthetic-message edge: execution still required

Keep an ordinary local target alive, create a one-shot monitor, and self-send `{anything, Ref, a, b, c}`. With the origin still active, `demonitor(Ref, [flush])` is predicted to return true **and leave that synthetic tuple available**. The helper initializes `multi=false`, removes the origin, and returns true for a process monitor. The true branch invokes the receive helper only when `multi=true`; it performs no mailbox scan for this case. [origin removal and process return](https://github.com/erlang/otp/blob/ad05823719d77c8faee87348ea39513d4e2f99c5/erts/emulator/beam/bif.c#L436-L523), [conditional helper dispatch](https://github.com/erlang/otp/blob/ad05823719d77c8faee87348ea39513d4e2f99c5/erts/emulator/beam/bif.c#L639-L654).

The documented expansion—plain demonitor followed by a receive matching `{_, Ref, _, _, _}`—would remove it. A subsequent flush after the origin is absent is also predicted to enter that helper and remove it. These statements qualify the broad documentation equivalence; they do not challenge the guarantee against future genuine monitor DOWN after cancellation.

The outstanding exact-version oracle should compare three isolated fixtures: active monitor plus synthetic tuple with `[flush]`; the documented expanded expression on equivalent fresh state; and a second `[flush]` after the first cancellation, without consuming the tuple between calls. Record return values and mailbox contents, keep the target alive throughout, and repeat for `[info, flush]`. No such fixture has been executed here, and no selected upstream test establishes this edge. This is a source-predicted documentation qualification, **not a definitive upstream bug claim**.

Bream's mapping to a typed inbox envelope remains unresolved. Do not infer that applications can or cannot construct lifecycle look-alikes, or choose a different flushing rule without establishing the precise supported representation and reference behavior.

### Audit limits

[Report 13](13-beam-lifecycle-source.md)'s blanket absent-peer-to-linked-noproc description needed correction for case 11's immediate error. Its exit matrix remains valid only with its stated ordinary-other-process scope; cases 14 and 17 make the timing and self-call exceptions explicit. Its monitor state labels describe an implementation model, not four independent public states that applications can query.

The selected `demonitor_flush_test` contains a weak negative assertion: its guard requires the same reference equal both distinct M1 and M3, so that branch cannot establish their absence. Its positive M4 assertion is still informative. We rely on the docs, C/receive implementation, and separate late-DOWN regression for the cancellation guarantee, not that guard. [test evidence limitation](https://github.com/erlang/otp/blob/ad05823719d77c8faee87348ea39513d4e2f99c5/erts/emulator/test/monitor_SUITE.erl#L287-L305).

This is **bounded source-supported coverage**, not exhaustive conformance. No test here demonstrates Bream yet. Outstanding work includes executable differential fixtures for these cases; invalid-argument and wrong-owner rules; combined link/monitor ordering; simultaneous death and multiple exit reasons; named registration races; spawn failure/resource exhaustion; aliases/priorities/distribution; and full interleaving and memory-lifetime checks. Bream's stop-before-DOWN requirement also remains stricter than BEAM's dirty-native exception: admitted native application work must actually stop, while tracked runtime cleanup may finish later. Neither Rust cleanup safety nor bounded kill/reclamation latency follows from these lifecycle rules.
