# Process heap roots and the Rust ownership opportunity

Status: source audit and proposed experiments, 2026-10-07. OTP reference: **29.1.1**, commit `ad05823719d77c8faee87348ea39513d4e2f99c5`, checked against the local checkout. No VM tests, Rust implementation or benchmarks were run for this report. It extends [report 18](/home/bat/projects/bream/docs/research/18-process-execution-memory-deep-dive.md) and [report 34](/home/bat/projects/bream/docs/research/34-message-allocation-and-copy-costs.md); their policy and message-copy findings remain the background, rather than new cases here.

The promising Rust advantage is to **avoid needing a general moving term collector for admitted typed state**. That could remove root enumeration, repeated graph copying and pointer repair. It does not follow that arbitrary Rust state is cheaply reclaimable, or that copying BEAM's collector into Rust would yield the same advantage. The following source obligations identify what a replacement representation must preserve.

## 1. Root discovery is a protocol with callers

`setup_rootset` includes the Erlang stack, dictionary, explicitly supplied live terms, tracing metadata, group leader, parent, failure value/trace, receive-marker references and saved native-function arguments. The native wrapper contributes `argv` only while its saved argument count is positive. Ordinary C locals are not conservatively discovered. Callers must expose surviving values in one of these representations. [Stack/dictionary/caller roots](https://github.com/erlang/otp/blob/ad05823719d77c8faee87348ea39513d4e2f99c5/erts/emulator/beam/erl_gc.c#L2630-L2643), [metadata/marker/native roots](https://github.com/erlang/otp/blob/ad05823719d77c8faee87348ea39513d4e2f99c5/erts/emulator/beam/erl_gc.c#L2661-L2705), [native wrapper](https://github.com/erlang/otp/blob/ad05823719d77c8faee87348ea39513d4e2f99c5/erts/emulator/beam/erl_nfunc_sched.h#L97-L114).

The BIF return path makes this contract concrete:

| Boundary | Values explicitly retained | Consequence |
|---|---|---|
| Successful BIF | A one-element array containing the result | GC rewrites the result; original argument registers are not automatically retained by this call. |
| Trapping BIF | Registers through the process's current `arity` | Resumption arguments determine liveness. |
| BIF exception | Registers through the incoming call's `arity` | Failure and argument handling differ from trap resumption. |
| GC disabled, first trap | Save the live-fragment boundary if none is already saved | Later traps must not replace that first boundary. |
| Successful result, collection changes process to EXITING | Return `THE_NON_VALUE` | Do not resume with an apparently successful result after that transition. |

These are exact branches in [`erts_gc_after_bif_call_lhf`](https://github.com/erlang/otp/blob/ad05823719d77c8faee87348ea39513d4e2f99c5/erts/emulator/beam/erl_gc.c#L418-L475). A generated Rust continuation can encode live fields and initialization states directly, but its success/error/suspension edges must remain equally explicit; an arbitrary native stack cannot simply be treated as that continuation.

Mailbox roots are representation-dependent. Only fully settled off-heap mode excludes the queues. Inner/middle internal messages without attached fragments expose their reference arrays; heap-allocated alias signals expose only slots starting at `m[2]`, because earlier slots are not yet valid terms. Root-array sizing can itself allocate. These are reasons to distinguish initialized payload ownership from “everything in a queue node.” [Mode predicate](https://github.com/erlang/otp/blob/ad05823719d77c8faee87348ea39513d4e2f99c5/erts/emulator/beam/erl_gc.c#L2709-L2716), [allocation and queue branches](https://github.com/erlang/otp/blob/ad05823719d77c8faee87348ea39513d4e2f99c5/erts/emulator/beam/erl_gc.c#L2740-L2775). This refines existing MEM-01.C01/C09, without allocating another case for their root list.

## 2. Minor collection relies on immutability, not an ordinary remembered set

Minor collection distinguishes the mature part below the high-water mark, the remaining young data, the pre-existing old heap and literals. Already-forwarded objects reuse their destination. Mature objects move to old storage, other nonliteral/non-old objects move to the new young heap, and old/literal references remain in place. `ErtsInYoungGen` is an exclusion test for literals and the old heap; it is not restricted to one contiguous young allocation. [Root movement](https://github.com/erlang/otp/blob/ad05823719d77c8faee87348ea39513d4e2f99c5/erts/emulator/beam/erl_gc.c#L1682-L1715), [generation predicate](https://github.com/erlang/otp/blob/ad05823719d77c8faee87348ea39513d4e2f99c5/erts/emulator/beam/erl_gc.h#L97-L99).

The important closure step scans **newly appended old objects**, rather than rescanning the entire old heap. Their descendants still pointing into evacuated young storage must be moved too. The high-water mark is then advanced, and HARDDEBUG checks reject forbidden old-heap references into evacuated young data/fragments. [Promotion closure and checks](https://github.com/erlang/otp/blob/ad05823719d77c8faee87348ea39513d4e2f99c5/erts/emulator/beam/erl_gc.c#L1802-L1822). The pinned internal documentation explicitly grounds the absence of old-to-young references in immutable Erlang terms. Its historical code links are not used as current implementation evidence here. [Immutability invariant](https://github.com/erlang/otp/blob/ad05823719d77c8faee87348ea39513d4e2f99c5/erts/emulator/internal_doc/GarbageCollection.md#L98-L110).

This is a substantial restriction on copying the design into mutable Rust graphs. Updating a long-lived object to reference newly allocated state can violate the invariant. A generational graph design would need mutation restrictions, a write barrier/remembered set, or a different traversal policy. Unique ownership with ordinary field replacement can instead avoid tracing that graph altogether. That is an architectural inference, not a demonstrated speedup.

Full collection follows all rooted nonliteral terms into a common destination, sweeps the copied graph and off-heap ownership, and frees the former old heap. Unreachable old ordinary terms that survived minor collections can then disappear. Forwarding preserves existing internal sharing during collection; this does not create a public Erlang pointer-identity guarantee. [Full root movement](https://github.com/erlang/otp/blob/ad05823719d77c8faee87348ea39513d4e2f99c5/erts/emulator/beam/erl_gc.c#L2005-L2028), [closure/release](https://github.com/erlang/otp/blob/ad05823719d77c8faee87348ea39513d4e2f99c5/erts/emulator/beam/erl_gc.c#L2036-L2055).

## 3. Not every collection immediately removes all garbage

Both collectors can move a known-live fragment prefix wholesale before tracing roots. `collect_live_heap_frags` walks `mbuf` until the saved boundary, using each fragment's `used_size`. The source explicitly permits garbage inside that prefix to survive this collection. Fragment off-heap lists must already be empty because the process owns those references through its MSO list. [Prefix copying](https://github.com/erlang/otp/blob/ad05823719d77c8faee87348ea39513d4e2f99c5/erts/emulator/beam/erl_gc.c#L2488-L2510), [minor entry](https://github.com/erlang/otp/blob/ad05823719d77c8faee87348ea39513d4e2f99c5/erts/emulator/beam/erl_gc.c#L1669-L1675).

The boundary cannot survive arbitrary state changes: the BIF wrapper invalidates it when fragments are already gone, while the main collector invalidates it for an abandoned heap and otherwise prefers the saved process boundary. After successful collection it resets the saved boundary. [BIF invalidation](https://github.com/erlang/otp/blob/ad05823719d77c8faee87348ea39513d4e2f99c5/erts/emulator/beam/erl_gc.c#L423-L445), [collector selection](https://github.com/erlang/otp/blob/ad05823719d77c8faee87348ea39513d4e2f99c5/erts/emulator/beam/erl_gc.c#L795-L798), [reset](https://github.com/erlang/otp/blob/ad05823719d77c8faee87348ea39513d4e2f99c5/erts/emulator/beam/erl_gc.c#L934-L935).

Storage release follows relocation: young-generation teardown joins a temporary abandoned-heap fragment into `mbuf`, releases fragments/adopted messages, clears accounting and frees the original heap. Queue-node removal, graph evacuation and allocation release are separate transitions. [Teardown](https://github.com/erlang/otp/blob/ad05823719d77c8faee87348ea39513d4e2f99c5/erts/emulator/beam/erl_gc.c#L2116-L2147). A Rust arena can similarly amortize allocation, but bulk retention has to appear in memory measurements; “owned” is not synonymous with “promptly reclaimed.”

## 4. Relocation has more than one kind of pointer

| Representation/transition | Pinned implementation obligation | Rust implication |
|---|---|---|
| Shrinking combined heap/stack | Move stack before realloc removes its former upper region. | A moving allocation needs a layout-aware protocol. |
| Growing combined heap/stack | Move stack after realloc into its new end position. | Heap and stack displacement are distinct. |
| Realloc returns the same heap address | Still offset stack/frame references because the stack moved. | A same-base allocation result does not prove all addresses are unchanged. |
| Realloc moves heap address | Offset heap contents and external roots, including markers, off-heap links and saved native arguments. | Every hidden owning/reference field matters. |
| `ErlSubBits.orig` moves | Update its owner reference; repair cached byte base for on-heap match contexts. | Owner-plus-offset handles can avoid storing a relocatable interior pointer. |

Sources: [stack ordering](https://github.com/erlang/otp/blob/ad05823719d77c8faee87348ea39513d4e2f99c5/erts/emulator/beam/erl_gc.c#L2808-L2838), [same/moved base](https://github.com/erlang/otp/blob/ad05823719d77c8faee87348ea39513d4e2f99c5/erts/emulator/beam/erl_gc.c#L2840-L2870), [external roots](https://github.com/erlang/otp/blob/ad05823719d77c8faee87348ea39513d4e2f99c5/erts/emulator/beam/erl_gc.c#L3507-L3535), [sub-bits branch](https://github.com/erlang/otp/blob/ad05823719d77c8faee87348ea39513d4e2f99c5/erts/emulator/beam/erl_gc.c#L1773-L1788).

The last row needs a precise qualification: `erl_sub_bits_update_moved` changes the base only when `orig` is `HEAP_BITS`; only match contexts may use that representation. Ordinary `ErlSubBits` must reference a `BinRef`. Moving a BinRef descriptor is not automatically moving its separately allocated bytes. [Cached-base helper](https://github.com/erlang/otp/blob/ad05823719d77c8faee87348ea39513d4e2f99c5/erts/emulator/beam/erl_bits.h#L522-L538). This is additional to report 34's freeze/realloc path.

## 5. Off-heap ownership has exceptions to minor-GC skipping

The writable-binary list is traversed in full even during a minor collection: its descriptors may be on the old heap. Forwarded descriptors are relinked and charged to the proper virtual heap; unforwarded non-old descriptors release their backing, while old descriptors survive. A descriptor whose backing has been frozen moves from the writable list into the regular off-heap list, with different insertion points for old versus young ownership. [Traversal/accounting](https://github.com/erlang/otp/blob/ad05823719d77c8faee87348ea39513d4e2f99c5/erts/emulator/beam/erl_gc.c#L3146-L3192), [list migration](https://github.com/erlang/otp/blob/ad05823719d77c8faee87348ea39513d4e2f99c5/erts/emulator/beam/erl_gc.c#L3243-L3256).

Shrinking also depends on the population: active writers change how much capacity inactive binaries retain, requiring deferred candidates and potentially a second traversal. [Writer/candidate classification](https://github.com/erlang/otp/blob/ad05823719d77c8faee87348ea39513d4e2f99c5/erts/emulator/beam/erl_gc.c#L3194-L3238), [second traversal](https://github.com/erlang/otp/blob/ad05823719d77c8faee87348ea39513d4e2f99c5/erts/emulator/beam/erl_gc.c#L3260-L3279). Rust's explicit mutable-builder→immutable-buffer transition could eliminate this particular cross-list discovery, if the runtime records the transition immediately and retains an auditable ownership ledger. It still needs to decide retained capacity, sharing and final-release policy.

## 6. Collection boundaries are not cancellation checkpoints

Minor collection allocates destination and root storage **before** installing forwarding markers; full collection has the same ordering. The comment promises an intact heap for allocation-failure crash dumps, not recoverable allocation failure. After destructive forwarding begins, treating an arbitrary instruction as a resumable safe point would require additional machinery. [Minor boundary](https://github.com/erlang/otp/blob/ad05823719d77c8faee87348ea39513d4e2f99c5/erts/emulator/beam/erl_gc.c#L1658-L1667), [full boundary](https://github.com/erlang/otp/blob/ad05823719d77c8faee87348ea39513d4e2f99c5/erts/emulator/beam/erl_gc.c#L1979-L1984).

The ordinary collector delays before starting for disabled/delayed GC or an EXITING process, and dispatches potentially long work to dirty execution before relocation. A minor failure can also reclassify the forthcoming full sweep. Size estimates include stack and, conditionally, private queue length; moving work to a dirty scheduler does not make it incremental. [Entry/defer](https://github.com/erlang/otp/blob/ad05823719d77c8faee87348ea39513d4e2f99c5/erts/emulator/beam/erl_gc.c#L780-L798), [size/dispatch](https://github.com/erlang/otp/blob/ad05823719d77c8faee87348ea39513d4e2f99c5/erts/emulator/beam/erl_gc.c#L694-L715), [reclassification](https://github.com/erlang/otp/blob/ad05823719d77c8faee87348ea39513d4e2f99c5/erts/emulator/beam/erl_gc.c#L839-L849). This does not establish a wall-clock kill bound, nor say every collector entry refuses terminating state; the root builder explicitly preserves an exit reason.

## 7. What Rust can remove, and what it cannot promise

These are **design hypotheses**, not selected implementation details:

- Typed continuation fields can replace tagged-term root enumeration and generic pointer scanning. Ownership moves can replace evacuation for uniquely owned state. This benefit comes from the representation and admission contract; C/C++ could implement a specialized representation too. Rust adds compiler-checked ownership and initialization constraints at safe interfaces.
- Ordinary Rust destruction handles initialized fields and recursively destroys their contents. That gives generated code a useful baseline, but neither recursive destruction cost nor user `Drop` execution becomes bounded. The admitted runtime needs qualified cleanup operations and explicit state for interrupted construction or transfer. [Rust destructor rules](https://doc.rust-lang.org/reference/destructors.html).
- Safe Rust permits leaks: `mem::forget` can suppress destruction, and reference-count cycles can remain allocated. `Weak` breaks ownership cycles but can keep the backing allocation alive after the value dies. A process resource ledger or arena can help only when all admitted allocations/resources participate; it cannot discover arbitrary hidden standard-library ownership after the fact. [Forget contract](https://doc.rust-lang.org/std/mem/fn.forget.html#safety), [Arc cycle/backing lifetime](https://doc.rust-lang.org/std/sync/struct.Arc.html#breaking-cycles-with-weak).
- An arena with index-based cyclic edges can reclaim its private storage without tracing each edge at process death, provided external ownership obligations are separately known. It still needs a live-process reclamation policy, stale-handle protection and budgeted external-resource release. This is not equivalent to admitting arbitrary `Rc`/`Arc` cycles.
- Borrow rules prevent many ordinary dangling/aliasing mistakes; they do not authorize an unsafe runtime to invalidate a live reference. The current Reference also explicitly excludes deallocating native Rust frames while skipping their owned-local destructors. Thus safe `forget` is not permission to abandon arbitrary native frames. [Reference validity/runtime assumptions](https://doc.rust-lang.org/reference/behavior-considered-undefined.html#undefined.runtime).
- `Pin` has a storage-validity requirement until the pinned value's destruction; merely promising not to resume the process does not discharge it. Arbitrary pinned or self-referential fields therefore need a sound admitted destruction boundary. Leaking pinned storage is different from reclaiming it. [Pin's drop guarantee](https://doc.rust-lang.org/std/pin/#subtle-details-and-the-drop-guarantee).
- `MaybeUninit` supplies neither initialized-field tracking nor automatic inner cleanup. Generated partial-state representations require their own initialization mask/state and ownership transfers; reading an unfinished field is not a shortcut to avoiding roots. [MaybeUninit contract](https://doc.rust-lang.org/std/mem/union.MaybeUninit.html).

Rust sources were checked on 2026-10-07; the rendered standard-library docs identify Rust 1.99.0. They are canonical documentation URLs rather than immutable OTP-style source snapshots. The generated process model must prove the composition of these rules; this report supplies no soundness proof.

## 8. Five falsifiable experiments

All are proposed. Use identical value-level work, generated switching/kill checks and ownership accounting in both arms. Measure throughput, p50/p99/max uninterrupted runtime work, peak/resident/retained bytes, allocation counts and kill-to-reclamation latency separately. Preserve cold-start results and code size; do not report a single throughput number as a universal win.

| Experiment | Baseline → treatment and workload | Acceptance/rejection condition |
|---|---|---|
| ROOT-38.T01 — Typed live state | Small tagged traced-state prototype → generated typed fields; persistent session state plus short-lived temporaries, varying live/allocated ratio. | Fewer scanned/copied bytes and useful latency or throughput gains after including generated metadata/code size. Reject if cleanup stalls or incomplete ownership merely hide work. |
| ROOT-38.T02 — Short-lived allocations | Individually owned qualified nodes → process-private region/index storage; bursts, long idle gaps and cycles confined to the region. | Allocation gains must survive retained-memory and death-drain measurements. Include stale handles, external immutable buffers and kill at construction boundaries; unreachable live-process garbage cannot silently accumulate without accounting. |
| ROOT-38.T03 — Relocatable continuations | Stable boxed storage → movable generated state with owner-plus-offset views; deep continuations and small binary-match state. | Move/grow/shrink correctness with no escaped references or pinned fields, then compare indirection, copying, footprint and cache misses. Force same-base/moved-base allocator outcomes in the eventual test harness rather than assume either from observed addresses. |
| ROOT-38.T04 — Exact liveness versus retained batches | Exact initialized-owner ledger with fine-grained reclamation → the same exact ledger with coarser region/batch retention; helpers with repeated suspend, successful return and error. | Lower bookkeeping cost must exceed the cost of retained dead temporaries. Every observable result survives; kill discharges all ownership; memory use reports the retained prefix honestly. |
| ROOT-38.T05 — Explicit buffer state | Discover writable/frozen descriptor state during periodic cleanup → record builder→frozen transitions immediately; vary active writers, spare capacity and fanout. | Preserve published bytes and final-owner release while reducing measured traversal or pause cost. Reject if transition overhead, atomic ownership or capacity retention outweighs saved scans. |

These isolate Rust representation opportunities; none presupposes reimplementing BEAM's heap or promising a general-purpose tracing collector in Bream.

## 9. Six proposed branch refinements

The current catalogue ended at MEM-01.C16 when inspected. The following IDs were reserved with the parent; this report does not edit the catalogue. All are planned/unexecuted. Representation-specific reference assertions guide a Bream oracle rather than requiring identical GC internals.

| Case | Trigger and reference outcome | Bream acceptance obligation |
|---|---|---|
| MEM-01.C17 | Post-BIF success, trap and exception use different explicit live arrays; successful return can become nonvalue on EXITING (§1). | Exercise generated success/error/suspend transitions with independently dying arguments and live results; no lost result, stale register read, or resumption after terminal transition. |
| MEM-01.C18 | Known-live fragment prefix contains dead temporaries; first disabled-GC trap saves the marker, later traps preserve it; prior GC/abandoned heap invalidates it (§3). | Preserve the selected retention boundary across repeated helpers; never walk a freed marker or promise immediate garbage removal. Account retained bytes and reclaim all admitted allocations on death. |
| MEM-01.C19 | Duplicate roots and mature descendants cross a minor collection, followed by dropping old roots and a full sweep (§2). | Preserve values and required ownership sharing through promotion closure; no surviving old reference into evacuated young storage. A mutable Rust graph must use an explicitly correct policy rather than assume BEAM's immutable invariant. |
| MEM-01.C20 | Heap/stack grow or shrink, with same-base and moved-base realloc outcomes (§4). | Preserve continuation and every external owner/reference; test independent stack displacement. A Rust representation may avoid relocation, but may not byte-move borrowed or pinned state without satisfying its contract. |
| MEM-01.C21 | A binary match context retains on-heap bytes through owner relocation; compare BinRef-backed views (§4). | Preserve owner, bit offset/length and subsequent reads. Repair or avoid cached interior pointers; distinguish descriptor movement from backing-byte movement. |
| MEM-01.C22 | Writable BinRef is old-generation, young-forwarded or dead-young; frozen backing moves to the regular list, with active/inactive shrink candidates (§5). | Each backing remains in exactly one applicable ownership structure, accounting matches its state, and final release occurs once. Preserve all published bytes and measure spare capacity rather than treating shrink as mandatory semantics. |

Selected upstream tests were read, not executed: minor/major self and async paths assert expected GC trace kinds and completion ([tests](https://github.com/erlang/otp/blob/ad05823719d77c8faee87348ea39513d4e2f99c5/erts/emulator/test/gc_SUITE.erl#L237-L288)); alias-signal roots exercise GC without interpreting unfinished message slots as terms ([test](https://github.com/erlang/otp/blob/ad05823719d77c8faee87348ea39513d4e2f99c5/erts/emulator/test/gc_SUITE.erl#L376-L394)). Neither demonstrates all six new branches. Deterministic branch instrumentation is still needed for fragment boundaries, relocation outcomes and writer-list combinations.

Remaining gaps: literal-area/code-purge collection, every map/fun scanner shape, all native-wrapper transitions, architecture-specific frame layouts, allocator failure interleavings and the complete resource-destructor graph. This audit cannot establish exhaustive collector safety, a Rust admission contract, or any measured performance advantage.

The proposed cases are integrated in the [build plan](../build-plan.md); the report-local experiments feed the stable [performance task backlog](../performance-plan.md). The [Rust opportunity map](../rust-opportunities.md) compares these mechanisms without selecting a production representation.
