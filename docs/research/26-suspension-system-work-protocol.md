# Suspension ownership, acknowledgment and system work

**Execution follow-up:** [Report 29](29-pinned-reference-observations.md) now records targeted observations on the exact pinned build. The source-only status and hypotheses below describe the original review stage; the follow-up identifies which variants were executed and which remain unresolved.

Reviewed 2026-10-07 against official Erlang/OTP tag `OTP-29.1.1`, commit `ad05823719d77c8faee87348ea39513d4e2f99c5`. Every upstream source link pins that revision. This pass reads source and test assertions only: no VM or test was executed and no upstream source was changed. It closes the explicit-suspension consumer gap recorded in [report 18](18-process-execution-memory-deep-dive.md), rather than auditing every system-work producer.

The central result is that suspension has three distinct pieces: an owned request count, activation on the target, and an acknowledgment of target state. Dirty execution can separate them substantially. This protocol prevents premature activation and stale-pointer use; it does not interrupt arbitrary native instructions. A source-level discrepancy also exists between two dead-target acknowledgment paths and requires reference execution before choosing compatibility behavior.

## 1. Two counts and a retained relationship

`ErtsMonitorSuspend` contains the origin/target monitor pair, a pending-list pointer, and an atomic word combining an `ACTIVE` flag with the requester's repeat count. The origin is keyed by the target PID; the target identifies the requester. This is an internal suspension relationship, not an application monitor returning a normal `DOWN` tuple. [Representation](https://github.com/erlang/otp/blob/ad05823719d77c8faee87348ea39513d4e2f99c5/erts/emulator/beam/erl_monitor_link.h#L277-L305), [fields](https://github.com/erlang/otp/blob/ad05823719d77c8faee87348ea39513d4e2f99c5/erts/emulator/beam/erl_monitor_link.h#L758-L764).

Repeated calls by the same requester increment that relationship's count without creating another target monitor. `unless_suspending` reuses the relationship without incrementing it; a synchronous call may still wait if its existing relationship is not active. Counter overflow rolls back the increment before returning `system_limit`. Separately, target `rcount` increments when a relationship activates; repeated requests within that already-active relationship do not each increment `rcount`. Other internal suspension mechanisms also use `rcount`, so it is not exclusively a count of public suspend monitors. [Request accounting](https://github.com/erlang/otp/blob/ad05823719d77c8faee87348ea39513d4e2f99c5/erts/emulator/beam/erl_process.c#L9064-L9115), [target accounting](https://github.com/erlang/otp/blob/ad05823719d77c8faee87348ea39513d4e2f99c5/erts/emulator/beam/erl_process.c#L7235-L7325), [busy-port sharing](https://github.com/erlang/otp/blob/ad05823719d77c8faee87348ea39513d4e2f99c5/erts/emulator/beam/erl_process.c#L9369-L9399).

For Bream, the transferable invariant is ownership: releasing one requester's claims must not release another requester's claims. The exact atomic packing and public debugging API are not prerequisites for automatic scheduling.

## 2. Immediate and queued activation

The first relationship tries to acquire target `MAIN|STATUS|BTM` locks while excluding exiting and normal/dirty running states. Successful immediate suspension updates scheduling state, pauses timers, inserts the target monitor and marks it active before unlocking. A busy target instead receives a `MONITOR` signal. The consumer inserts the target record, then either activates it or records pending activation. [Producer](https://github.com/erlang/otp/blob/ad05823719d77c8faee87348ea39513d4e2f99c5/erts/emulator/beam/erl_process.c#L9118-L9159), [consumer](https://github.com/erlang/otp/blob/ad05823719d77c8faee87348ea39513d4e2f99c5/erts/emulator/beam/erl_proc_sig_queue.c#L6544-L6561), [local consumer](/home/bat/projects/bream/upstream/otp/erts/emulator/beam/erl_proc_sig_queue.c:6544).

The queued activation helper pauses receive and BIF timers, atomically marks the relationship active, then calls `erts_suspend`; ordinary signal handling also sets its yield indicator. This differs in textual order from the locked immediate path. It is not evidence that application code can run between timer and scheduling updates: the consumer holds `MAIN`, and `erts_suspend` additionally obtains `STATUS`. Pending-suspend storage likewise requires `MAIN` for get and set. [Activation](https://github.com/erlang/otp/blob/ad05823719d77c8faee87348ea39513d4e2f99c5/erts/emulator/beam/erl_proc_sig_queue.c#L5432-L5455), [locking](https://github.com/erlang/otp/blob/ad05823719d77c8faee87348ea39513d4e2f99c5/erts/emulator/beam/erl_process.c#L9369-L9394), [pending-storage lock contract](https://github.com/erlang/otp/blob/ad05823719d77c8faee87348ea39513d4e2f99c5/erts/emulator/beam/erl_process.h#L943-L950).

## 3. Dirty execution: accepting control is not completing suspension

When the consumer sees `DIRTY_RUNNING`, it does **not** activate the suspension. It stores the monitor on a pending list and increments the monitor allocation's reference count. Subsequent acknowledgment requests are also retained. At the dirty scheduler's scheduling boundary, before its next `erts_schedule`, `erts_proc_sig_handle_pending_suspend` drains this state. [Deferral](https://github.com/erlang/otp/blob/ad05823719d77c8faee87348ea39513d4e2f99c5/erts/emulator/beam/erl_proc_sig_queue.c#L5456-L5476), [acknowledgment deferral](https://github.com/erlang/otp/blob/ad05823719d77c8faee87348ea39513d4e2f99c5/erts/emulator/beam/erl_proc_sig_queue.c#L5537-L5547), [dirty boundary](https://github.com/erlang/otp/blob/ad05823719d77c8faee87348ea39513d4e2f99c5/erts/emulator/beam/beam_common.c#L150-L179).

The drain activates a retained monitor only if the target is not exiting **and** its target record is still installed. Every retained monitor reference is released regardless. It then rereads target state, answers pending acknowledgments, frees the pending structure and clears its pointer. Thus a resume/requester-death demonitor processed before native return cancels pending activation without freeing storage still referenced by the pending list. An exiting target skips activation. [Drain and lifetime conditions](https://github.com/erlang/otp/blob/ad05823719d77c8faee87348ea39513d4e2f99c5/erts/emulator/beam/erl_proc_sig_queue.c#L5649-L5686), [local drain](/home/bat/projects/bream/upstream/otp/erts/emulator/beam/erl_proc_sig_queue.c:5649).

How can signals be consumed during native execution? Only designated dirty-signal-handler processes may call the relevant internal BIF. It tries target `MAIN`, rechecks liveness/dirty state, avoids concurrent signal handling and charges consumed reductions to the handler. Lock contention can return `more`; the Erlang handler requeues the target after five repeated `more` results to serve other requests. Neither mechanism stops the native call. [Handler BIF](https://github.com/erlang/otp/blob/ad05823719d77c8faee87348ea39513d4e2f99c5/erts/emulator/beam/erl_proc_sig_queue.c#L8892-L8962), [handler loop](https://github.com/erlang/otp/blob/ad05823719d77c8faee87348ea39513d4e2f99c5/erts/preloaded/src/erts_dirty_process_signal_handler.erl#L83-L89).

`DIRTY_RUNNING_SYS` is different: current dirty system tasks hold `MAIN`, and dirty-handler eligibility explicitly excludes that state. The source leaves signals for the process to detect when this work ends. Therefore neither “suspended” nor “has a control queue” proves bounded control-response latency. [Eligibility](https://github.com/erlang/otp/blob/ad05823719d77c8faee87348ea39513d4e2f99c5/erts/emulator/beam/erl_process.h#L1355-L1382), [system-work explanation](https://github.com/erlang/otp/blob/ad05823719d77c8faee87348ea39513d4e2f99c5/erts/emulator/beam/erl_process.c#L11102-L11125).

Bream's accepted stop-before-`Down` requirement remains stronger than BEAM's dirty-native exception. This trace supplies ownership and deferred-completion patterns, not a Rust-safe way to admit an uninterruptible function or destroy its live resources.

## 4. What acknowledgments actually certify

For a synchronous request needing confirmation, the producer creates a reference, saves the caller's receive position and sends `SYNC_SUSPEND`; the public wrapper waits for `{Ref, Result}`. A tagged asynchronous request uses the supplied tag and returns its request result immediately. Prepared reply payload is the synchronous boolean or asynchronous `suspended`. The consumer patches it according to target state and sends an ordinary mailbox message; if the requester no longer exists, it frees that message. [Producer and wrapper](https://github.com/erlang/otp/blob/ad05823719d77c8faee87348ea39513d4e2f99c5/erts/emulator/beam/erl_process.c#L9163-L9173), [wrapper](https://github.com/erlang/otp/blob/ad05823719d77c8faee87348ea39513d4e2f99c5/erts/preloaded/src/erlang.erl#L6363-L6400), [reply construction](https://github.com/erlang/otp/blob/ad05823719d77c8faee87348ea39513d4e2f99c5/erts/emulator/beam/erl_proc_sig_queue.c#L3192-L3233), [consumer](https://github.com/erlang/otp/blob/ad05823719d77c8faee87348ea39513d4e2f99c5/erts/emulator/beam/erl_proc_sig_queue.c#L5480-L5533).

| State at consumer reply | Tagged asynchronous payload | Synchronous internal result |
|---|---|---|
| Suspended and not exiting | `suspended` | Prepared `true`/`false` |
| Exiting, even if also suspended | `exited` | `badarg` |
| Neither suspended nor exiting | `not_suspended` | `internal_error` |
| Requester missing | Message reclaimed | Message reclaimed |

This is a state observation when the reply is constructed, not a permanent lease or evidence that the requester consumed it. It tests target state rather than the continued ownership of one particular relationship. Pending acknowledgments are prepended and drained forward: multiple delayed tags are not implemented as a FIFO completion list. No execution here establishes a universal public reply-order guarantee. [Pending lists](https://github.com/erlang/otp/blob/ad05823719d77c8faee87348ea39513d4e2f99c5/erts/emulator/beam/erl_proc_sig_queue.c#L5537-L5547), [drain order](https://github.com/erlang/otp/blob/ad05823719d77c8faee87348ea39513d4e2f99c5/erts/emulator/beam/erl_proc_sig_queue.c#L5673-L5686).

### Dead-target discrepancy requiring an oracle

The send-helper's enqueue-failure branch chooses **asynchronous `badarg`, synchronous `exited`**, the reverse of the consumer's exiting branch. Its `async_suspend` value is explicitly derived from absence of a synchronous result. The consumer comment also incorrectly describes its prepared default as always `false`; actual construction uses the values above. [Send fallback](https://github.com/erlang/otp/blob/ad05823719d77c8faee87348ea39513d4e2f99c5/erts/emulator/beam/erl_proc_sig_queue.c#L3214-L3242), [consumer branch](https://github.com/erlang/otp/blob/ad05823719d77c8faee87348ea39513d4e2f99c5/erts/emulator/beam/erl_proc_sig_queue.c#L5482-L5527).

Do not conflate this with ordinary early rejection. An already-dead target in a normal synchronous call is rejected by the BIF before creating an acknowledgment request. For tagged asynchronous calls the same `noproc` branch retains the `true` return and tag, reaching the send helper. A synchronous helper failure instead needs a later disappearance race. The public documentation lists three tagged states and also generally lists dead-target `badarg`; it does not explain the helper's fourth tagged state. [BIF distinction](https://github.com/erlang/otp/blob/ad05823719d77c8faee87348ea39513d4e2f99c5/erts/emulator/beam/erl_process.c#L9148-L9173), [documented states/failures](https://github.com/erlang/otp/blob/ad05823719d77c8faee87348ea39513d4e2f99c5/erts/preloaded/src/erlang.erl#L6304-L6355).

Minimal **unexecuted here** public-API fixture for the deterministic branch:

```erlang
{P,M} = spawn_monitor(fun() -> ok end),
receive {'DOWN',M,process,P,_} -> ok end,
Tag = make_ref(),
Call = catch erlang:suspend_process(P, [{asynchronous,Tag}]),
Reply = receive {Tag,R} -> R after 1000 -> timeout end,
Sync = catch erlang:suspend_process(P),
{Call,Reply,Sync}.
```

Source prediction: `true`, tagged `badarg`, and synchronous `badarg` exception. The timeout is a harness watchdog, not a semantic deadline. Until reference execution and reconciliation, this must remain a reference discrepancy, not silently become Bream's contract.

## 5. Resume, requester death and target death

`resume_process` decrements only the caller's relationship count. Its last resume removes the origin and sends `DEMONITOR`. The target removes its half, atomically clears `ACTIVE`, and only if previously active decrements target suspension state and resumes paused timers. A never-activated pending relationship therefore cannot decrement a target/timer count it never acquired. If the target half is already absent, the consumer only releases the incoming origin. [Resume producer](https://github.com/erlang/otp/blob/ad05823719d77c8faee87348ea39513d4e2f99c5/erts/emulator/beam/erl_process.c#L9181-L9212), [consumer branches](https://github.com/erlang/otp/blob/ad05823719d77c8faee87348ea39513d4e2f99c5/erts/emulator/beam/erl_proc_sig_queue.c#L6589-L6627).

Requester exit sends this same demonitor once per relationship, releasing its ownership regardless of its repeat count. Target exit sends an internal suspension `MONITOR_DOWN`; its live consumer removes the origin and releases the pair without converting it to an application `DOWN`. If that origin already disappeared, it releases only the arriving target half. Exit dispatch separately releases incoming monitor-down/demonitor records, handles incoming monitors through exit cleanup, and still processes `SYNC_SUSPEND`. [Exit relationship actions](https://github.com/erlang/otp/blob/ad05823719d77c8faee87348ea39513d4e2f99c5/erts/emulator/beam/erl_process.c#L13806-L13815), [requester exit](https://github.com/erlang/otp/blob/ad05823719d77c8faee87348ea39513d4e2f99c5/erts/emulator/beam/erl_process.c#L13891-L13898), [internal down cleanup](https://github.com/erlang/otp/blob/ad05823719d77c8faee87348ea39513d4e2f99c5/erts/emulator/beam/erl_proc_sig_queue.c#L6440-L6509), [exit dispatcher](https://github.com/erlang/otp/blob/ad05823719d77c8faee87348ea39513d4e2f99c5/erts/emulator/beam/erl_proc_sig_queue.c#L7309-L7410).

Timer pause ownership follows activation, not every repeated request. Existing paused receive timers increment their pause count; the BIF-timer collection has its own count even when empty. Only the last relevant decrement reconstructs running timers. Resume clears scheduling suspension before restoring timers while the signal consumer still owns `MAIN`. The BIF-timer pause traversal deliberately does not yield: its comment accepts responsiveness loss for a debugger facility. Reusing this code as a bounded general scheduling operation would exceed its stated design. [Receive counts](https://github.com/erlang/otp/blob/ad05823719d77c8faee87348ea39513d4e2f99c5/erts/emulator/beam/erl_hl_timer.c#L1029-L1056), [BIF pause](https://github.com/erlang/otp/blob/ad05823719d77c8faee87348ea39513d4e2f99c5/erts/emulator/beam/erl_hl_timer.c#L2874-L2915), [resume counts](https://github.com/erlang/otp/blob/ad05823719d77c8faee87348ea39513d4e2f99c5/erts/emulator/beam/erl_hl_timer.c#L2919-L2964). Timer identity/expiry races remain in [report 19](19-process-signals-timers-deep-dive.md).

## Remaining limits

Traced: public request/resume branches; immediate activation; live monitor/demonitor/monitor-down and acknowledgment consumers; pending-list lifetime; dirty-handler lock/state gate; dirty-boundary drain; adjacent exit dispatch; timer pause/resume call ordering. Sampled: scheduler suspension primitives and system-work exclusion. Not closed: all lock-free publication/memory-order interleavings, every dirty native-return/exit path, timer-manager cancellation races, all system-task producers, maximum-count execution, allocator failure behavior, or an executable Rust admission/cleanup proof. Source tests and these ten branch cases narrow the gap; they do not establish every edge case.

Plan integration: these additional IDs are recorded in the [build plan](../build-plan.md); conditional scope and unexecuted ownership/interleaving obligations remain explicit.
