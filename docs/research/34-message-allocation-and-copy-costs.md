# Message allocation, copying and immutable-byte costs

Read-only source investigation, 2026-10-07: OTP 29.1.1, commit `ad05823719d77c8faee87348ea39513d4e2f99c5`. **No benchmarks, new VM experiments, implementation or upstream modifications were performed.** Performance improvements below are hypotheses with rejection criteria, not measured gains. Existing [mailbox](12-beam-mailboxes-source.md), [memory](18-process-execution-memory-deep-dive.md), [publication](30-buffered-signal-publication-protocol.md) and [parking](31-receive-parking-wakeup-protocol.md) reports cover the surrounding protocols.

The useful opportunity is to exploit Rust's admitted owned values and [accepted immutable byte sharing](../adr/0008-immutable-buffer-sharing.md) while preserving automatic scheduling, kill-safe ownership and selective-receive ordering. BEAM's allocation strategy is evidence, not a requirement to reproduce its heaps in Rust.

## 1. Send has several materially different allocation paths

`erts_send_message` first reads receiver state. Sequence-trace token presence selects a path that sizes the payload and token, allocates destination storage, and copies their non-immediate terms. Thus self-send does **not** universally avoid payload preparation. Only the no-token branch, with sender equal to receiver and OFF_HEAP_MSGQ clear, allocates a message reference without copying the term. Both paths still publish a queued message; neither invokes the receiver inline. [Trace selection](https://github.com/erlang/otp/blob/ad05823719d77c8faee87348ea39513d4e2f99c5/erts/emulator/beam/erl_message.c#L737-L758), [trace allocation/copy](https://github.com/erlang/otp/blob/ad05823719d77c8faee87348ea39513d4e2f99c5/erts/emulator/beam/erl_message.c#L767-L802), [self-send and normal copy](https://github.com/erlang/otp/blob/ad05823719d77c8faee87348ea39513d4e2f99c5/erts/emulator/beam/erl_message.c#L821-L861).

| Allocation condition | Pinned branch | Cost/ownership consequence |
|---|---|---|
| Off-heap receiver mode | Allocate message with attached fragment. | Avoid receiver MAIN heap allocation; positive-size message header and fragment are one allocation. |
| On-heap mode, MAIN already held or try-lock succeeds | Recheck usable heap; advance receiver heap top and use its off-heap list. | Receiver owns copied terms directly; message itself is a separate reference allocation. |
| Volatile heap, GC disabled, insufficient room or failed MAIN try-lock | Fall back to a fragment. | On-heap mode does not promise heap placement and does not block waiting for MAIN. |
| Refreshed state reports off-heap and heap attempt falls back | Fallback chooses combined fragment allocation. | The recheck alone is not an unconditional jump out of a successful heap attempt. |
| Zero copied words | Allocate message reference without a positive-size fragment. | Immediate/static/self-referenced payloads still incur queue-node work. |

[Mode dispatch](https://github.com/erlang/otp/blob/ad05823719d77c8faee87348ea39513d4e2f99c5/erts/emulator/beam/erl_process.h#L2878-L2897), [heap eligibility/try-lock](https://github.com/erlang/otp/blob/ad05823719d77c8faee87348ea39513d4e2f99c5/erts/emulator/beam/erl_message.c#L630-L665), [fallback representations](https://github.com/erlang/otp/blob/ad05823719d77c8faee87348ea39513d4e2f99c5/erts/emulator/beam/erl_message.c#L668-L687), [combined versus reference allocation](https://github.com/erlang/otp/blob/ad05823719d77c8faee87348ea39513d4e2f99c5/erts/emulator/beam/erl_message.h#L573-L595). Local starting point: [heap attempt](/home/bat/projects/bream/upstream/otp/erts/emulator/beam/erl_message.c:622).

The usable-room comparison is `free <= requested`: an exact fit takes the fallback. “Volatile” includes EXITING, DIRTY_RUNNING and DIRTY_RUNNING_SYS; it is not merely a synonym for insufficient capacity. No receiver GC is invoked by this allocation helper to create space. A concurrent mode change also cannot be equated with all senders already using off-heap storage: completion waits for thread progress before excluding mailbox roots from GC. Message-reference allocation already uses a scheduler-preferred quick allocator, so a Bream pool proposal should not compare itself against an assumed naive BEAM allocation. [Volatile mask](https://github.com/erlang/otp/blob/ad05823719d77c8faee87348ea39513d4e2f99c5/erts/emulator/beam/erl_process.h#L1352-L1354), [mode-change barrier](https://github.com/erlang/otp/blob/ad05823719d77c8faee87348ea39513d4e2f99c5/erts/emulator/beam/erl_message.c#L1113-L1131), [reference allocator](https://github.com/erlang/otp/blob/ad05823719d77c8faee87348ea39513d4e2f99c5/erts/emulator/beam/erl_message.c#L40-L64).

### Copy avoidance has explicit exceptions

The ordinary build path computes `size_object_litopt`, then copies with `copy_struct_litopt`. Literal terms outside the current purge area are skipped during sizing and retained by reference during copying. Ordinary shared subterms can instead be duplicated. The optional sharing-preserving build selects a different copier through SHCOPY_SEND; its calculation can temporarily insert move markers into the sender heap, and the source warns against using that heap between calculate and perform. This is not a safe template for interrupting an arbitrary Rust object graph. [Literal sizing](https://github.com/erlang/otp/blob/ad05823719d77c8faee87348ea39513d4e2f99c5/erts/emulator/beam/copy.c#L101-L121), [literal copy](https://github.com/erlang/otp/blob/ad05823719d77c8faee87348ea39513d4e2f99c5/erts/emulator/beam/copy.c#L758-L769), [build switch](https://github.com/erlang/otp/blob/ad05823719d77c8faee87348ea39513d4e2f99c5/erts/configure.ac#L874-L882), [temporary mutation warning](https://github.com/erlang/otp/blob/ad05823719d77c8faee87348ea39513d4e2f99c5/erts/emulator/beam/erl_message.c#L747-L750).

Copy reductions are charged **after** publication, based on copied words, and capped at CONTEXT_REDS. That does not make one large size walk, copy or allocator call preemptible, nor accurately price every binary backing-byte operation. Bream must account for its actual admitted operations and continuations, including construction and cleanup. [Accounting](https://github.com/erlang/otp/blob/ad05823719d77c8faee87348ea39513d4e2f99c5/erts/emulator/beam/erl_message.c#L874-L885).

## 2. Publication and selection do not erase allocation ownership

The send wrapper may prepend a scheduler-pending MONITOR to the payload, preserving the sender's control/message order. Direct publication then checks EXITING under MSGQ. On rejection it puts the prepended control signal back into `pending_signal` and cleans up only the ordinary messages. A faster batch or self-send path must not discard that control obligation together with its payload. This is already covered by **MSG-04.C14** in the [messaging plan](../build-plan/messaging.md), not a new case. Buffer acceptance has different admission mechanics described in report 30; the late buffer-reinstallation concern remains unconfirmed. [Prepending](https://github.com/erlang/otp/blob/ad05823719d77c8faee87348ea39513d4e2f99c5/erts/emulator/beam/erl_message.c#L463-L479), [process wrapper](https://github.com/erlang/otp/blob/ad05823719d77c8faee87348ea39513d4e2f99c5/erts/emulator/beam/erl_message.c#L532-L544), [direct rejection/restore](https://github.com/erlang/otp/blob/ad05823719d77c8faee87348ea39513d4e2f99c5/erts/emulator/beam/erl_message.c#L406-L426).

Accepted fragment data does not necessarily undergo an immediate second whole-message copy when selected. The receive instruction unlinks the message, cancels its receive timer and calls `erts_save_message_in_proc`. That function adopts fragment off-heap lists and their accounting into the process, clears the old list ownership, and retains the message/fragment on `msg_frag`. With no attached data it frees the message reference. Adoption itself walks each fragment's off-heap list to find its tail: a payload containing many distinct references can make this step substantial even when byte copying is small. [Receive adoption](https://github.com/erlang/otp/blob/ad05823719d77c8faee87348ea39513d4e2f99c5/erts/emulator/beam/emu/msg_instrs.tab#L227-L235), [ownership transfer](https://github.com/erlang/otp/blob/ad05823719d77c8faee87348ea39513d4e2f99c5/erts/emulator/beam/erl_message.c#L965-L999).

Cleanup distinguishes separate and combined fragments, releases each attached off-heap list, and finally frees message storage. A payload already on the receiver heap has no attached fragment to release here; its heap owner remains responsible. “Free queue node” and “reclaim every byte represented by the message” are different operations. [Fragment cleanup](https://github.com/erlang/otp/blob/ad05823719d77c8faee87348ea39513d4e2f99c5/erts/emulator/beam/erl_message.c#L194-L205), [message cleanup](https://github.com/erlang/otp/blob/ad05823719d77c8faee87348ea39513d4e2f99c5/erts/emulator/beam/erl_message.c#L229-L249).

## 3. Immutable bytes avoid payload copies, not every cost

The efficiency guide explicitly says its internal representation description predates the OTP 27 binary rewrite. For OTP 29 this audit follows `ErlHeapBits`, `ErlSubBits`, `BinRef` and `Binary` in source instead of treating the guide's ProcBin terminology as current layout. [Documentation caveat](https://github.com/erlang/otp/blob/ad05823719d77c8faee87348ea39513d4e2f99c5/system/doc/efficiency_guide/binaryhandling.md#L119-L128).

| Binary branch | Actual work and constraint |
|---|---|
| New bitstring at most 64 bytes | Store bytes inline on a heap; ordinary message copy includes bytes. The threshold is a BEAM implementation choice, not Bream's selected threshold. |
| ErlSubBits backed by BinRef | Allocate/copy view and reference descriptors, pin writable storage, increment backing reference, attach reference to destination off-heap ownership. Stable bytes are shared. |
| Match-context view backed by heap bits | Copy the selected bits into a heap bitstring, rather than sharing mutable matching state. |
| New small slice | The generic slice builder copies sizes at most the on-heap limit, even from a large backing allocation. |
| Already ref-backed small view copied as a message | Preserve its ref-backed representation even below the normal threshold. Small visible size alone therefore does not determine retention or send cost. |

[Threshold](https://github.com/erlang/otp/blob/ad05823719d77c8faee87348ea39513d4e2f99c5/erts/emulator/beam/erl_bits.h#L166-L176), [new storage](https://github.com/erlang/otp/blob/ad05823719d77c8faee87348ea39513d4e2f99c5/erts/emulator/beam/erl_bits.c#L2757-L2786), [copy branches](https://github.com/erlang/otp/blob/ad05823719d77c8faee87348ea39513d4e2f99c5/erts/emulator/beam/copy.c#L812-L862), [small-slice creation](https://github.com/erlang/otp/blob/ad05823719d77c8faee87348ea39513d4e2f99c5/erts/emulator/beam/erl_bits.c#L2635-L2668), [preserved small reference representation](https://github.com/erlang/otp/blob/ad05823719d77c8faee87348ea39513d4e2f99c5/erts/emulator/beam/copy.c#L219-L238). Bitstring cases inform representation safety; they do not admit a full Erlang bit-syntax API into Bream.

### First sharing can be more expensive than subsequent sharing

`erts_pin_writable_binary` clears write flags, asserts unique backing ownership and, if at least eight allocated bytes are spare, calls binary realloc to shrink capacity. It then updates the view's base address. Realloc may move storage; this source does not establish its latency or copying behavior. A later nonempty append to nonwritable storage allocates a new writable binary and copies the old contents, preserving the sent snapshot. Repeated steady-state fanout of already-frozen bytes therefore misses the first-publication and append-after-send costs. [Pin/freeze](https://github.com/erlang/otp/blob/ad05823719d77c8faee87348ea39513d4e2f99c5/erts/emulator/beam/erl_bits.c#L2051-L2079), [allocator delegation](https://github.com/erlang/otp/blob/ad05823719d77c8faee87348ea39513d4e2f99c5/erts/emulator/beam/erl_binary.h#L320-L347), [append copy](https://github.com/erlang/otp/blob/ad05823719d77c8faee87348ea39513d4e2f99c5/erts/emulator/beam/erl_bits.c#L1896-L1921). Local source: [freeze](/home/bat/projects/bream/upstream/otp/erts/emulator/beam/erl_bits.c:2051).

### Sharing can retain much more than visible payload

Binary overhead accounting uses backing `orig_size`, not slice length; `binary:referenced_byte_size` exposes backing size when a BinRef exists. Multiple views or processes can charge/reference the same allocation. Summing those charges is neither unique physical storage nor RSS. A small retained slice of a large buffer can keep its entire backing allocation alive; deliberately copying that slice can improve retained-memory cost while worsening immediate CPU/allocation cost. [Overhead](https://github.com/erlang/otp/blob/ad05823719d77c8faee87348ea39513d4e2f99c5/erts/emulator/beam/erl_bits.h#L346-L349), [backing-size inspection](https://github.com/erlang/otp/blob/ad05823719d77c8faee87348ea39513d4e2f99c5/erts/emulator/beam/erl_bif_binary.c#L2520-L2533).

Normal message copying handles every encountered ref-backed view, creating destination descriptors and reference obligations. The optional shared copier can preserve shared structure and performs its pinning earlier. Thus fanout cost depends on recipient count **and reference/view multiplicity inside each payload**, not only byte length. [Ordinary reference copy](https://github.com/erlang/otp/blob/ad05823719d77c8faee87348ea39513d4e2f99c5/erts/emulator/beam/copy.c#L823-L846), [shared-copy variant](https://github.com/erlang/otp/blob/ad05823719d77c8faee87348ea39513d4e2f99c5/erts/emulator/beam/copy.c#L1652-L1675).

Finally, generic off-heap cleanup also releases magic references, and `erts_bin_free` may invoke a magic-binary destructor that takes over deallocation. Ordinary immutable bytes and arbitrary native resources cannot be conflated merely because both use a refcounted allocation. Bream's accepted sharing contract covers runtime-managed immutable bytes; it does not admit arbitrary destructor-bearing objects. [Off-heap release types](https://github.com/erlang/otp/blob/ad05823719d77c8faee87348ea39513d4e2f99c5/erts/emulator/beam/erl_message.c#L165-L183), [last-reference/free branches](https://github.com/erlang/otp/blob/ad05823719d77c8faee87348ea39513d4e2f99c5/erts/emulator/beam/erl_binary.h#L373-L395).

## 4. Seven performance experiments, all proposed

These report-local task IDs do not replace the feature index. Before comparison, establish a semantically correct baseline and freeze the workload and acceptable regression thresholds. Every candidate must pass publication-order, partial-operation kill, sender-death and receiver-death checks; throughput cannot compensate for a failed ownership invariant.

| Task | Candidate and experiment | Acceptance/rejection evidence |
|---|---|---|
| PERF-34.T01 — Move admitted payloads | Compare direct ownership transfer against deliberate clone/copy for equivalent generated protocol values: inline fields, owned vectors and immutable-buffer handles. Measure preparation separately from enqueue and consume. | Accept eliminated walks/copies only with valid ownership at every suspension/publication boundary. Reject generic `Clone` or user callbacks that evade admission, or a faster send that moves work into an unbounded later phase. |
| PERF-34.T02 — Node layout/allocation | Compare separate node/payload, combined allocation and small inline envelope; then compare allocator baseline with bounded worker-local caches. Sweep envelope size and cross-worker final frees. | Require fewer allocations or lower measured latency without unacceptable retained cache capacity, fragmentation or cleanup stalls. Cache emptying and host shutdown must release all owned storage. Do not adopt BEAM's 64-byte threshold without data. |
| PERF-34.T03 — Self-send specialization | Compare common ingress with owner-local append, including pending control signals, unmatched old messages, concurrent external traffic and tracing on/off. | Accept only equivalent selectable order and wakeup behavior. Reject a shortcut that overtakes prior traffic, invokes a handler inline or suppresses trace events. Trace overhead is reported separately. |
| PERF-34.T04 — Freeze without compulsory shrink | Compare freeze retaining capacity, eager compaction, and an explicit budgeted compact operation. Separate first send, subsequent fanout and append-after-freeze; vary capacity/length ratio. | Seek lower worst operation time at an explicit retained-memory cost. Reject hidden allocator/copy stalls or any mutable alias surviving publication. Kill-safe ownership must cover both old/new allocation during compaction. |
| PERF-34.T05 — Detach retained slices selectively | Compare shared slices with copied slices across backing/slice ratios, fanout counts and short/long residence. Include another holder that retains the full backing regardless. | Accept only when end-to-end CPU and uniquely retained physical bytes justify the policy. Copying cannot save the backing allocation while another owner still needs it; reject claims based solely on per-process charged bytes. |
| PERF-34.T06 — Fanout reference overhead | Measure one buffer versus many views of the same buffer, one versus many senders, one versus multiple workers. Compare straightforward per-holder references with a separately modeled batched publication scheme. | Count atomic reference operations and contention. Any batching must register each recipient obligation before visibility and release unused reservations after partial fanout/kill. No non-atomic cross-worker sharing or coupling recipient death to producer lifetime. |
| PERF-34.T07 — Budget adoption and release work | Compare off-heap-list traversal/cleanup equivalents for one large buffer versus many small buffers of equal total bytes; test retaining a received payload after node removal. Prototype explicit incremental cleanup before allocator pooling. | Require bounded admitted steps, accurate pending-cleanup counters and improved peer progress/cleanup tails. Reject moving a linear ownership walk into an allegedly constant-time dequeue or reporting reclamation while references remain. |

Record payload construction strategy, literal versus dynamic inputs, compiler/runtime build, mailbox mode, worker count and tracing configuration. Sweep 0/1/63/64/65 bytes, larger payloads, recipient count and queue residence. Include both successful delivery and dead-recipient disposal. Measure allocations, bytes copied, unique backing capacity, logical references, throughput, p50/p99/p99.9 latency, longest uninterrupted operation, peer progress, stop latency and final reclamation latency. These are different metrics; RSS and message rate alone cannot choose a design. No numeric speedup or latency target is claimed here.

## 5. Proposed additional behavior cases

Checked `messaging.md`, `execution-and-resources.md` and `features.json`: current final IDs were MSG-01.C09 and EXEC-03.C10. The following **seven new refinements are planned, not implemented or executed**. ERTS-specific storage branches become conditional reference oracles, not mandatory Rust representations.

| Case | Trigger and required/forbidden behavior; acceptance check |
|---|---|
| MSG-01.C10 | Self-send with/without sequence tracing and with on-/off-heap mailbox mode. Preserve identical payload and selective ordering despite different preparation paths; retain enabled trace behavior. Check snapshot immutability and lifetime after sender-local replacement. |
| MSG-01.C11 | MAIN try-lock fails, heap is volatile, GC is disabled, or free words equal requested size. Fragment fallback must preserve delivery/ownership without assuming synchronous receiver GC or waiting for its application code. Force each reference branch; qualify corresponding Rust path only if implemented. |
| MSG-01.C12 | Zero-size message reference versus combined fragment versus separate fragment, followed by selection, discard or receiver death. Release the right allocation/list exactly once; adopted receiver payload survives queue-node removal. Instrument allocation owners instead of inferring them from payload size. |
| EXEC-03.C11 | First sharing freezes writable backing, possibly shrinks it; sender later appends. Previously sent bytes remain unchanged. Cover spare-capacity and allocator-movement branches; Bream must reject post-freeze mutable aliases and own both allocations through any resumable replacement. |
| EXEC-03.C12 | Small slice construction versus already ref-backed small view; large backing outlives producer. Preserve visible bytes, track full retained backing separately, and release only after final actual holder. Do not assert all small slices are copied or all slicing is zero-copy. |
| EXEC-03.C13 | One payload contains repeated/shared views, then fans out; holders die in different orders. Every descriptor/ownership obligation is discharged once while one physical backing remains valid. Exercise ordinary/shared reference builds separately; Bream's chosen descriptor representation must not alter value semantics. |
| EXEC-03.C14 | Last release of ordinary immutable bytes versus a destructor-bearing resource encoded through similar refcount machinery. Ordinary bytes follow qualified runtime deallocation; unqualified callbacks/resources are rejected by admission rather than silently treated as bytes. Test the actual admitted destructor boundary, including host shutdown. |

Selected upstream assertions were **read, not run**: message-queue mode tests compare unconsumed heap growth ([test](https://github.com/erlang/otp/blob/ad05823719d77c8faee87348ea39513d4e2f99c5/erts/emulator/test/message_queue_data_SUITE.erl#L185-L205)); writable-binary tests retain old values across copies and further append ([test](https://github.com/erlang/otp/blob/ad05823719d77c8faee87348ea39513d4e2f99c5/erts/emulator/test/bs_construct_SUITE.erl#L733-L758)); combinations of parent/sub-bitstrings test the optional sharing-preserving copier ([test](https://github.com/erlang/otp/blob/ad05823719d77c8faee87348ea39513d4e2f99c5/erts/emulator/test/binary_SUITE.erl#L2157-L2180)); retained-size tests demonstrate a 128-byte view retaining 1,024,000 backing bytes and explicit copying reducing that retention ([test](https://github.com/erlang/otp/blob/ad05823719d77c8faee87348ea39513d4e2f99c5/lib/stdlib/test/binary_module_SUITE.erl#L775-L790)). These are correctness examples, not benchmark results.

Remaining gaps include allocator internals/latency, full shared-copier mutation recovery, all literal-purge interactions, distributed/alternate-action producers, weak-memory publication, native-resource destructors and Bream's actual Rust payload representation. Small focused experiments can resolve the performance choices only after those candidates' ownership and scheduling boundaries are explicit.

The proposed cases are integrated in the [build plan](../build-plan.md). Report-local experiment names feed the separately numbered [performance backlog](../performance-plan.md); they are not additional executed tests or measured results.
