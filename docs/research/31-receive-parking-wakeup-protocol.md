# Receive parking and wakeup ownership

Source review, 2026-10-07, against official OTP `29.1.1`, commit `ad05823719d77c8faee87348ea39513d4e2f99c5`. This extends [report 18](18-process-execution-memory-deep-dive.md) and [report 19](19-process-signals-timers-deep-dive.md). All upstream links pin that commit. No VM, runtime fixture or upstream test was executed in this review, and no upstream source was changed. Coverage is the interpreter/x86 receive boundary, normal scheduling-state handoff and directly connected message/signal/timer producers. OS worker-idle mechanisms are excluded.

The protocol is more precise than “check the mailbox, then sleep.” The final receive check retains `MSGQ` until application activity is cleared; producers synchronize with that decision; scheduling-state CAS operations then decide who owes a queue insertion. Enqueueing work, marking it runnable, inserting a scheduling record, claiming execution and consuming a message are separate events. The source supports a lost-wakeup argument for these paths, not an exhaustive proof across every scheduler/backend combination.

## 1. The state being parked

| State/record | Role in this trace | Must not be inferred |
|---|---|---|
| `ACTIVE` | Application work is eligible to continue; receive wait clears it. | Every retained mailbox item currently matches, or the process owns a worker. |
| `ACTIVE_SYS` | Runtime control/system work is eligible independently. | An application receive handler should run. |
| `RUNNING` / `RUNNING_SYS` | A scheduler has claimed the respective execution mode. | Physical absence from every queue/proxy structure. |
| `IN_RUNQ` and per-priority queue bits | Reserve representation in scheduling queues; proxy entries have additional rules. | Queue insertion has already completed at the instant the state changes. |
| Receive save pointer | Next candidate for the current selective scan. | The mailbox is empty when the pointer reaches its end. |
| Process timer pointer / `TIMEDOUT` | Identity of the current receive timer or its committed expiry state. | A timeout mailbox message or an arbitrary PID-scoped callback. |

These roles follow the wait instruction, queue-admission/claim branches, receive peek and timer definitions. [Wait](https://github.com/erlang/otp/blob/ad05823719d77c8faee87348ea39513d4e2f99c5/erts/emulator/beam/emu/msg_instrs.tab#L371-L383), [queue bits](https://github.com/erlang/otp/blob/ad05823719d77c8faee87348ea39513d4e2f99c5/erts/emulator/beam/erl_process.c#L6570-L6627), [execution claim](https://github.com/erlang/otp/blob/ad05823719d77c8faee87348ea39513d4e2f99c5/erts/emulator/beam/erl_process.c#L10068-L10137), [peek](https://github.com/erlang/otp/blob/ad05823719d77c8faee87348ea39513d4e2f99c5/erts/emulator/beam/erl_proc_sig_queue.h#L2301-L2307), [timer states](https://github.com/erlang/otp/blob/ad05823719d77c8faee87348ea39513d4e2f99c5/erts/emulator/beam/erl_hl_timer.h#L38-L53).

A correct progress invariant therefore concerns newly unexamined input or required control work, not merely `mailbox_length > 0`. A selective receive can properly park with many already-rejected messages retained. Advancing after rejection preserves that distinction. [No-match advance](https://github.com/erlang/otp/blob/ad05823719d77c8faee87348ea39513d4e2f99c5/erts/emulator/beam/emu/msg_instrs.tab#L249-L261).

## 2. The final check carries a lock into generated code

Interpreter `i_loop_rec` peeks at the save position. At the end it calls `erts_proc_sig_receive_helper`, which fetches outer input and processes middle signals. The helper returns one of three materially different states: a candidate; yield/exit without a candidate; or no further candidate/control work with `MSGQ` **still held**. It explicitly documents retaining the lock to avoid incoming-message races on the way to wait. Reaching the end of the current scan is not enough by itself. [Interpreter entry](https://github.com/erlang/otp/blob/ad05823719d77c8faee87348ea39513d4e2f99c5/erts/emulator/beam/emu/msg_instrs.tab#L44-L113), [helper contract/fetch](https://github.com/erlang/otp/blob/ad05823719d77c8faee87348ea39513d4e2f99c5/erts/emulator/beam/erl_proc_sig_queue.c#L7730-L7803), [control/yield branches](https://github.com/erlang/otp/blob/ad05823719d77c8faee87348ea39513d4e2f99c5/erts/emulator/beam/erl_proc_sig_queue.c#L7808-L7868).

The loader distinguishes wait labels reached from `loop_rec` from unlocked entry paths. Locked variants inherit the queue lock; unlocked variants acquire it. Here `ERTS_PROC_LOCKS_MSG_RECEIVE` is exactly `MSGQ`. The x86 JIT calls the same receive helper and preserves its locked-empty result before entering wait. This is a compiler/runtime interface obligation, not a Rust `Poll::Pending` convention supplied automatically by a native stack. [Loader predicates](https://github.com/erlang/otp/blob/ad05823719d77c8faee87348ea39513d4e2f99c5/erts/emulator/beam/predicates.tab#L183-L194), [instruction selection](https://github.com/erlang/otp/blob/ad05823719d77c8faee87348ea39513d4e2f99c5/erts/emulator/beam/emu/ops.tab#L459-L487), [lock alias](https://github.com/erlang/otp/blob/ad05823719d77c8faee87348ea39513d4e2f99c5/erts/emulator/beam/erl_process_lock.h#L209-L209), [x86 helper return](https://github.com/erlang/otp/blob/ad05823719d77c8faee87348ea39513d4e2f99c5/erts/emulator/beam/jit/x86/instr_msg.cpp#L143-L200).

Wait records the continuation, clears `ACTIVE` unless the receive timer is already marked expired, unlocks `MSGQ`, and schedules out. `RUNNING` is not cleared by wait itself. The JIT helper writes its continuation after unlocking, while still in the current process's execution context; another scheduler must still pass the execution claim/`MAIN` ownership protocol. [Interpreter wait](https://github.com/erlang/otp/blob/ad05823719d77c8faee87348ea39513d4e2f99c5/erts/emulator/beam/emu/msg_instrs.tab#L371-L383), [JIT helpers](https://github.com/erlang/otp/blob/ad05823719d77c8faee87348ea39513d4e2f99c5/erts/emulator/beam/jit/beam_jit_common.cpp#L1188-L1206), [JIT schedule-out call](https://github.com/erlang/otp/blob/ad05823719d77c8faee87348ea39513d4e2f99c5/erts/emulator/beam/jit/x86/instr_msg.cpp#L280-L302).

## 3. Direct ingress and schedule-out form the handoff

For ordinary direct message ingress, `queue_messages` acquires `MSGQ` if needed, checks exit state, appends the message, releases the lock if locally acquired, **then** calls the notification helper. A caller already owning `MSGQ` retains it. `LINK_MESSAGE` also marks `MSG_SIG_IN_Q`; notification separately reads current scheduling state and sets `ACTIVE` if needed. Append and wakeup are therefore not one atomic step. [Direct producer](https://github.com/erlang/otp/blob/ad05823719d77c8faee87348ea39513d4e2f99c5/erts/emulator/beam/erl_message.c#L394-L459), [append flag](https://github.com/erlang/otp/blob/ad05823719d77c8faee87348ea39513d4e2f99c5/erts/emulator/beam/erl_message.h#L474-L488), [notification](https://github.com/erlang/otp/blob/ad05823719d77c8faee87348ea39513d4e2f99c5/erts/emulator/beam/erl_proc_sig_queue.h#L2080-L2088).

`schedule_process` uses `change_proc_schedule_state` to set `ACTIVE`. Its CAS loop reserves an insertion only when the process is not already running, suspended or represented appropriately; it cannot alter the running bits. Actual queue insertion follows the state transition. Concurrent changes force reconsideration. [Activation CAS](https://github.com/erlang/otp/blob/ad05823719d77c8faee87348ea39513d4e2f99c5/erts/emulator/beam/erl_process.c#L6899-L6975), [activation entry](https://github.com/erlang/otp/blob/ad05823719d77c8faee87348ea39513d4e2f99c5/erts/emulator/beam/erl_process.c#L7005-L7022), [insertion](https://github.com/erlang/otp/blob/ad05823719d77c8faee87348ea39513d4e2f99c5/erts/emulator/beam/erl_process.c#L6867-L6895).

Schedule-out clears the normal running bits, reevaluates application/system activity and reserves queue representation in the **same CAS**. Insertion follows under the selected run-queue lock. These branches support the following source-derived interleaving argument; this is not a completed memory-model proof. [Schedule-out transition](https://github.com/erlang/otp/blob/ad05823719d77c8faee87348ea39513d4e2f99c5/erts/emulator/beam/erl_process.c#L6741-L6805), [physical insertion](https://github.com/erlang/otp/blob/ad05823719d77c8faee87348ea39513d4e2f99c5/erts/emulator/beam/erl_process.c#L6843-L6863).

| Arrival relative to receive parking | Observed transition / outstanding obligation |
|---|---|
| Append before final locked fetch | Fetch exposes the input; receiver examines it or handles its control effect before concluding the scan is exhausted. |
| Sender attempts direct append during locked-empty → clear-`ACTIVE` | Sender waits for `MSGQ`; its append/notification follows that sleep decision. |
| Notify after `ACTIVE` clear, while `RUNNING` remains set | Activation remains visible; sender does not claim a second executor. Schedule-out sees it or loses its CAS and retries. |
| Notify after schedule-out clears `RUNNING` | Sender's activation can reserve the insertion itself. A racing insertion reservation is detected through queue/state bits. |
| Append consumed before delayed notify | Notification may produce an unnecessary turn; this is not lost delivery. A model must permit pending notification and harmless extra activation. |

“Exactly one queue node globally” is too strong: priority elevation can require proxies. At dispatch, the scheduler removes the consumed queue reservation, checks active/suspended/running states, and CAS-claims execution. Obsolete records may be discarded. The relevant invariant is one application execution owner plus a surviving progress obligation, not a universal node count. [Proxy admission](https://github.com/erlang/otp/blob/ad05823719d77c8faee87348ea39513d4e2f99c5/erts/emulator/beam/erl_process.c#L6599-L6627), [claim/discard](https://github.com/erlang/otp/blob/ad05823719d77c8faee87348ea39513d4e2f99c5/erts/emulator/beam/erl_process.c#L10046-L10176), [subsequent process locks](https://github.com/erlang/otp/blob/ad05823719d77c8faee87348ea39513d4e2f99c5/erts/emulator/beam/erl_process.c#L10191-L10194).

## 4. Buffered input and control signals add obligations

Buffer ingress can bypass `MSGQ` while appending under a slot lock. When insertion observed all slots previously empty, it waits until `MSGQ` is released **before notification**; the source explicitly says this prevents a sleep decision overwriting the wakeup. Flush concurrently exchanges the nonempty bitmap and drains selected slots; producer retries preserve message/non-message summary flags. The direct-ingress argument alone cannot verify this optimization; [report 30](30-buffered-signal-publication-protocol.md) traces the broader buffer publication/retirement protocol. [Producer/flush race](https://github.com/erlang/otp/blob/ad05823719d77c8faee87348ea39513d4e2f99c5/erts/emulator/beam/erl_proc_sig_queue.c#L10308-L10365), [sleep synchronization](https://github.com/erlang/otp/blob/ad05823719d77c8faee87348ea39513d4e2f99c5/erts/emulator/beam/erl_proc_sig_queue.c#L10379-L10420), [flush](https://github.com/erlang/otp/blob/ad05823719d77c8faee87348ea39513d4e2f99c5/erts/emulator/beam/erl_proc_sig_queue.c#L10532-L10560).

Fetch also repairs flags if new buffered input crossed its clearing operation. If corresponding activity is absent, it schedules an auxiliary notification because it cannot assume the caller's locks. That callback looks up the PID anew and suppresses already-satisfied notifications. A queue flag is evidence of pending work, not necessarily a completed enqueue. [Repair and callback](https://github.com/erlang/otp/blob/ad05823719d77c8faee87348ea39513d4e2f99c5/erts/emulator/beam/erl_proc_sig_queue.c#L1446-L1564).

Non-message signals use `ACTIVE_SYS`, with a distinct activation path. Schedule-out also notices middle signals/system-task flags before their sender's final notification, including receive-traced messages in the middle queue. A selected `RUNNING_SYS` turn handles control work, then returns to sleep if there is no application activity or the process remains suspended. Only an eligible transition CASes into `RUNNING`; a kill may instead select exit processing. [Signal notification](https://github.com/erlang/otp/blob/ad05823719d77c8faee87348ea39513d4e2f99c5/erts/emulator/beam/erl_proc_sig_queue.h#L2062-L2075), [early work detection](https://github.com/erlang/otp/blob/ad05823719d77c8faee87348ea39513d4e2f99c5/erts/emulator/beam/erl_process.c#L6708-L6739), [system/application transition](https://github.com/erlang/otp/blob/ad05823719d77c8faee87348ea39513d4e2f99c5/erts/emulator/beam/erl_process.c#L10320-L10412). Waking a process for runtime work does not mean its application receives a message or resumes through a suspension.

## 5. Receive expiry is an identity-checked wakeup

The wait-timeout instruction installs a timer only when neither `F_INSLPQUEUE` nor `F_TIMO` is set. Repeated wakes and rejected messages therefore do not restart the timeout. Zero proceeds directly to the timeout continuation; infinity needs no running timer; invalid values release the receive lock and reset the cursor before raising. Interpreter and shared JIT helpers implement these branches. [Interpreter timeout setup](https://github.com/erlang/otp/blob/ad05823719d77c8faee87348ea39513d4e2f99c5/erts/emulator/beam/emu/msg_instrs.tab#L317-L359), [JIT counterpart](https://github.com/erlang/otp/blob/ad05823719d77c8faee87348ea39513d4e2f99c5/erts/emulator/beam/jit/beam_jit_common.cpp#L1208-L1255).

`proc_timeout_common` first CASes the **specific timer pointer** to `TIMEDOUT`. Only the winner acquires/releases `MSGQ`, reads scheduling state and activates an inactive, non-exiting target. This is not a numeric receive-generation field; identity plus retained timer/process lifetime supplies the inspected mechanism. Timer-wheel creation retains the process and two timer references, and its callback releases the relevant references after this arbitration. [Expiry](https://github.com/erlang/otp/blob/ad05823719d77c8faee87348ea39513d4e2f99c5/erts/emulator/beam/erl_hl_timer.c#L692-L705), [ownership setup](https://github.com/erlang/otp/blob/ad05823719d77c8faee87348ea39513d4e2f99c5/erts/emulator/beam/erl_hl_timer.c#L914-L922), [callback releases](https://github.com/erlang/otp/blob/ad05823719d77c8faee87348ea39513d4e2f99c5/erts/emulator/beam/erl_hl_timer.c#L828-L845).

The critical race has two source-derived resolutions. If expiry is visible before wait checks the timer, wait leaves `ACTIVE` set. If expiry happens after that check but before wait clears activity, the callback's later `MSGQ` synchronization observes the completed sleep decision and supplies activation. Expiry does not directly rewrite a running continuation: scheduler reentry, while owning `MAIN`, selects the saved timeout continuation and clears the timer sentinel, unless exiting. [Wait check](https://github.com/erlang/otp/blob/ad05823719d77c8faee87348ea39513d4e2f99c5/erts/emulator/beam/emu/msg_instrs.tab#L371-L383), [continuation selection](https://github.com/erlang/otp/blob/ad05823719d77c8faee87348ea39513d4e2f99c5/erts/emulator/beam/erl_process.c#L10447-L10464).

Successful message removal cancels the receive timer. Cancellation atomically exchanges its pointer for `NONE`, clears flags, and routes outstanding physical cleanup to the owning timer scheduler if necessary. An old callback whose pointer no longer matches cannot commit expiry for a later receive. This trace does not prove every allocator-reuse or remote-cancellation interleaving. [Removal](https://github.com/erlang/otp/blob/ad05823719d77c8faee87348ea39513d4e2f99c5/erts/emulator/beam/emu/msg_instrs.tab#L227-L231), [cancellation](https://github.com/erlang/otp/blob/ad05823719d77c8faee87348ea39513d4e2f99c5/erts/emulator/beam/erl_hl_timer.c#L2832-L2845), [cleanup routing](https://github.com/erlang/otp/blob/ad05823719d77c8faee87348ea39513d4e2f99c5/erts/emulator/beam/erl_hl_timer.c#L1768-L1790).

Do not infer a universal message-versus-timeout winner from wall-clock ordering alone: matching can proceed while running, whereas committed expiry changes continuation at scheduler reentry. Characterize each controlled ordering and preserve unselected messages; an elapsed-time assertion alone does not identify the branch.

## 6. Evidence, new cases and limits

Upstream `parallel_signal_enqueue_race_1/2` documents formerly stranded receivers when fetching buffered signals outside normal running execution; both comments warn their stress tests may pass even with the old bug present. `dirty_schedule` documents the separate “runnable but absent from the queue” race between selection and schedule-out. These are evidence for required transitions, not reproduced proofs. [Fetch race tests](https://github.com/erlang/otp/blob/ad05823719d77c8faee87348ea39513d4e2f99c5/erts/emulator/test/signal_SUITE.erl#L1332-L1347), [inspection race](https://github.com/erlang/otp/blob/ad05823719d77c8faee87348ea39513d4e2f99c5/erts/emulator/test/signal_SUITE.erl#L1403-L1422), [scheduling race](https://github.com/erlang/otp/blob/ad05823719d77c8faee87348ea39513d4e2f99c5/erts/emulator/test/signal_SUITE.erl#L1499-L1521). Invalid-timeout cursor recovery has a direct regression requiring the following receive to find retained input. [Regression](https://github.com/erlang/otp/blob/ad05823719d77c8faee87348ea39513d4e2f99c5/erts/emulator/test/receive_SUITE.erl#L694-L721).

`features.json` ended at `EXEC-01.C10` and `MSG-03.C10` when allocation was checked. These eight proposed cases do not edit that inventory or select a Rust engine.

| Case | Controlled branch and oracle | Scope / forbidden outcome |
|---|---|---|
| EXEC-01.C11 | Place direct append before final fetch versus while receiver retains `MSGQ` through parking. Input must be examined or leave a wakeup obligation. | Initial core. Forbid a stable sleeping state with fresh input and no producer/queue obligation. Old unmatched messages are excluded. |
| EXEC-01.C12 | Delay sender notification after append; race activation CAS with schedule-out CAS and delayed physical insertion. | Initial core. Forbid losing `ACTIVE` through stale overwrite or forgetting a reserved insertion; permit harmless extra turns. |
| EXEC-01.C13 | Several concurrent wakes cross queue reservation and execution claim. Count application owners, not only queue records. | Initial single-worker ownership; true parallel producer/worker variants conditional on embedding/scaling. Forbid double execution; priority proxies are later scope. |
| EXEC-01.C14 | Runtime-only signal/kill arrives during parking or explicit suspension; complete control processing without unrelated application continuation. | Kill/control progress initial; explicit suspension later. Forbid treating `ACTIVE_SYS` as permission to run a suspended application. |
| EXEC-01.C15 | Buffered insertion crosses empty-slot publication, final fetch, flag clearing and auxiliary notification; include a non-running inspection fetch. | Buffered optimization later/research. Forbid stranded work or relying only on the direct-ingress model. |
| MSG-03.C11 | Timer expires before wait's sentinel check, between check/clear, and after `MSGQ` unlock. | Initial. Each branch retains or creates progress; forbid overwritten wakeup and duplicate timeout continuation. |
| MSG-03.C12 | Receive A matches/cancels, receive B arms; delay A's callback/physical cleanup, including timer-owner migration. | Identity/cancellation initial; migration conditional. Forbid A timing out B, duplicate cleanup or restarting A's timeout on unmatched traffic. |
| MSG-03.C13 | Matching input, unmatched suffix and expiry cross a scheduling boundary; compare zero/infinity/invalid timeout entry and subsequent receive. | Initial ordinary mailbox; priority/marker variants conditional. Record allowed outcomes by transition, forbid lost retained messages or an invented wall-clock tie-breaker. |

Traced coverage ends at the named normal state/queue transitions, interpreter/x86 helpers, direct and selected buffered producers, process-timer arbitration and callback cleanup routing. Unresolved: all hardware memory-order executions, complete timer allocator/refcount reclamation, every priority/dirty/migration combination, arbitrary loader control-flow validity and generated Rust admission/continuation safety. A finite interleaving model can test a stated abstraction and mutations; it cannot turn these exclusions into verified BEAM or Bream behavior. No new handwritten-yield requirement, exact latency promise, public API or implementation architecture follows from this audit.
