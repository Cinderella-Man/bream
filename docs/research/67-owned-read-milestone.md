# Owned local read: implementation findings

Completed **2026-10-09**. The [source contract](66-owned-read-source-contract.md) now has an executed [fourteenth implementation milestone](../../experiments/owned-read/README.md). This adds one concrete external operation to the generated process boundary, while keeping broader G1–G5 qualification open.

The runtime owns a local socket and read buffer in a private operation record. A dedicated readiness driver claims the request, releases shared-state locks and attempts one nonblocking read. An actor waits for a typed result; its generated frame does not lend storage to the driver. On a positive read, the existing Vec moves into an owned ReadBytes value. A correctness control checks that its backing address is unchanged across that transfer. This supports an ownership-based way to avoid an extra payload copy, not a measured improvement over BEAM; the BEAM source also contains buffer reuse and transfer paths.

The important experiment stops an actor while the driver has a claimed request. Actor cleanup completes and the registry slot is reused while the original read buffer remains live. Completing that request later disposes its data without changing the replacement. This applies the [historical green-runtime lesson](63-rust-green-runtime-lessons-and-experiments.md): actor lifetime and external-operation lifetime can be separated without retaining an actor-frame borrow.

That separation does not make external effects transactional. Cancellation before the final check can suppress a read; a claimed read that passed the check may consume bytes after actor death, then discard them. This backend uses synchronous nonblocking recv plus poll, so the kernel does not keep the buffer after the syscall returns. It does not qualify cancellation of io_uring requests, borrowed native callbacks or arbitrary dependency code.

Admission includes both pending and ready-but-unconsumed requests. Up to sixteen operations, each at most4096 bytes, may be outstanding. Returned buffers follow actor ownership and no longer consume an operation slot, so these limits are not a whole-runtime memory bound. One endpoint can be installed per actor, and it closes after the first completed read, including a positive short read. Host-side aliases must not compete for reads or change the admitted endpoint's nonblocking mode.

Review identified two implementation flaws before retained qualification. Cancellation was sampled before request claim, allowing an older observation to bypass cancellation completed before claim; it is now sampled after claim. The wake path retried Interrupted indefinitely while actor lifecycle locks could be held. It now performs one nonblocking write; failure other than WouldBlock closes the sole control writer. The driver observes persistent EOF/HUP, closes admission and settles requests. This is a deliberate fail-closed policy, with Unavailable returned to affected live waiters. Both changes have controlled regression cases.

The [passing cohort](../../evidence/owned-read/runs/20261009-read-01/results.json) records 454 expected command outcomes, 408 aggregate observations and 219 preserved inputs. Each compiler profile passes 119 runtime tests, 169 rejected consumer programs and ten positive shadowing examples. Six public read configurations include 96 write/kill races and stop at pending, ready and actor-owned buffer boundaries. All inherited controls pass, including the prior BEAM exit reference. A failed-result conversion and duplicate completion are synthetic controls; actual socket observations cover short data, buffered data with peer closure, EOF, WouldBlock and shutdown. No speed tests or performance comparisons ran.

The [read-only audit](../../evidence/owned-read/validation.json) checks 1,157 hash records and preservation of all 205 preceding-milestone inputs. No remaining material issue was found in the source-contract review within the declared single-worker, trusted-host scope. This is bounded evidence, not an exhaustive concurrency proof or general driver-panic recovery.

Next: preserve a local endpoint across sequential reads. A persistent resource introduces a new distinction between endpoint ownership and successive request identities on the same live actor. Old cancellation/readiness/completion must not affect a later read, and stopping between operations must still close the endpoint and settle buffers exactly once.
