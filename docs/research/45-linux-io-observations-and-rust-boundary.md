# Linux I/O observations and the Rust boundary

**2026-10-07. Five isolated syscall scenarios, compiled at two optimization levels: 2 compilations and 10 executions, all with expected observations.** These are Linux contract observations, not BEAM execution, a Bream backend or speed measurements. They complement the pinned-source [polling review](42-linux-readiness-and-registration-lifetime.md) and [native-resource review](44-native-resource-callback-and-owner-lifetime.md).

## What was executed

The [fixture](../../evidence/io-lifetime-review/epoll_contract.c) uses nonblocking anonymous pipes and explicit ordering. Each scenario gets a fresh executable process. Successful expected events use a one-second epoll timeout; expected empty observations use a zero timeout. A five-second parent watchdog bounds each child, including unexpected interruption loops. There are no external network peers, sleeps used to guess a race, benchmark timing claims or Bream dependencies. The small C fixture tests the Linux ABI Bream's Rust backend would also face; it is not proposed library implementation code.

[Manifest and results](../../evidence/io-lifetime-review/probe-results.json) record the host, exact compiler invocation, source/runner/binary hashes and raw streams. Recorded host: Linux `7.0.0-34-generic`, x86-64. Compiler: GCC 15.2.0; `-std=c11 -Wall -Wextra -Werror`, with `-O0` and `-O2`. Each scenario fails on unexpected output, stderr, nonzero exit or timeout. Compiler/version commands require successful exit without timeout; their recorded stderr was also empty.

| Scenario | Controlled sequence and observation | Implication to qualify in Bream |
|---|---|---|
| Copied readiness survives deregistration and reuse | Pipe A reports token 101 into a local event variable. Delete its registration, close its read FD, deliberately reuse that exact numeric FD for pipe B and register token 202. New readiness carries 202; the retained old event still carries 101. Reading the reused numeric FD gets B's byte. | Dispatch must establish which live registration authorizes the operation. A saved number alone can address the wrong resource. A generation check does not itself keep a validated resource alive through the subsequent operation. |
| Duplicate keeps the kernel association alive | Register one read FD, duplicate it, close the registered descriptor, then write. The old token still arrives. Deleting via the unregistered duplicate returns ENOENT. Closing the remaining duplicate removes the interest. | Own the registration separately from a handle's drop; know whether duplicates exist. Do not assume a duplicate descriptor is interchangeable with the registration key. |
| Readiness is consumed before use | Observe readable, consume the byte, then attempt another nonblocking read. It returns EAGAIN. | Readiness is a hint to attempt qualified I/O, not a completed operation or a reservation. This fixture orders two reads; it does not exercise competing threads. |
| One-shot registration needs rearming | Observe a one-shot event without draining the pipe. A second poll is empty. MOD rearms and replaces token 505 with 506; readiness returns again. | Represent enabled/disabled/rearming obligations and retry paths. The fixture does not test simultaneous rearm/cancel or claim all BEAM pollsets use one-shot mode. |
| Hangup can coexist with unread data | Write a byte and close the writer. The reader gets IN and HUP together, reads the byte, then gets EOF. | Do not discard buffered data simply because a hangup bit appears. Routing bits and completing I/O are different steps. |

The Linux manual defines an epoll key using both descriptor number and open file description; duplicates affect automatic removal. It also describes stale event-cache entries. The control API documents one-shot rearm, caller-supplied event data and unread data accompanying HUP. These contracts motivated the scenarios; the table reports our executions rather than inferring that Bream already handles them. [epoll(7)](https://man7.org/linux/man-pages/man7/epoll.7.html), [epoll_ctl(2)](https://man7.org/linux/man-pages/man2/epoll_ctl.2.html).

## What Rust can establish earlier

`OwnedFd` provides ownership of one descriptor and closes it on drop; `BorrowedFd<'a>` expresses a borrowed valid descriptor. An API using those types can reject ordinary premature owner destruction while a live borrow is still used. Neither type identifies a poll-registration incarnation, cancels a detached event, excludes other duplicated descriptors or reserves readable bytes. `OwnedFd::try_clone` explicitly creates another owned handle sharing the same open file description. [OwnedFd](https://doc.rust-lang.org/std/os/fd/struct.OwnedFd.html), [BorrowedFd](https://doc.rust-lang.org/std/os/fd/struct.BorrowedFd.html).

That is useful leverage: the public API can consume descriptor ownership at registration and expose only qualified operations, instead of repeatedly trusting arbitrary integers. Internally, a short-lived dispatch guard could retain registration storage and borrow its descriptor for the operation. Private types can distinguish a detached owned notification from permission to touch a live resource. Such designs are candidates, not a chosen representation. Concurrent teardown, token reuse, raw syscalls and foreign callbacks still require protocol proofs.

Automatic forced termination makes the ownership contract stricter. If admitted code can forget a handle or its cleanup is abandoned, ordinary Drop alone is insufficient. Registration obligations must either remain independently tracked or the admission boundary must make the escape impossible. A guard that remains accessible on a suspended computation cannot be reclaimed merely because a user-visible handle vanished. See the executed counterexamples in [report41](41-rust-guarantees-and-process-admission.md).

## Turn the observations into bounded work

The first backend experiment should connect owner death, operation cancellation, detached notification disposal, backend stop acknowledgment and final handle close. Record each transition independently. Exercise copied old events after slot reuse and close the owner between validation and use; the latter needs real concurrent or modeled evidence absent here. Preserve already completed external effects. Track cleanup through the final outstanding registration owner, separately from process Down.

Rust-specific performance candidates should compare a correct baseline with typed registration ownership, compact typed event records and guarded accesses. Measure allocation, syscalls, lookup/refcount work, peer scheduling delay and stop-to-close tails. Batching must preserve cancellation/rearm dependencies; a throughput gain from delaying teardown indefinitely is a failure. The [performance backlog](../performance-plan.md) carries these experiments with the source reviews' corresponding branches.

This report adds evidence to IO-01 refinements rather than duplicating their case IDs. It does not close the production admission question, prove weak-memory correctness, cover all Linux file types or certify any BEAM source concern. No new user preference is needed: the remaining work is establishing a safe implementation of the accepted process contract.
