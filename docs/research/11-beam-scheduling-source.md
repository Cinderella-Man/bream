# BEAM scheduling: source trace and consequences for Bream

Inspected on 2026-10-07: official Erlang/OTP tag **OTP-29.1.1**, commit **`ad05823719d77c8faee87348ea39513d4e2f99c5`**, from the clean checkout at `/home/bat/projects/bream/upstream/otp`. All GitHub links below are immutable commit permalinks. This is source inspection, not a benchmark, a built-VM experiment, or proof of Bream's implementation.

The central finding is that **BEAM's automatic scheduling is an execution contract shared by generated code, process representation, and runtime operations**. A run queue alone is insufficient. Both the interpreter and native x86 JIT repeatedly return control at prescribed points with a known process state. Runtime operations that can grow with input need their own accounting and resumable implementation. Dirty native execution is a distinct escape path and does not inherit forced native termination.

This report concerns raw BEAM/ERTS primitives. It proposes no GenServer, supervisor, restart strategy, or other OTP behavior.

## 1. Process state is more than a runnable closure

`struct process` stores heap/stack pointers, failure state, the remaining reduction count `fcalls`, saved argument registers and their live count, instruction pointer `i`, accumulated reductions, run-queue linkage, and signal queues. Its comments explicitly restrict when `fcalls` and saved `arity` are valid. State flags separately represent application activity, queue presence, running application code, running system work, suspension, exiting, and dirty execution. These are not interchangeable values of a single simplistic `Running/Stopped` flag. [Process layout, lines 1039–1106](https://github.com/erlang/otp/blob/ad05823719d77c8faee87348ea39513d4e2f99c5/erts/emulator/beam/erl_process.h#L1039-L1106), [local layout](/home/bat/projects/bream/upstream/otp/erts/emulator/beam/erl_process.h:1039); [state flags, lines 1278–1340](https://github.com/erlang/otp/blob/ad05823719d77c8faee87348ea39513d4e2f99c5/erts/emulator/beam/erl_process.h#L1278-L1340), [local flags](/home/bat/projects/bream/upstream/otp/erts/emulator/beam/erl_process.h:1278).

The scheduler's next-process selection uses an atomic state transition to claim execution. It considers activity, suspension, and existing normal/dirty execution. A special case permits exit processing on a normal scheduler while an exiting process is still doing dirty native work; this is not permission for two application continuations to run concurrently. [Claim and exception, lines 10066–10188](https://github.com/erlang/otp/blob/ad05823719d77c8faee87348ea39513d4e2f99c5/erts/emulator/beam/erl_process.c#L10066-L10188), [local](/home/bat/projects/bream/upstream/otp/erts/emulator/beam/erl_process.c:10066).

**Bream implication:** define separate execution ownership, wakeup/queued work, exit state, and reclamation state before adding multiple workers. A generated future's Rust type does not itself provide these lifecycle transitions. Initially proving exactly one active poll and preventing every post-stop resume is more important than reproducing ERTS's full flag layout.

## 2. Where an interpreter process gives up its turn

The normal build's `CONTEXT_REDS` is 4,000. `erts_schedule` also has a modified-timing configuration path, so the constant should not be promoted into a universal timing promise. A reduction is accounted work, not a native instruction or a nanosecond. [Constant, lines 49–58](https://github.com/erlang/otp/blob/ad05823719d77c8faee87348ea39513d4e2f99c5/erts/emulator/beam/erl_vm.h#L49-L58), [local](/home/bat/projects/bream/upstream/otp/erts/emulator/beam/erl_vm.h:49); [budget choice, lines 9607–9638](https://github.com/erlang/otp/blob/ad05823719d77c8faee87348ea39513d4e2f99c5/erts/emulator/beam/erl_process.c#L9607-L9638), [local](/home/bat/projects/bream/upstream/otp/erts/emulator/beam/erl_process.c:9607).

The interpreter's `DISPATCH`, `DISPATCH_EXPORT`, `DISPATCH_FUN`, and `DISPATCH_RETURN` macros decrement `FCALLS` or branch to a context switch. These macros are used by local calls, external calls, function calls, and returns. This is explicit accounting at execution boundaries; the inspected path does not interrupt arbitrary C instructions using a periodic scheduler signal. [Dispatch macros, lines 154–232](https://github.com/erlang/otp/blob/ad05823719d77c8faee87348ea39513d4e2f99c5/erts/emulator/beam/emu/macros.tab#L154-L232), [local](/home/bat/projects/bream/upstream/otp/erts/emulator/beam/emu/macros.tab:154); [call instructions, lines 145–231](https://github.com/erlang/otp/blob/ad05823719d77c8faee87348ea39513d4e2f99c5/erts/emulator/beam/emu/instrs.tab#L145-L231), [local](/home/bat/projects/bream/upstream/otp/erts/emulator/beam/emu/instrs.tab:145).

On exhaustion, `process_main` reaches `context_switch`/`context_switch3`, determines the live argument count, checks exiting state, computes consumed reductions, saves argument registers and heap/stack state, saves `i`, and calls `erts_schedule`. On return, it restores arguments, `i`, and the new budget before dispatching again. `copy_out_registers` saves exactly the declared live argument count, allocating a larger save area when necessary. [Interpreter switch, lines 358–422 and 458–501](https://github.com/erlang/otp/blob/ad05823719d77c8faee87348ea39513d4e2f99c5/erts/emulator/beam/emu/beam_emu.c#L358-L501), [local](/home/bat/projects/bream/upstream/otp/erts/emulator/beam/emu/beam_emu.c:358); [register save/restore, lines 306–345](https://github.com/erlang/otp/blob/ad05823719d77c8faee87348ea39513d4e2f99c5/erts/emulator/beam/beam_common.c#L306-L345), [local](/home/bat/projects/bream/upstream/otp/erts/emulator/beam/beam_common.c:306).

**Bream implication:** a checkpoint must have a valid suspended representation and known ownership, not merely a counter decrement. The accepted generated-process route can delegate ordinary suspended-state representation and destruction to rustc, but its admission checker must ensure every supported execution cycle reaches such a boundary. Instrumenting the caller cannot interrupt an uninstrumented callee that never returns.

## 3. Native JIT execution keeps the same contract

The x86 JIT's instruction transformation adds `i_test_yield` at normal function ingress. `BeamModuleAssembler::emit_i_test_yield` emits the decrement and branch; the shared slow path derives the current MFA and arity before transferring to `context_switch_simplified`. The JIT's return sequence also decrements reductions and branches to a dispatch-return fragment. Tail calls can jump directly to a destination because the destination's ingress supplies the check. [Function transformation, lines 829–866](https://github.com/erlang/otp/blob/ad05823719d77c8faee87348ea39513d4e2f99c5/erts/emulator/beam/jit/x86/ops.tab#L829-L866), [local](/home/bat/projects/bream/upstream/otp/erts/emulator/beam/jit/x86/ops.tab:829); [ingress machine-code generation, lines 3201–3250](https://github.com/erlang/otp/blob/ad05823719d77c8faee87348ea39513d4e2f99c5/erts/emulator/beam/jit/x86/instr_common.cpp#L3201-L3250), [local](/home/bat/projects/bream/upstream/otp/erts/emulator/beam/jit/x86/instr_common.cpp:3201); [return/tail-call generation, lines 30–96](https://github.com/erlang/otp/blob/ad05823719d77c8faee87348ea39513d4e2f99c5/erts/emulator/beam/jit/x86/instr_call.cpp#L30-L96), [local](/home/bat/projects/bream/upstream/otp/erts/emulator/beam/jit/x86/instr_call.cpp:30).

`BeamGlobalAssembler::emit_process_main` generates the native scheduling stubs. They store the continuation address, redirect exiting processes, copy out live registers, call the same `erts_schedule`, copy in the selected process's arguments, reload `fcalls`, restore the process stack/heap registers, and jump to its continuation. This is native machine code designed for the runtime, rather than arbitrary native functions admitted after compilation. [JIT switch and restore, lines 126–315](https://github.com/erlang/otp/blob/ad05823719d77c8faee87348ea39513d4e2f99c5/erts/emulator/beam/jit/x86/process_main.cpp#L126-L315), [local](/home/bat/projects/bream/upstream/otp/erts/emulator/beam/jit/x86/process_main.cpp:126).

JIT runtime-entry/leave helpers explicitly synchronize heap, stack, and reductions according to the operation's requirements and switch to the runtime stack. Yielding is only safe at a suitable boundary: comments on shared BIF/NIF fragments explain that those fragments cannot simply yield everywhere and therefore require the check in module code. [Runtime transition, lines 753–859](https://github.com/erlang/otp/blob/ad05823719d77c8faee87348ea39513d4e2f99c5/erts/emulator/beam/jit/x86/beam_asm.hpp#L753-L859), [local](/home/bat/projects/bream/upstream/otp/erts/emulator/beam/jit/x86/beam_asm.hpp:753); [shared BIF boundary, lines 810–872](https://github.com/erlang/otp/blob/ad05823719d77c8faee87348ea39513d4e2f99c5/erts/emulator/beam/jit/x86/instr_bif.cpp#L810-L872), [local](/home/bat/projects/bream/upstream/otp/erts/emulator/beam/jit/x86/instr_bif.cpp:810).

**Bream implication:** “native” and “automatically scheduled” are compatible, but BEAM's JIT does not demonstrate transparent preemption/kill for every ordinary Rust dependency. The transferable design is mandatory generated boundaries plus a runtime-owned continuation contract. Exact registers, BEAM stack conventions, and term layout cannot be copied into an ordinary Rust library as its safety argument.

## 4. Run queues select work; they do not create interruption points

`ErtsRunQueue` includes priority queues, counters, synchronization, waiting/wakeup state, balancing state, and port work. `ErtsSchedulerData` owns worker-local registers, current process, scheduler type, run queue, timer structures, and other state. The normal/low priority queue is shared; maximum and high priorities have distinct selection. `enqueue_process_internal` appends, and `dequeue_process` removes the head of the selected queue. [Queue/worker structures, lines 472–519 and 687–747](https://github.com/erlang/otp/blob/ad05823719d77c8faee87348ea39513d4e2f99c5/erts/emulator/beam/erl_process.h#L472-L747), [local](/home/bat/projects/bream/upstream/otp/erts/emulator/beam/erl_process.h:472); [enqueue/dequeue, lines 3943–4035](https://github.com/erlang/otp/blob/ad05823719d77c8faee87348ea39513d4e2f99c5/erts/emulator/beam/erl_process.c#L3943-L4035), [local](/home/bat/projects/bream/upstream/otp/erts/emulator/beam/erl_process.c:3943).

`schedule_out_process` clears the appropriate running bits, preserves or updates runtime-system activity, and atomically decides whether to queue more work. `erts_schedule` may process auxiliary work, try stealing if a normal queue is empty, and wait when it has no work. The inspected stealing path limits a batch to roughly half the available tasks and at most 100 to constrain the critical section. These are implementation policies, not a language promise of globally exact round-robin fairness. [Schedule-out state transition, lines 6695–6810](https://github.com/erlang/otp/blob/ad05823719d77c8faee87348ea39513d4e2f99c5/erts/emulator/beam/erl_process.c#L6695-L6810), [local](/home/bat/projects/bream/upstream/otp/erts/emulator/beam/erl_process.c:6695); [steal batch, lines 4526–4595](https://github.com/erlang/otp/blob/ad05823719d77c8faee87348ea39513d4e2f99c5/erts/emulator/beam/erl_process.c#L4526-L4595), [local](/home/bat/projects/bream/upstream/otp/erts/emulator/beam/erl_process.c:4526); [idle scheduler path, lines 9870–9944](https://github.com/erlang/otp/blob/ad05823719d77c8faee87348ea39513d4e2f99c5/erts/emulator/beam/erl_process.c#L9870-L9944), [local](/home/bat/projects/bream/upstream/otp/erts/emulator/beam/erl_process.c:9870).

**Bream implication:** prove the process execution and wakeup contract on one normal-priority worker first. Copy the invariants—one execution owner, accounted runnable work, race-safe enqueue/wakeup—not the full mature scheduling policy. Work stealing cannot rescue a runtime whose every worker is stuck inside an unqualified operation.

## 5. Runtime and mailbox work also spend reductions

The selected process does not necessarily receive the whole nominal budget as application work. The normal scheduler can run signal handling and system tasks first, debit that cost, and reschedule before returning to application code. It limits signal work in the ordinary active-process case while permitting more work when preparing dirty execution or completing a signal flush. Before dispatch, it stores remaining `reds` into `p->fcalls` and asserts an exiting process points at an exit continuation. [Signal work accounting, lines 10320–10383](https://github.com/erlang/otp/blob/ad05823719d77c8faee87348ea39513d4e2f99c5/erts/emulator/beam/erl_process.c#L10320-L10383), [local](/home/bat/projects/bream/upstream/otp/erts/emulator/beam/erl_process.c:10320); [remaining turn/exit continuation, lines 10435–10464](https://github.com/erlang/otp/blob/ad05823719d77c8faee87348ea39513d4e2f99c5/erts/emulator/beam/erl_process.c#L10435-L10464), [local](/home/bat/projects/bream/upstream/otp/erts/emulator/beam/erl_process.c:10435).

Selective receive is also a scheduling path. In the interpreter, `loop_rec_end` advances the save pointer and decrements `FCALLS`; `i_loop_rec` checks exhaustion, saves a resumable receive location, and returns to the scheduler. The x86 JIT does the equivalent through `emit_loop_rec_end` and the shared receive loop. Thus a large queue of nonmatching messages is not treated as one indivisible cheap receive operation. [Interpreter receive, lines 44–111 and 249–262](https://github.com/erlang/otp/blob/ad05823719d77c8faee87348ea39513d4e2f99c5/erts/emulator/beam/emu/msg_instrs.tab#L44-L262), [local](/home/bat/projects/bream/upstream/otp/erts/emulator/beam/emu/msg_instrs.tab:44); [JIT receive check, lines 105–126](https://github.com/erlang/otp/blob/ad05823719d77c8faee87348ea39513d4e2f99c5/erts/emulator/beam/jit/x86/instr_msg.cpp#L105-L126), [local](/home/bat/projects/bream/upstream/otp/erts/emulator/beam/jit/x86/instr_msg.cpp:105); [JIT scan step, lines 268–279](https://github.com/erlang/otp/blob/ad05823719d77c8faee87348ea39513d4e2f99c5/erts/emulator/beam/jit/x86/instr_msg.cpp#L268-L279), [local](/home/bat/projects/bream/upstream/otp/erts/emulator/beam/jit/x86/instr_msg.cpp:268).

**Bream implication:** runtime control must proceed without an application receive, and runtime work needs its own bounded segments. The accepted growing mailbox/selective receive contract makes scanning, large message manipulation, and teardown scheduling essential qualification cases. A scheduler checking only at the outer Rust `loop` would still have blind spots inside `receive` or a large collection operation.

## 6. A concrete built-in operation is manually resumable

`BUMP_REDS` changes the remaining process budget; the trap macros set a continuation, live arguments, and `freason = TRAP`, returning a distinguished non-value. Yield variants additionally exhaust the current turn. This is runtime-internal continuation machinery, not an exception meaning that the application failed and not a signal handler abandoning a C stack. [Accounting, lines 66–104](https://github.com/erlang/otp/blob/ad05823719d77c8faee87348ea39513d4e2f99c5/erts/emulator/beam/bif.h#L66-L104), [local](/home/bat/projects/bream/upstream/otp/erts/emulator/beam/bif.h:66); [trap representation, lines 310–340 and 392–443](https://github.com/erlang/otp/blob/ad05823719d77c8faee87348ea39513d4e2f99c5/erts/emulator/beam/bif.h#L310-L443), [local](/home/bat/projects/bream/upstream/otp/erts/emulator/beam/bif.h:310); [explicit yield macros, lines 454–522](https://github.com/erlang/otp/blob/ad05823719d77c8faee87348ea39513d4e2f99c5/erts/emulator/beam/bif.h#L454-L522), [local](/home/bat/projects/bream/upstream/otp/erts/emulator/beam/bif.h:454).

List append (`++`) makes the design concrete. Its paths inspect/copy bounded cell counts derived from remaining reductions—32, 40, or 60 elements/cells per reduction in the examined normal-build paths. When unfinished, it puts `ErtsAppendContext` into a magic binary, creates a tracked reference, disables process GC while the continuation contains sensitive state, and traps. On re-entry it validates the continuation type, continues, traps again if necessary, then re-enables GC before returning or reporting an error. [Chunk accounting, lines 46–236](https://github.com/erlang/otp/blob/ad05823719d77c8faee87348ea39513d4e2f99c5/erts/emulator/beam/erl_bif_lists.c#L46-L236), [local](/home/bat/projects/bream/upstream/otp/erts/emulator/beam/erl_bif_lists.c:46); [trap/resume path, lines 267–342](https://github.com/erlang/otp/blob/ad05823719d77c8faee87348ea39513d4e2f99c5/erts/emulator/beam/erl_bif_lists.c#L267-L342), [local](/home/bat/projects/bream/upstream/otp/erts/emulator/beam/erl_bif_lists.c:267).

The interpreter's BIF instruction recognizes `TRAP` and dispatches the prepared continuation. The x86 heavy-BIF epilogue handles the trap through a context-switch fragment. A trap and “consume the entire turn” are distinguishable mechanisms; do not assume every trap has identical scheduling behavior in both execution engines. [Interpreter BIF return, lines 291–307](https://github.com/erlang/otp/blob/ad05823719d77c8faee87348ea39513d4e2f99c5/erts/emulator/beam/emu/bif_instrs.tab#L291-L307), [local](/home/bat/projects/bream/upstream/otp/erts/emulator/beam/emu/bif_instrs.tab:291); [JIT epilogue, lines 765–797](https://github.com/erlang/otp/blob/ad05823719d77c8faee87348ea39513d4e2f99c5/erts/emulator/beam/jit/x86/instr_bif.cpp#L765-L797), [local](/home/bat/projects/bream/upstream/otp/erts/emulator/beam/jit/x86/instr_bif.cpp:765).

**Bream implication:** admit a small useful family of owning operations and design each expensive one as resumable work with safe partial state. `Vec` growth, collection search, payload copying, broadcast, and cleanup cannot be assumed cheap because a function call looks small. Rust continuation state should remain normally destructible at every allowed stop boundary. Copying ERTS's raw-pointer/disabled-GC trick would not establish that property for Rust.

## 7. Dirty execution isolates work; it does not forcibly stop native code

ERTS defines separate dirty CPU and dirty I/O run queues. `erts_dirty_process_main` executes native BIF/NIF or dirty system work rather than the full BEAM instruction stream. It initializes `fcalls` for compatibility but explicitly does not use it to interrupt that work. Dirty CPU reductions are derived from elapsed time when control returns; dirty I/O receives a different accounting treatment. [Dirty queue identities, lines 1860–1882](https://github.com/erlang/otp/blob/ad05823719d77c8faee87348ea39513d4e2f99c5/erts/emulator/beam/erl_process.h#L1860-L1882), [local](/home/bat/projects/bream/upstream/otp/erts/emulator/beam/erl_process.h:1860); [dirty execution loop, lines 150–208 and 269–303](https://github.com/erlang/otp/blob/ad05823719d77c8faee87348ea39513d4e2f99c5/erts/emulator/beam/beam_common.c#L150-L303), [local](/home/bat/projects/bream/upstream/otp/erts/emulator/beam/beam_common.c:150).

`erts_call_dirty_nif` creates a shadow process environment, unlocks the main process lock, directly calls the native function, relocks, and checks whether the real process is exiting before arranging further application execution. This supports concurrent logical exit handling; there is no inspected mechanism here that makes an arbitrary nonreturning native function stop. The reference manual explicitly confirms this limitation and qualifies which resources death notification waits for. [Native call and return, lines 426–535](https://github.com/erlang/otp/blob/ad05823719d77c8faee87348ea39513d4e2f99c5/erts/emulator/beam/erl_nif.c#L426-L535), [local](/home/bat/projects/bream/upstream/otp/erts/emulator/beam/erl_nif.c:426); [resource/stop qualification, lines 460–490](https://github.com/erlang/otp/blob/ad05823719d77c8faee87348ea39513d4e2f99c5/system/doc/reference_manual/ref_man_processes.md#L460-L490), [local](/home/bat/projects/bream/upstream/otp/system/doc/reference_manual/ref_man_processes.md:460).

**Bream implication:** an escape to a blocking/native worker pool does not satisfy the accepted safe forced-termination requirement for arbitrary work. Keep unsupported operations rejected until their own resumable execution and resource lifetime are qualified. If a separate host-native escape is ever offered, it needs a plainly different contract; it cannot silently be presented as an ordinary killable Bream process.

## What transfers, and what does not

| Transferable design | BEAM dependency that Bream must replace |
|---|---|
| Renewable work allowance with automatic suspension | Compiler/VM-generated call, return, receive, and operation boundaries |
| Explicit saved continuation and live state | BEAM register conventions, term representation, stack/heap ownership |
| Runtime signal work independent of application receive | ERTS signal machinery, process states, locking and lifecycle protocols |
| Resumable data operations charged for work | Individually engineered trapping BIFs and their VM-managed partial state |
| Single execution owner and race-safe wakeup | ERTS atomic state/run-queue protocols, not merely a generic executor |
| Observable work and exit phases | Honest metrics for Bream's own admitted operations and cleanup |

Recommendation: retain the generated checked process model as an experiment, but treat its code/data-operation boundary as the main research work. The source supports this direction; it does not prove that a procedural macro can enforce a broad transitive Rust effect system. The previously executed signal probe remains evidence for asynchronous native scheduling, not a substitute for this ownership and termination contract.

## Falsifiable next experiments

1. **Boundary coverage:** on one worker, exercise admitted direct loops, nested loops with `continue`, helper calls, tail-recursive or equivalent repeated work, and a large data operation. A peer must progress; a stop request must prevent every later application step. An uninstrumented dependency that loops must fail admission, not hang after being labelled a process.
2. **Work budget versus wall time:** use the same budget for cheap arithmetic, variable-size payload transforms, large nonmatching mailbox scans, and fanout. Record work units, longest uninterrupted segment, peer ready-to-run latency, kill-to-stop latency, throughput, and stop-to-cleanup latency. Failure: any admitted input-proportional primitive becomes an unbounded scheduling blind spot. No hard deadline is inferred from the measured maximum.
3. **Partial-operation death:** kill between every chunk of an owned-buffer copy/search or room fanout operation. Record allocation ownership and destination admission decisions. Failure: double drop, lost accountability, invalid partially initialized state, or resumed work after execution-stop acknowledgement. Already delivered messages are not rolled back.
4. **Runtime-control pressure:** give a raw process a growing nonmatching mailbox and continual runtime relationship events while another process hogs CPU. Verify peer progress and kill serviceability even though the target never consumes an application stop message. Failure: either user scanning or runtime control monopolizes the worker indefinitely.
5. **Reference engine parity:** build explicitly identified interpreter and x86 JIT OTP reference binaries later; run raw recursive CPU work plus receive scans. Compare the observable contracts and costs, not equal reduction-to-time conversion. This report has not built or run either configuration.
6. **Multiple-worker ownership, after single-worker correctness:** race wakeup/kill/complete/transfer around the process execution claim. Record generation and execution-owner transitions. Failure: two workers poll one continuation, a freed continuation remains queue-visible, or a stale wakeup addresses a new incarnation.

## Tradeoff questions grounded in this code

These are suggested interview questions, not additional requirements or decisions already made.

1. **Which useful data work must the first process subset handle?** The room fixture needs membership scanning, owned payload handling, and fanout; should P0 qualify those runtime operations first, or must it also demonstrate a named real CPU algorithm through checked helper functions? The append implementation shows why the choice determines substantial runtime work.
2. **How should a turn be specified experimentally?** Prefer renewable work units with measured soft latency, or add elapsed-time checks at the same mandatory safe boundaries? Neither choice can interrupt an opaque operation between boundaries. The source's 4,000 reductions should not become an invented universal Bream quantum.
3. **What is the first migration contract?** Keep each process attached to one worker while proving local ownership, or require suspended admitted state to migrate before the first multi-worker milestone? ERTS supports migration because it controls process representation; ordinary Rust state needs an explicit transfer rule. This does not change the accepted single-worker mechanism tests or native-platform scope.

## Inspection coverage and remaining uncertainty

Read paths: `Process`/run-queue/scheduler structures and flags; normal `erts_schedule` selection and schedule-out paths; interpreter call/return/context-switch and receive paths; x86 JIT function-ingress, return, process-main, receive, and heavy-BIF/NIF boundary fragments; BIF accounting/trap macros; list append's complete start/chunk/trap/resume flow; dirty process loop; dirty native call/return; the documented dirty resource boundary.

Not established: a proof that every compiler-generated cycle and every built-in operation has bounded latency; all compiler transformations/loader validation; a full ARM JIT audit; complete priority fairness or work-stealing correctness; scheduler suspension/thread-progress invariants; every native extension or allocator path; full exit/resource reclamation; measured latency/density; or soundness of Bream's future public admission API. Other source reports cover complementary subsystems. No source was modified and no BEAM executable was built or run for this report.
