# Clock domains and process deadlines

Inspected **2026-10-07**, Erlang/OTP **OTP-29.1.1**, commit `ad05823719d77c8faee87348ea39513d4e2f99c5`. This is source research: **no clock was changed, timer fixture executed, or performance measured** for this report. [Report19](19-process-signals-timers-deep-dive.md) covers timer APIs and cancellation; [report36](36-timer-service-costs-and-batching.md) covers timer indexes and service costs. This pass traces the clock and conversion beneath those operations. In this checkout the associated declarations are in `erl_time.h`; there is no `erl_time_sup.h`.

The important separation is **deadline, observation, and service**. A deadline belongs to Erlang monotonic time. A clock reading determines whether that deadline has passed. Servicing the timer, making a process runnable, and the process consuming a message happen through other protocols. A more precise clock does not establish a dispatch-latency bound. The documented timer rule is no early triggering, with millisecond resolution and potentially later triggering under load. [Timer contract][timer-contract]; [deadline construction][parse]; [service integration][sched-check].

## 1. The time domains are distinct, even when their C types are not

| Domain | Representation and meaning | Process-timer consequence |
|---|---|---|
| OS system time | Platform wall-clock reading; Unix uses the configured realtime provider. | This can jump. It is not the absolute timestamp accepted by `send_after`/`start_timer`. [OS read][os-read]; [API][timer-api]. |
| OS monotonic time | Configured monotonic provider, with platform and build-dependent adjustment/suspend behavior. | It supplies corrected Erlang monotonic time when supported and enabled, but is not necessarily a raw hardware counter. [Provider selection][provider-select]; [configuration][clock-config]. |
| Internal Erlang monotonic time | Signed 64-bit representation on Unix, starting internally at one native-time second, with a finite upper endpoint. | Wheel and high-level deadlines use this domain after conversion to ticks. [Type][time-type]; [range][internal-range]; [parser][parse]. |
| External Erlang monotonic time | Internal time plus a fixed runtime-origin translation; on the common 64-bit nanosecond configuration, the external starting value is negative to retain immediate integer representation longer. | Negative absolute timestamps can be valid. They are neither Unix timestamps nor negative relative durations. [Origin][external-origin]; [translation][external-offset]. |
| Erlang system time / time offset | System time is monotonic time plus the current offset; the offset may change according to mode. | An offset update is not a request to rebuild existing monotonic deadlines. The fixed internal/external translation above is a different offset. [Domain definition][domains]; [offset update][offset-check]. |

These are semantic domains, not unique identifiers. Equal consecutive monotonic readings are allowed; tests explicitly accept equality. A timestamp must not replace a process/timer incarnation reference. The runtime's Unix `ErtsSystemTime` is a typedef of `ErtsMonotonicTime`, so C does not enforce the distinction. Rust private newtypes could reject accidental cross-domain operations before execution; they still need checked arithmetic and a well-defined runtime origin. [Monotonicity test][mono-test]; [typedefs][time-type].

## 2. Which clock implementation actually runs

Initialization selects a `get_time` function once. `erts_get_monotonic_time` invokes it and updates scheduler-local `last_monotonic_time`, resetting `check_time_reds`. This is not the same cost on every configuration. [Selection][dispatch]; [read entry][read-entry]; [bookkeeping][bookkeeping].

| Configuration | Read path and correction behavior | Meaning for deadlines |
|---|---|---|
| Correction enabled, OS clock already drift-corrected, multi-time-warp | `get_os_corrected_time`: OS monotonic read plus fixed `moffset`. A separate periodic checker compares OS and Erlang system time, adjusts the system offset when its threshold is crossed, and schedules change notifications. | Wall-clock jumps do not directly move the monotonic timer coordinate. This is the important modern fast path; do not benchmark a hypothetical per-read correction lock as its baseline. [Read/check][offset-check]. |
| Correction enabled, OS clock already drift-corrected, no/single warp | `get_os_drift_corrected_time` reads a correction instance under an RW lock and applies the error-rate adjustment. | Keeping the system offset fixed can require intentionally changing monotonic frequency. No-warp does not mean a more accurate elapsed-time clock. [Corrected read][corrected-read]; [no-warp contract][no-warp]. |
| Correction enabled, OS clock not drift-corrected | `get_corrected_time` uses the same instance protocol, applying both drift and error adjustment. | A different hardware/native clock is not an interchangeable optimization: it changes who is responsible for rate correction. [Formula][corrected-read]; [selection][dispatch]. |
| Correction disabled or OS monotonic support unavailable | `get_not_corrected_time` reads **OS system time under a mutex**, subtracts its offset, and clamps backwards results to the last value. Multi-warp can update its offset on that backwards branch. | No/single-warp can freeze until wall time catches up; forward jumps advance timer time. Multi-warp reduces the backwards freeze by changing the offset. [Implementation][uncorrected]; [documented modes][no-warp], [multi-warp][multi-warp]. |

The default is multi-time-warp, with correction enabled where supported. Single-warp has a preliminary phase and one finalization: the first finalizer changes the offset and returns the previous preliminary state; subsequent calls return final. No-warp is already final, and multi-warp remains volatile. Finalization is serialized by `erts_get_time_mtx`; it does not reset the monotonic epoch or each timer. These compatibility modes are reference branches, **not a proposal to add a Bream clock-policy menu**. [Default][multi-warp]; [correction default][correction-default]; [finalization][finalize].

The correction-instance boundary is more than storing a new multiplier. A writer holds the RW lock, retains the previous instance, selects a new OS-time start two native units ahead, computes its Erlang starting value using the previous correction, and publishes the new instance. Readers choose current or previous according to their OS reading; a value older than both aborts. This preserves the intended continuity across the transition without treating the two-unit offset as a timer quantum. The error coefficients are `20/2048` and `1/2048`, roughly 1% and 0.05%; these are adjustment constants, not scheduling accuracy guarantees. [Transition][correction-publish]; [reader/formula][corrected-read]; [constants][correction-constants]. The full drift-estimator numerical stability and all threshold transitions remain outside this bounded proof.

System-offset publication uses release-store/acquire-load. Notification dispatch is scheduled separately as auxiliary work; the public documentation permits different processes to observe an offset change at slightly different times. A timer must not wait for a `CHANGE` notification to establish that its monotonic deadline is due. Nor should two separately sampled clock domains be treated as one atomic snapshot: the Unix paired reader calls the monotonic provider and system provider sequentially. [Offset atomics][offset-atomic]; [notification scheduling][offset-notify]; [observation contract][offset-observe]; [paired reads][paired-read].

## 3. Linux provider and suspend qualifications

The build can select clock resolution and a custom monotonic ID. The default suspend preference is **not** to prefer clocks that count suspended time; enabling that preference changes the candidate list to include `CLOCK_BOOTTIME`. Configure refuses CPU-time and realtime IDs as monotonic choices. On Linux, support for `CLOCK_MONOTONIC` or `CLOCK_BOOTTIME` together with the raw-clock capability marks the selected clock as OS-corrected. These branches must be recorded in an experiment's configuration, rather than inferred just from “Linux.” [Options][clock-config]; [ID validation][clock-validation]; [candidate lists][clock-candidates]; [corrected-provider classification][clock-classification].

The Linux wrapper uses the configured monotonic provider on kernels at least 2.6.33. Its historical fallback selects `CLOCK_MONOTONIC_RAW` where supported, otherwise mutex-protected verification that clamps backwards values. Normal POSIX read failure aborts ERTS. These are inspected compatibility branches, not claims that this host exercised them. [Kernel-version selection][provider-select]; [wrappers/error][provider-wrappers].

Linux `CLOCK_MONOTONIC` excludes system suspend, admits rate adjustment and repeated values, and is unaffected by discontinuous wall-clock steps. RAW excludes suspend and rate adjustment; BOOTTIME includes suspend. Some `clock_gettime` implementations use vDSO, so counting function calls as kernel crossings is incorrect. [Linux clock manual](https://man7.org/linux/man-pages/man3/clock_gettime.3.html).

Host suspend, an offlined scheduler, debugger process suspension, and ordinary process preemption are different events. Normal scheduling turns do not pause elapsed deadlines. The source even samples time and services timers while a normal scheduler is in its scheduler-suspension loop. Debugger timer pausing remains the separate behavior in reports19/29. No new pause-on-preemption or hard-real-time rule is selected here. [Suspended scheduler service][suspended-scheduler]; [running scheduler service][sched-check].

## 4. Rounding is directional and operation-specific

For nonnegative internal readings, let `q` be native units per wheel tick. On the common millisecond wheel, positive relative setup computes `ceil(now/q) + duration_ms`: `(now-1)/q + 1` provides the upward rounding. At an exact tick boundary it adds no extra tick. A finite BIF timer uses `parse_timeout_pos`; an absolute external millisecond deadline is translated to the internal epoch and checked against runtime endpoints. The absolute path does not add another relative-duration rounding step. [Tick conversions][tick-convert]; [parser][parse].

Receive timeout setup reuses parsing but enforces the 32-bit millisecond duration limit; zero sets `F_TIMO` directly. The unsigned receive helper also handles zero before clock/deadline construction. BIF timers go through their own setup even for zero, and some internal callback/port helpers use a separate `msec <= 0` branch. Thus one universal “round every timeout up and allocate a timer” helper would change behavior. Infinity handling and receive-selection rules are already covered by the messaging reports. [Receive setup][receive-setup]; [BIF entry][bif-entry]; [internal helper][rounding].

**New source-derived edge:** `get_time_left` rounds **now** up and subtracts it from the stored deadline, returning zero when the deadline is no later than that rounded value. The active-state read branch calls this helper. Consequently, an active timer can report integer `0` during the final fractional millisecond before its deadline, or when due but not yet serviced. A cancellation that wins can also return zero. This is not `false`, and it does not establish message delivery or mailbox emptiness. The fractional-boundary branch is source-predicted here, not reproduced. [Remaining-time formula][rounding]; [active/cancel branches][remaining-read].

Generic `erlang:convert_time_unit` is different again: it uses mathematical floor, including negatives. For example, converting −1 microsecond to milliseconds produces −1, not zero. The Erlang implementation adjusts a negative numerator before `div`; uncommon units and negative internal values can trap from the native helper into this Erlang path. Internal positive conversion has a multiplication fast path and a split high/low path to avoid overflow of an intermediate product. This does **not** establish that every arbitrary mathematical result fits its final 64-bit representation. [Public conversion][public-convert]; [negative implementation][negative-convert]; [native fallback][conversion-fallback]; [wide intermediate][wide-convert].

A Rust conversion should make four decisions explicit: domain, unit, rounding direction and accepted range. Preserve the distinction between invalid duration, valid past absolute deadline and out-of-range timestamp. Widen before epoch translation/multiplication and check the final result; never let wrapping produce an apparently immediate timer. The existing source checks establish intended endpoint rejection, but this review is not a proof of every C arithmetic/compiler configuration at signed extrema. [Range and signed parse][parse]; [API endpoints][timer-api].

## 5. A kernel wait finishing is not the timeout oracle

`erl_poll.c:get_timeout` keeps an absolute Erlang deadline and derives the remaining relative wait from a fresh clock reading. Millisecond conversion rounds up and clamps at `INT_MAX`; other backends accept finer units. The platform premature-wait subtraction is zero on Linux in this revision. For a zero-event return, `erts_poll_wait` checks Erlang monotonic time again and repeats while still before the original deadline. It does not restart the full original duration on each empty wakeup. [Wait conversion][poll-convert]; [platform adjustment][premature]; [recheck loop][poll-recheck].

The epoll configuration either passes that relative millisecond wait to `epoll_wait`, or arms an internal `CLOCK_MONOTONIC` timerfd with a relative timespec and waits for events. Timerfd wakeups are translated back into the poll loop. The user timer remains governed by Erlang deadline/service logic; the timerfd's submillisecond wait precision does not make the process timer API submillisecond. [Epoll branches][epoll-branches]; [timerfd setup][timerfd]. Linux also documents that epoll timeout uses CLOCK_MONOTONIC, rounds to kernel granularity, and can overrun due to scheduling. [epoll_wait manual](https://man7.org/linux/man-pages/man2/epoll_wait.2.html).

Clock reads are already amortized in part of the running scheduler: reductions accumulate `check_time_reds`; the activities loop refreshes when its threshold is reached, then compares the saved clock against the next timeout. Other system-service paths refresh explicitly. A stale observation can postpone service; reusing a stale **registration** sample can instead make a new relative deadline too early. Those two caching uses must not be conflated. Clock reads, wheel bump, timeout signal publication, runnable transition and user dispatch need separate timestamps in any experiment. [Reduction accounting][clock-reds]; [refresh/reset][bookkeeping]; [activity loop][sched-check]; [additional refresh][system-refresh].

## 6. Rust opportunities and their limits

Official Rust documentation checked on 2026-10-07 reports std **1.99.0**. `Instant` is opaque, monotonic but not guaranteed steady; suspend behavior is unspecified across platforms/versions. `checked_add` reports representability failure. `checked_duration_since` can expose reversed readings, whereas saturating subtraction can hide a programming error or clock anomaly. The current Unix provider is CLOCK_MONOTONIC; this is not a portable promise of BEAM's configurable correction policy. [Instant](https://doc.rust-lang.org/std/time/struct.Instant.html).

`Duration::as_millis` returns whole milliseconds as `u128`, discarding a fractional millisecond. It cannot be substituted blindly for upward deadline or blocking-wait rounding, nor narrowed unchecked into an OS timeout integer. Its checked arithmetic is useful, but the maximum representable duration is not a guarantee that `Instant + duration` or a runtime tick counter can represent the result. [Duration](https://doc.rust-lang.org/std/time/struct.Duration.html).

Private typed domains can remove repeated tag checks and prevent adding a wall timestamp to a duration intended for a runtime deadline. Compile-time unit specialization may remove divisions; a runtime stamp or generative API is still needed if values from different runtime instances could otherwise mix. Neither the language nor the wrapper type proves clock monotonicity, fresh sampling, correction continuity or cancellation-race handling. These are proposals for the admitted runtime surface, not an API selection.

## 7. Eight additional planned cases

All cases below are **unimplemented/unexecuted proposals**, extending TIME-01.C01–C16. They refine previously broad timer inputs and service behavior with clock-specific oracles. Fault injection belongs in an isolated provider/harness; no host-clock mutation is authorized by this report.

| ID | Trigger and required observations | Forbidden outcome / qualification |
|---|---|---|
| **TIME-01.C17** | With corrected multi-warp, hold finite receive and BIF deadlines while injecting forward/backward wall-clock steps. Observe monotonic deadline, system offset and later notification separately. | Retiming an elapsed deadline from wall offset; requiring notification delivery before expiry; assuming atomic equality across separately sampled domains. [Offset][offset-check], [paired reads][paired-read]. |
| **TIME-01.C18** | Exercise correction/provider dispatch and no/single/multi-warp compatibility branches. Race two single-warp finalizers; verify one preliminary→final transition and unchanged timer coordinate. | Claiming correction-disabled mode still reads OS monotonic time; assuming every mode has identical freeze/rate behavior. Bream compatibility-mode admission remains unselected. [Dispatch][dispatch], [fallback][uncorrected], [finalize][finalize]. |
| **TIME-01.C19** | Distinguish configured suspend-excluding/inclusive clocks, repeated readings, historical regression verification and provider read failure; separately record runtime scheduling/preemption. | Using CPU time, treating repeated readings as duplicate timer identity, pausing deadlines on ordinary preemption, or asserting one cross-platform suspend contract. Failure injection must use the documented supported provider contract. [Configuration][clock-config], [providers][provider-wrappers]. |
| **TIME-01.C20** | Place setup/read/cancel just before, exactly on and after a tick boundary; include positive relative, absolute, BIF zero and receive zero. Delay service while the timer remains active. | Early firing through floor rounding; treating integer remaining-time zero as false, expired or delivered; allocating a receive-zero timer merely to share a helper. Fractional active-zero outcome still needs execution. [Parse][parse], [remaining][remaining-read], [receive][receive-setup]. |
| **TIME-01.C21** | Cross negative external origin, signed unit conversion, runtime start/end translation and final representability limits; use large intermediate products whose quotient fits and ones whose result does not. | Truncation-toward-zero replacing mathematical floor; rejecting all negative absolute timestamps; wraparound into an accepted near deadline. General parser boundary tests already in C01 remain prerequisites. [Origin][external-origin], [conversion][negative-convert], [range][parse]. |
| **TIME-01.C22** | Cause repeated empty poll returns before the deadline, waits exceeding `INT_MAX` milliseconds, and a provider rate differing from the kernel wait clock. Trace every derived remaining interval and final Erlang-time check. | Resetting the full original duration, accepting a capped/early kernel return as user expiration, or spinning indefinitely once genuinely due. Events/errors still follow their separate poll protocol. [Conversion][poll-convert], [recheck][poll-recheck]. |
| **TIME-01.C23** | Register near-deadline timers after lengthy work with an old cached clock; transfer already-constructed deadlines between workers; delay expiry batches and inspect the next fresh sample. | Constructing a relative deadline from a sample predating the allowed registration observation; mixing runtime origins; restarting elapsed duration during transfer. A stale servicing sample may add lateness, never license early expiry. [Read][read-entry], [scheduler][sched-check]. |
| **TIME-01.C24** | Force reads around previous/current correction-instance cutover and concurrently publish an offset update; cover equal readings and explicit backward-provider faults. | Torn correction fields, backwards corrected time at a valid transition, treating the future instance as applicable too soon, or changing stored timer positions on a system-offset notification. Full numerical/weak-memory qualification remains required. [Reader][corrected-read], [writer][correction-publish], [atomic offset][offset-atomic]. |

## 8. Five performance experiments

These are **unmeasured hypotheses**. Each treatment must preserve the accepted deadline and cancellation outcomes, cleanup progress, and independent timer identities. Measure through the runnable/dispatch phase as well as the clock call; report target, provider, correction configuration and compiler. Do not count a vDSO call as a syscall or derive a latency guarantee from an observed maximum.

| Local task | Correct baseline → candidate treatment | Measurements and semantic constraints |
|---|---|---|
| **PERF-48.T01: typed clock domains** | Dynamically tagged domain/unit values → private typed deadline/duration wrappers with checked boundary constructors. | Tag branches, instruction count, representation size and compile-fail rejection coverage. Inspect generated code before claiming zero runtime cost. C17/C21/C23 must still pass; cross-runtime identity is a separate obligation. |
| **PERF-48.T02: checked conversion specialization** | General checked wide conversion → constant-unit specialized operations with a verified fast path and checked wide fallback. | Cycles, divisions, fallback frequency, boundary failures and code size. Preserve ceiling for deadlines/waits and floor for signed public conversion; no truncating `as_millis` shortcut. C20/C21. |
| **PERF-48.T03: worker clock-read amortization** | Fresh reads at every service check → shared per-batch service observation plus mandatory freshness at registration and sleep/recheck boundaries. | Clock calls, actual kernel crossings, cycles, timer lateness, peer p99/max and backlog after a long batch. Reject early relative deadlines or unbounded stale service. Compare against a baseline that already includes BEAM-style scheduler caching. C20/C23. |
| **PERF-48.T04: retained deadline across waits** | Repeated generic wait conversion → typed stored absolute deadline, specialized remaining-wait conversion and backend-appropriate precision. | Clock/conversion calls, poll wakeups, retries, idle CPU, stop/wakeup response and timeout tails. Retain the original deadline through capped/empty waits; finer kernel waits must not silently change public timer resolution. C22. |
| **PERF-48.T05: qualified correction snapshot** | Lock-protected correction instances where correction is actually required → immutable versioned snapshot with safe publication/retirement, or initialization specialization for an already-corrected provider. | Read contention, update latency, retries, allocation/retention and scaling. First measure the existing direct-provider baseline; never “optimize away” a lock it does not use. Preserve continuity, provider failure behavior and reader lifetime; selection of representation is deferred. C18/C24. |

## Evidence limits and follow-up

Traced: principal correction dispatch, fixed versus mutable offsets, current/previous correction publication, Linux provider-selection branches, BIF/receive conversion, active remaining-time rounding, polling conversion/recheck, and selected scheduler sampling paths. Sampled: the drift estimator, time-offset notification fanout, custom build-provider combinations, timerfd integration and upstream tests. Unreviewed: every non-Linux provider, every native API time conversion, complete estimator error bounds, host-suspend recovery across all configured clock/poller combinations, and full overflow/weak-memory proofs.

Selected upstream source tests cover configuration/finalization, nondecreasing readings, cross-scheduler observation ordering and signed conversions. They are useful starting oracles but were **not run here**. The timer read test checks successive remaining values within one millisecond on a pinned scheduler; it is not an exact fractional-boundary demonstration of C20.
