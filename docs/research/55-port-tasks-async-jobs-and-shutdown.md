# Port tasks, async jobs and shutdown

Research date: **2026-10-08**. Reference: Erlang/OTP **OTP-29.1.1**, commit `ad05823719d77c8faee87348ea39513d4e2f99c5`. **Source and test-source review only: no driver test, runtime experiment, benchmark or Bream implementation was executed.** This extends [report25](25-process-owned-external-state.md)'s connection/link lifetime, [report44](44-native-resource-callback-and-owner-lifetime.md)'s callback ownership, and [report50](50-system-task-dispatch-and-dirty-handoff.md)'s native-return boundary. ETS algorithms, a port/driver compatibility layer and arbitrary host jobs remain unselected.

The useful distinction is between **preventing an unclaimed operation from starting**, **suppressing delivery to a dead recipient**, and **waiting until execution and cleanup have finished**. BEAM provides different mechanisms for these events. A Rust cancellation flag, dropped receiver or retained allocation does not make them equivalent. Bream's accepted [ADR0009](../adr/0009-death-and-reclamation-observation.md) still requires admitted process/helper execution to stop before `Down`; subsequent tracked reclamation cannot conceal continuing application work.

## 1. A port task is scheduled work, not an async thread-pool job

`erts_port_task_schedule` publishes input/output readiness, timeouts and process-to-port signals to a port's scheduler state. A scheduler claims these tasks and invokes their callbacks with the port lock held. In contrast, `driver_async` creates a distinct record for a pool thread to invoke without running through that port-task claim loop. The eventual ready callback is scheduler auxiliary work that looks up and locks the port anew. Treating these as one generic cancellable task would erase different ownership and cancellation contracts. [Port publication][schedule]; [port dispatch][execute]; [async record/admission][async-admit]; [worker execution][async-run]; [ready routing][async-ready].

Port-task admission first protects lookup: unmanaged callers acquire a port reference while delaying thread-progress reclamation, then leave that delay. The queue mutex serializes the rejection check and insertion. The scheduler's terminal EXIT flag rejects every new task; a synchronous `nosuspend` request also rejects when the port is already busy. EXIT is distinct from the earlier EXITING/closing phase that can still need driver service. Only after insertion does a state transition arrange run-queue ownership or notice an existing executor. A port that dies after insertion transfers the remaining obligation to cleanup. Failed process-signal publication invokes its abort callback and releases the record; a busy `nosuspend` branch settles through its own abort reason and can return scheduling success. **A scheduling return value alone is not evidence that the driver's operation ran.** [Lookup/admission][schedule]; [queue commit][enqueue]; [publication outcomes][schedule-outcomes]; [earlier exiting flag][exiting-flag].

The executor races `SCHEDULED → EXECUTING` against cancellation's `SCHEDULED → ABORTED`. Successful cancellation resets the handle and performs operation-specific abort accounting. It does not immediately free the queued node: the executor/cleanup later observes ABORTED and retires it through thread progress. A failed cancellation can mean no handle, already aborted, already executing or already executed; it is not a join or proof of completion. The callback's reduction charge and long-schedule observation occur after its return, so this state machine does not interrupt an executing native callback. [Abort claim][abort]; [execution claim and accounting][execute]; [deferred task free][task-free].

For Bream, a private typed request can express pending, claimed and settled ownership without retaining an arbitrary C callback ABI. On the accepted single-worker profile, a local request lane might also avoid cross-worker references and atomics where the publication model proves they are unnecessary. Both are implementation hypotheses. They cannot remove cancellation's loser branch or permit a running helper to outlive `Down`.

## 2. Busy queues preserve dependencies rather than global FIFO

When a busy port cannot accept a task marked `WAIT_BUSY`, the task moves to a local busy queue. A caller table records that sender's pending count and last task. A later `SIG_DEP` task from the same caller joins immediately after its latest dependent task even when the later operation itself does not wait for busy state. A task from a caller with no such dependency can proceed. This is a concrete reason that blindly replacing the queues with either one global FIFO or independent task-type queues changes behavior. [Busy insertion][busy-insert]; [dependency insertion][busy-dependency]; [selection][select].

The free transition seals task admission; cleanup drains the remaining **busy queue, local queue, incoming queue**, in that order to preserve signal ordering. Cleanup claims each still-scheduled record; already-aborted records skip their callback. Process signals receive `ABORT_CLOSED`, stale I/O tasks trigger selection cleanup, and suspended senders are resumed. The task records and the port structure are retired separately. [Free transition][free-port]; [ordered cleanup][cleanup]; [waiter and port release][cleanup-release].

The cleanup loops over the caller table and all queued tasks have no reduction-budget check. This is an unmeasured cost candidate, not an observed latency defect. A Rust cleanup cursor would have to retain queue order, per-task settlement, byte accounting, blocked-sender obligations and final-release ownership across every pause. It must not publish complete reclamation while residual work remains. The executor's ordinary reduction limit does not bound this nested cleanup loop. [Cleanup loops][cleanup]; [dispatch enters cleanup][execute].

## 3. Async job ownership survives the port

The async record stores the port identity, invocation and free functions, opaque job data, originating scheduler ID, optional port-data lock (PDL), dynamic-driver handle and queue-reclamation state. Admission validates the driver port while its lock is held. Before queue publication it retains the PDL when present and the dynamic-driver library, and prepares the eventual ready-queue insertion. It does **not** acquire general ownership of every allocation reachable from `async_data`, or keep `drv_data` alive merely because a job points into it. A driver must provide those data-lifetime obligations. [Record][async-layout]; [admission][async-admit]; [publication/code retention][async-publish].

The pool worker dequeues a record, invokes its native function and queues a completion; it does not first test whether the port is still alive. At completion, the scheduler looks up the port using driver-validity flags. A missing/dead/invalid port takes `async_free` when supplied. A valid port with `ready_async` invokes that callback, which takes responsibility for the job data; ERTS does not then also call `async_free`. A valid port with no ready callback takes the free branch. Only afterward does ERTS release PDL and driver-code holds. The record itself is then released by the ready-queue consumer. [Worker][async-run]; [completion branches and retention release][async-ready]; [callback ownership choice][ready-callback]; [record release][ready-budget].

“Closing” is not yet driver-invalid: the driver lookup mask deliberately excludes CLOSING, although the ordinary lookup mask includes it. A closing port can therefore receive ready callbacks that drain queued output and allow termination; the callback epilogue terminates a closing port once its I/O queue is empty. Port `stop` runs during termination before removal from the table; the async-code retention must remain independent of that port lifetime. This extends report25's close-versus-drain boundary rather than replacing it. [Lookup masks][lookup-masks]; [close and drain][close]; [callback epilogue][callback-epilogue]; [termination][terminate]; [flush fixture][test-flush-driver].

The pinned `peek_non_existing_queue` fixture starts an async operation, kills its port and waits for the port exit, then schedules another operation on the same async key. The first native operation sleeps and subsequently checks that the old port's I/O queue is unavailable while using the retained PDL; the second supplies a sequencing barrier. That test source explicitly exercises native activity after port death. **It was not run in this review.** Retaining the PDL keeps that synchronization object usable; it does not resurrect the I/O queue. [Fixture orchestration][test-dead-port]; [native checks and barrier][test-dead-job].

No generic async cancellation mechanism appears in this worker/record path. The pinned release history records removal of `driver_async_cancel`; old fixture names and a payload atom named `cancel` do not reintroduce that API. Port-task cancellation is a different facility. Suppressing `ready_async` after port death also cannot undo external side effects already produced by native invocation. [Removed API][cancel-removed]; [current invocation][async-run]; [historical fixture still submits all jobs][test-key-driver].

For Rust, a narrow job can own only its validated input/result buffers, a completion route and the specific resources it needs. Keeping an entire process or resource actor in an `Arc` solely for a result recipient unnecessarily expands retention; replacing it requires a safe publication and reclamation design, not just an integer ID. Conversely, moving a borrowed `drv_data` pointer into a job would lose the lifetime separation entirely. These lessons apply first to qualified runtime helpers. A separate host-job service with independent lifetime and side effects would require a user decision; this report neither chooses that service nor uses it to admit uninterruptible process work.

## 4. Invocation order and completion service are distinct

With a supplied key, admission maps it modulo pool size and writes the queue index back through the key pointer. Equal mapped keys use one worker, whose loop invokes jobs serially. Different keys can collide and thereby serialize unrelated work. With no key, assignment uses the incrementing async ID modulo worker count. The public documentation promises sequential invocation for same-thread requests; it does not turn all async work into one global FIFO. [Key routing][async-keys]; [public ordering contract][async-doc]; [worker loop][async-run].

Each job also records the scheduler that submitted it, with scheduler 1 as fallback for a non-scheduler caller. Ready results are sent to that scheduler's queue. Consequently, **source inference to test:** equal-key native invocations can remain ordered while ready callbacks from submissions on different schedulers are serviced in another order. The per-port lock excludes simultaneous callback execution; it does not itself resequence distinct ready queues. No newly executed trace establishes this candidate here, and the old `otp_9302` fixture sends its ordering messages from the native invocation on SMP, so that fixture is not evidence of globally ordered `ready_async` callbacks. [Scheduler capture][async-admit]; [ready queue selection][async-reply]; [native fixture messages][test-key-driver].

Ready service already caps one invocation of `erts_check_async_ready` at **20 callbacks** and re-arms scheduler auxiliary work when more may remain. This bounds a callback count, not elapsed service: one callback/free function, port-lock wait or reclamation operation can dominate. Completion enqueue also deliberately uses a mutex despite the queue's thread safety; the source explains its purpose as reducing producer contention during completion bursts so scheduler consumers can progress. A proposed Rust “lock-free improvement” must compare peer latency and wasted producer CPU, not infer superiority from removing that mutex. [Budget and release][ready-budget]; [auxiliary rescheduling][ready-aux]; [contention rationale][ready-contention]; [enqueue mutex][async-reply].

The file retains a synchronous no-pool fallback, but startup clamps the async-thread count to at least one in this pinned revision. A source branch is not automatically a supported `+A 0` experiment. This avoids mistaking old no-thread fixture comments for the normal supported runtime path. [Fallback][async-keys]; [startup clamp][pool-clamp].

## 5. Whole-runtime exit is not an embeddable-runtime destructor

Flushing halt marks run queues as halting, stops ordinary process scheduling and reaps ports; port callbacks can continue to drain their I/O. The final port close proceeds into system cleanup, which runs late NIF halt handlers, flushes async workers and waits for NIF calls with delayed-halt behavior. The port reaper has a special case for the heart port. This is coordinated VM termination, not ordinary process exit or a reusable resource shutdown primitive. [Halt sequence][halt]; [port reaping][reap]; [last port/closed ordering][terminate]; [system cleanup][system-cleanup].

`erts_exit_flush_async` appends a sentinel to each worker queue and joins every worker. Earlier queued jobs must reach their native return for those workers to reach the sentinel. It explicitly omits full cleanup because the runtime is terminating. The worker's final replies may therefore have been queued without a guarantee that their ready callbacks or every allocation were reclaimed before OS exit. A configured halt timeout ultimately calls `_exit`, which is an escape from whole-process shutdown, not safe cancellation of a Rust job inside a still-running host. [Sentinel/join][async-shutdown]; [timeout][halt-timeout].

Bream is intended to be embedded. Returning from runtime shutdown while a worker can still call freed runtime state, driver code or an allocator is not a valid adaptation of this source. A correct shutdown needs an explicit admission seal, ownership of already-admitted work, callback/completion settlement and proof that no worker retains callable runtime state before final release. This is a refinement of existing EXEC-05 evidence, not a selection of blocking arbitrary native jobs. Bounded shutdown still depends on the admitted work's enforceable execution boundary; a join cannot manufacture a bound for an uninterruptible invocation.

## 6. Seven additional planned branch cases

These extend **RES-01.C01–C06** without adopting ports or a general native-job API. All are **planned, unimplemented and unexecuted**. Dependencies: REF-02 fixtures, LANG-02/03 admitted resources/helpers, EXEC-03 cleanup, EXEC-05 embedding, LIFE-05 termination; cross-worker treatments additionally require EXEC-07.

| Case | Trigger and required qualification | Forbidden result / proposed evidence |
|---|---|---|
| **RES-01.C07** | Pause port-task publication before lookup retention, admission, insertion and activation; race exit, `nosuspend` busy rejection, execution and explicit abort. | No task both executed and aborted, no unowned rejected payload, no freed queued node, and no interpreting scheduling success as operation success. Record exactly one settlement and final release across each claim winner. |
| **RES-01.C08** | Sender A has a busy-waiting command then a signal-dependent control operation; sender B has independent work. Toggle busy state and trigger `nosuspend` cancellation. | No dependent A operation overtakes its predecessor; do not invent total order between independent senders or leave a canceled command's queue-byte accounting. Trace caller dependency and settlement separately. |
| **RES-01.C09** | Close with tasks in busy, local and incoming queues, including already-aborted nodes, stale readiness and suspended senders; pause any proposed cleanup cursor between queues/tasks. | Preserve required busy/local/incoming abort order, exactly-once stale-event cleanup and waiter release; never acknowledge reclamation with residual task ownership. Measure the whole nested cleanup path rather than only the outer turn budget. |
| **RES-01.C10** | Complete an async request while its port is live, closing/draining, dead or missing a ready callback; kill before native invocation and separately while it runs. | Reference queued/running invocation may continue; live/closing ready delivery or free-path ownership must settle once with code/PDL still retained. Do not turn suppressed delivery into stopped execution or allow admitted Bream process/helper work after `Down`. |
| **RES-01.C11** | Submit numbered requests with equal keys, colliding different keys and unkeyed routing; vary submitting scheduler while holding one completion consumer back. | Check required native invocation sequence separately from ready-callback sequence; do not assume equal-key completion FIFO across scheduler queues without evidence. Probe the source-permitted reordering candidate with controlled barriers. |
| **RES-01.C12** | Produce a ready burst with cheap and expensive callbacks/free functions, port-lock contention and dead recipients. | Every accepted completion retains one owner and settles once; a 20-callback cap is not a service-time bound. Measure publication contention, consumer progress and maximum uninterrupted callback/cleanup work. |
| **RES-01.C13** | Seal shutdown with queued jobs, one in-flight job, ready results and a closing resource awaiting completion; race attempted new admission. | No post-shutdown callback into released runtime state, no lost accepted record and no join completion claimed before native return. Keep VM `_exit` escape separate from safe embedded shutdown and preserve stop-before-`Down` for admitted process work. |

## 7. Four Rust-specific performance comparisons

All are **unmeasured hypotheses**. Use qualified helpers or an isolated ownership model first; none authorizes a native-job escape or a production port ABI. Global backlog IDs belong to the main plan.

| Local task | Baseline → treatment | Measure and reject |
|---|---|---|
| **PORT-P01 — Typed local resource requests** | Correct generic boxed callback/task records → private typed request variants in a single-worker owned queue, retaining explicit claimed/aborted/settled states and only necessary cancellation metadata. | Allocations, record size, cache misses, dispatch instructions and cancellation cost. Compare against ERTS's existing pooled task allocation, not an invented malloc-per-task baseline. Reject lost admission rollback, caller order or cleanup ownership. C07–C09. |
| **PORT-P02 — Ordering lanes without worker-key collisions** | One serial invocation queue per hashed key bucket → per-resource ordering lanes with runnable-lane scheduling, where one lane stays serial while unrelated lanes can use available workers. | Head-of-line delay, queue age, throughput under skewed keys, scheduling overhead and retained bytes. Reject concurrent execution within a required serial lane, changed side-effect order or unsupported cancellation. First model qualified work; arbitrary blocking native jobs remain conditional. C11/C13. |
| **PORT-P03 — Completion publication under bursts** | Thread-safe completion queue plus producer mutex, as in the reference → bounded producer batching or a sharded completion handoff with a deliberate consumer budget. | Producer CPU, enqueue contention, scheduler peer p99/max delay, ready latency, wakeups and retained results. Keep both cheap and expensive callbacks, locks and dead-recipient cleanup in the workload. Reject lost wakeups, reordered required effects or a treatment that merely moves unbounded work into one batch. C10–C12. |
| **PORT-P04 — Resumable ordered resource teardown** | Monolithic drain of busy/local/incoming request queues → runtime-owned cleanup cursor with explicit per-queue progress and retained waiter/accounting obligations. | Stop-to-reclamation tails, maximum uninterrupted cleanup, throughput, extra cursor bytes and resource retention. Reject early completion acknowledgment, duplicate abort/free, unreleased blocked senders or inner destructors that defeat the outer allowance. This is distinct from report50's successful system-request reply fanout: it handles ordered cancellation during resource teardown. C09/C13. |

## Evidence limits and next factual frontier

Read the task claim/admission and cleanup loops, principal async ownership path, key routing, ready service, shutdown integration, plus the upstream `ioq_exit`, `peek_non_existing_queue`, `otp_9302` and `async_blast` fixture sources. The flush fixture checks eventual `closed` and removal from `ports`; the blast fixture checks driver allocation return after completion. Neither is a universal latency proof, and neither was executed here. [Flush assertions][test-flush]; [blast assertions][test-blast].

Unclosed: complete driver-defined resource ownership, every process-to-port signal producer, all nosuspend/backpressure races, full thread-queue memory ordering, weak-memory runs, dynamic-driver unload interleavings, port-ID reuse bounds, OS backends, full halt/NIF interactions, measured queue contention and Rust implementation. In particular, same-key ready-callback reordering is an identified source inference for an executable probe, not an observed behavior claim.

No new preference question blocks these source facts. The existing unresolved choice about arbitrary host jobs remains unresolved; it should be revisited only with a concrete proposed lifetime/side-effect contract and evidence that the admitted process model stays useful. The nearest useful experiment is a controlled request-ownership/ordering harness at admission, claim, port invalidation and completion gates, followed by teardown-cost measurements. Merely building another pool of uninterruptible callbacks would not resolve the project's central execution-admission question.
