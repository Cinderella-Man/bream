# Rust's 2013 linked-task failure: delivery, cleanup, and unresolved boundaries

**2026-10-09. Primary-source audit; no historical compiler execution, speed tests, or performance measurements.** This is the earlier linked-failure branch of the green-thread investigation. It complements the history and final-2014 runtime reviews. Its central finding is that green threads did **not** mean arbitrary native instructions could safely be killed: Rust used cooperative scheduling, deferred failure delivery, protected regions, and runtime-aware I/O. Linked failure itself was removed a year before the final green-runtime extraction.

## Pinned evidence and scope

The inspected source is Rust commit [`85a1eff3a99c5d60bf34ca6f08f87ed341329af0`](https://github.com/rust-lang/rust/tree/85a1eff3a99c5d60bf34ca6f08f87ed341329af0), the direct parent of removal change [`acca9e3834842ee8d8104abe9b8b9bb88861793c`](https://github.com/rust-lang/rust/commit/acca9e3834842ee8d8104abe9b8b9bb88861793c). [PR #10603](https://github.com/rust-lang/rust/pull/10603) merged on **2013-11-25**, merge commit `6c1645a4ac5875bf2b7b5fe1cdca4531977d14b3`. The removal rationale names model complexity, implementation complexity and dwindling understanding, existing scheduler context-switch races, and uncertainty about mapping linked failure to native 1:1 threading. It proposes a more conservative future reimplementation, rather than claiming the problem cannot be solved.

[PR #7858](https://github.com/rust-lang/rust/pull/7858) records the earlier design discussion. Its reviewer distinguished semantic complexity, taskgroup bookkeeping, interruptible blocking/I/O, and runtime shutdown. In particular, the reviewer objected to separately configurable linked, supervised, and watched relationships and to a default shared taskgroup lock on spawn/exit. These are contemporaneous review concerns, **not measurements made here**. [Review comment](https://github.com/rust-lang/rust/pull/7858#issuecomment-21224028).

Read-only source and GitHub metadata snapshots are under ignored `upstream/rust-green-history/linked-failure-85a1eff3a99c5d60bf34ca6f08f87ed341329af0/`. `source-manifest.json` pins source URLs and SHA-256 digests; `metadata-manifest.json` does the same for the PR, issue, and comment responses. No historical tests were run. Old comments describe their authors' intentions; they are not a proof that the old unsafe implementation met them. In particular, the tutorial's blanket memory-isolation claims are not imported as guarantees of modern Rust or of this historical snapshot's entire unsafe library surface.

## The scheduler delivered failure at known boundaries

The tutorial explicitly describes green tasks scheduled **cooperatively** onto OS threads. It does not establish signal-driven preemption of arbitrary computation. The implementation agrees: the killer records pending state; the target begins unwinding at a scheduler return or a transition out of a protected region. A native function that does not reach those operations is not interrupted by this kill mechanism. [Tutorial](https://github.com/rust-lang/rust/blob/85a1eff3a99c5d60bf34ca6f08f87ed341329af0/doc/tutorial-tasks.md#L11-L18), [kill request](https://github.com/rust-lang/rust/blob/85a1eff3a99c5d60bf34ca6f08f87ed341329af0/src/libstd/rt/kill.rs#L425-L459), [delivery predicate](https://github.com/rust-lang/rust/blob/85a1eff3a99c5d60bf34ca6f08f87ed341329af0/src/libstd/rt/kill.rs#L630-L644).

The exact context-switch order matters. `change_task_context` moves scheduler/task ownership and swaps register contexts. When the old task resumes, it first runs the scheduler's pending cleanup job, then calls `death.check_killed(unwinder.unwinding)`. The failure is a normal `fail!` on that task's stack, not a foreign thread destroying its live stack. The check excludes already-unwinding tasks and tasks inside an unkillable region. [Switch and delivery order](https://github.com/rust-lang/rust/blob/85a1eff3a99c5d60bf34ca6f08f87ed341329af0/src/libstd/rt/sched.rs#L549-L627).

There were two **different** protected-region concepts:

| Mechanism | What it prevented | What it did not establish |
| --- | --- | --- |
| `unkillable` / `rekillable` | Deferred linked-failure unwinding while sensitive work was incomplete; pending kill could be delivered on entry/exit transitions | A completion bound for that work; freedom from explicit panic/failure |
| `atomically` / `wont_sleep` | Asserted that code holding a runtime native mutex did not deschedule | Cross-thread transactional atomicity, or automatic protection for arbitrary third-party locks |

`unkillable` was nestable and restored the mask through a `finally` guard. A masked task could still suspend and resume normally; it simply could not be woken early by linked failure. `LittleLock::lock` wrapped a native mutex with the no-deschedule counter and guaranteed unlock through `finally`. The scheduler explicitly checked this counter because switching away while holding a pthread mutex could deadlock the scheduler. [Mask implementation](https://github.com/rust-lang/rust/blob/85a1eff3a99c5d60bf34ca6f08f87ed341329af0/src/libstd/task/mod.rs#L593-L659), [nested mask and no-sleep counters](https://github.com/rust-lang/rust/blob/85a1eff3a99c5d60bf34ca6f08f87ed341329af0/src/libstd/rt/kill.rs#L646-L704), [mutex wrapper](https://github.com/rust-lang/rust/blob/85a1eff3a99c5d60bf34ca6f08f87ed341329af0/src/libstd/unstable/sync.rs#L299-L353), [scheduler check](https://github.com/rust-lang/rust/blob/85a1eff3a99c5d60bf34ca6f08f87ed341329af0/src/libstd/rt/sched.rs#L560-L567).

**Bream implication:** suspension safety and destruction safety should remain independent properties. It can be correct to yield while preserving an in-flight operation's storage but incorrect to unwind that storage. Conversely, switching away with some native locks held can itself be invalid. A single label such as “interruptible” hides these distinctions.

## Kill, block, and ordinary wake competed for one task

The `KillHandle` carried two atomics. The kill flag held `RUNNING`, `KILLED`, or the owning pointer to a blocked task. The separate unkillable flag controlled whether a kill request could steal that blocked pointer. A blocked communication primitive retained a refcounted flag handle instead of unconditionally owning the task forever. [State representation and intended arbitration](https://github.com/rust-lang/rust/blob/85a1eff3a99c5d60bf34ca6f08f87ed341329af0/src/libstd/rt/kill.rs#L24-L62), [fields](https://github.com/rust-lang/rust/blob/85a1eff3a99c5d60bf34ca6f08f87ed341329af0/src/libstd/rt/kill.rs#L168-L233).

The intended protocol was:

1. Blocking tries to replace `RUNNING` with the task pointer. If `KILLED` won first, it restores ownership and requeues the task instead of registering the blocked operation.
2. Ordinary wake exchanges the blocked pointer for `RUNNING`. A pointer means the caller won ownership; a sentinel means another wake or killer already won.
3. Kill first records the pending request in the mask flag. When allowed, it exchanges the kill flag for `KILLED`; a returned task pointer is scheduled to resume and unwind.
4. Multiple select registrations share the same flag, so only one can recover the owning pointer.

[Block and select paths](https://github.com/rust-lang/rust/blob/85a1eff3a99c5d60bf34ca6f08f87ed341329af0/src/libstd/rt/kill.rs#L262-L328), [kill path](https://github.com/rust-lang/rust/blob/85a1eff3a99c5d60bf34ca6f08f87ed341329af0/src/libstd/rt/kill.rs#L425-L446), [block registration order](https://github.com/rust-lang/rust/blob/85a1eff3a99c5d60bf34ca6f08f87ed341329af0/src/libstd/rt/sched.rs#L668-L700).

This is a reusable **protocol problem**, not an implementation to copy. [Issue #8863](https://github.com/rust-lang/rust/issues/8863) reports an abort at `task.unwinder.unwinding`, with platform-dependent reproducibility. The parent source has exactly that invariant in the blocked-task path: a missing spare flag is assumed to imply the task is already unwinding. PR #10603 cites existing context-switch races, but this audit does **not** establish a complete event-by-event root cause for that issue. [Assumption in source](https://github.com/rust-lang/rust/blob/85a1eff3a99c5d60bf34ca6f08f87ed341329af0/src/libstd/rt/kill.rs#L290-L301).

The right modern experiment is to enumerate kill/register/complete interleavings and assert one owner, at most one enqueue, no lost wake, and no stale registration retaining access to reclaimed storage. That is more informative than hoping a stress loop happens to reproduce a thirteen-year-old crash.

## The I/O boundary was unfinished, visibly in source

[Issue #8674](https://github.com/rust-lang/rust/issues/8674) explicitly says blocked I/O tasks could resume under linked failure without correct recovery. Its proposed immediate remedy was to make I/O blocking noninterruptible, then add interruptibility case by case. The inspected source shows both forms of defense:

**Filesystem calls defer kill.** `file::execute` wraps request creation, submission, waiting, and result collection in `task::unkillable`. The libuv request stores a pointer to a local blocked-task slot; its completion callback retrieves that pointer and resumes the task. The mask preserves the task frame until that callback has completed its part of the protocol. A pending linked failure can be delivered as the protected operation returns. This protects lifetime at the cost of deferred termination; it does not promise completion of arbitrary I/O. [Filesystem request lifetime](https://github.com/rust-lang/rust/blob/85a1eff3a99c5d60bf34ca6f08f87ed341329af0/src/librustuv/file.rs#L287-L329).

**Stream operations detect forbidden unwind rather than implement complete cancellation.** `StreamWatcher::read` places a `ReadContext` on the task stack, stores its address in the libuv handle, and contains the caller's buffer descriptor. The allocation and completion callbacks retrieve that context. The source comment says an unwind needs `uv_read_stop`; the shown path instead installs `ForbidUnwind`. The write path similarly installs a guard and comments on uncertain request ownership if unwinding occurs. [Read/write registration](https://github.com/rust-lang/rust/blob/85a1eff3a99c5d60bf34ca6f08f87ed341329af0/src/librustuv/stream.rs#L67-L132), [callbacks](https://github.com/rust-lang/rust/blob/85a1eff3a99c5d60bf34ca6f08f87ed341329af0/src/librustuv/stream.rs#L135-L179).

`ForbidUnwind` records whether the task was already failing and asserts on destruction if that changed. The generic callback wait also installs this guard. A newly initiated linked unwind through it can therefore raise a second failure; the runtime's unwind entry aborts if it is already unwinding. This is a source-level failure path, **not a historical crash reproduced by this audit**, and not proof that every stream operation necessarily reaches it. The guard is a defensive boundary, not successful per-task recovery. [Guard and wait](https://github.com/rust-lang/rust/blob/85a1eff3a99c5d60bf34ca6f08f87ed341329af0/src/librustuv/lib.rs#L179-L208), [double unwind abort](https://github.com/rust-lang/rust/blob/85a1eff3a99c5d60bf34ca6f08f87ed341329af0/src/libstd/rt/task.rs#L676-L694).

**Bream implication:** a safe-looking synchronous wrapper over asynchronous/native work needs its own cancellation protocol. Stopping the actor is not evidence that the operation stopped referencing its state. Alternatives include waiting for an acknowledged cancel/completion, transferring request and buffer ownership into a separate runtime record, or restricting cancellation while that operation is active. These are operation-level adapter choices; the history does not imply a permanent whole-crate allowlist.

## Taskgroup propagation and cleanup had distinct lifetimes

The relationship model had three axes: bidirectional linked failure, one-way supervised failure, and watched-child exit-status aggregation. The third was a wait/reporting policy, not just another kill edge. Group state held members and descendants; ancestor lists let supervised descendants enroll in every relevant ancestor group. The source states supervised spawn and exit traverse live ancestry. This is structural work observed in source, not elapsed-time evidence. [Relationship contract](https://github.com/rust-lang/rust/blob/85a1eff3a99c5d60bf34ca6f08f87ed341329af0/src/libstd/task/mod.rs#L140-L164), [group structure](https://github.com/rust-lang/rust/blob/85a1eff3a99c5d60bf34ca6f08f87ed341329af0/src/libstd/task/spawn.rs#L12-L36).

A failing task takes the group's state under its lock, marking it failed and preventing further successful enlistment. It then sends kill requests **outside** that lock using retained handles. Competing failures find the state already taken. Child setup enrolls in the group and ancestors before executing the user body, rolling back earlier enrollments if another group has failed. These are useful patterns for failure versus spawn races: closed publication state, a single propagation owner, and user-code execution only after relationship installation succeeds. [Group destruction](https://github.com/rust-lang/rust/blob/85a1eff3a99c5d60bf34ca6f08f87ed341329af0/src/libstd/task/spawn.rs#L322-L354), [propagation](https://github.com/rust-lang/rust/blob/85a1eff3a99c5d60bf34ca6f08f87ed341329af0/src/libstd/task/spawn.rs#L397-L442), [enlist and start](https://github.com/rust-lang/rust/blob/85a1eff3a99c5d60bf34ca6f08f87ed341329af0/src/libstd/task/spawn.rs#L539-L604).

Watched-child aggregation used reference-count ownership, blocking unwrap, and lazy closures called tombstones to carry descendants' outstanding obligations after an intermediate task had exited. The source itself identifies possible stack overflow from deeply nested tombstones and describes the complication of cleanup being outside the unwinder's catch and protected against kill. It also labels a non-atomic child-failure write a benign race. Those details are reasons to preserve the separation of concepts while replacing the old representation, not reasons to transplant the unsafe code. [Aggregation and explicit limitations](https://github.com/rust-lang/rust/blob/85a1eff3a99c5d60bf34ca6f08f87ed341329af0/src/libstd/rt/kill.rs#L65-L149), [failure write and tombstones](https://github.com/rust-lang/rust/blob/85a1eff3a99c5d60bf34ca6f08f87ed341329af0/src/libstd/rt/kill.rs#L461-L538).

Task execution and user cleanup ran inside a task-level unwinder catch. Cleanup destroyed task-local storage, remaining managed boxes, and output resources; the source explicitly notes that user destructors run. Only afterward did `collect_failure` protect group removal and exit-status collection against further kill delivery. Thus task termination included executing ordinary code and waiting for lifetime obligations, rather than atomically throwing away a native stack. [Task teardown order](https://github.com/rust-lang/rust/blob/85a1eff3a99c5d60bf34ca6f08f87ed341329af0/src/libstd/rt/task.rs#L285-L341), [protected failure collection](https://github.com/rust-lang/rust/blob/85a1eff3a99c5d60bf34ca6f08f87ed341329af0/src/libstd/rt/kill.rs#L568-L627).

## Experiments and design choices this suggests for Bream

These are proposed checks derived from the source, not results claimed by this audit:

1. **Borrowed I/O cancellation model.** Register an operation referencing actor-owned storage; request stop before completion; deliberately delay completion with a handshake. A premature-release model should reject the dangling obligation without accessing freed memory. Controls should either mask cancellation until acknowledgment or give the operation independent ownership and delay its physical-release receipt.
2. **Wake arbitration model.** Enumerate stop-before-register, register-before-stop, completion-before-stop, stop-before-completion, and duplicate completion. Verify one owning task/frame, at most one runnable publication, and eventual cleanup after the completion acknowledgment.
3. **Mask semantics model.** While a kill is deferred, prove that independent actors can still run and that the protected task cannot report complete cleanup prematurely. Then deliver the pending request exactly once when the protected operation relinquishes access. No elapsed-time target is needed for this correctness check.
4. **Spawn versus failing group.** Force failure before, during, and after relationship installation. A rejected child must never execute its body; a published child must have its failure/monitor relationship before its first user action. Bream's existing atomic spawn work already addresses a narrower version of this contract.
5. **Separate completion receipts.** Keep actor execution stopped, child-scope completed, native operation completed, and physical storage released as distinct observations. Rust's historical tombstones demonstrate a real need for longer-lived obligation records, while their recursive representation illustrates one design to avoid.

The evidence supports the project's distinction between native scheduling and disposal, but it makes “preemption was easy; killing was hard” a poor historical summary. The old runtime did not qualify arbitrary native preemption in the first place. It did attempt linked cancellation at controlled boundaries and encountered precisely the I/O lifetime, race, cleanup, and relationship-complexity issues relevant to Bream. Its removal is evidence of an unfinished and costly design, **not proof that a narrower, better-specified modern Rust runtime is impossible**.
