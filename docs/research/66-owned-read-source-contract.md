# Owned local reads: source contract for the next milestone

**2026-10-09. Source audit and implementation recommendation. No experiments, benchmarks or performance comparisons were executed for this report.** OTP baseline: **29.1.1**, commit `ad05823719d77c8faee87348ea39513d4e2f99c5`. Rust baseline: installed **1.98.1**, commit `48a229ceaefd4985c50990b14116b6d856af0985`. Source links below pin those commits; Linux manual links were checked on this date and are live documentation.

A bounded, runtime-owned nonblocking `UnixStream` read is a useful next step. A readiness driver can retain the endpoint, request buffer and completion identity independently of an actor. It can stop delivering to a dead actor without freeing storage still used by the driver. This directly addresses the lifetime problem identified in the [green-runtime investigation](63-rust-green-runtime-lessons-and-experiments.md). It does **not** establish cancellation of arbitrary native work or of a kernel-submitted asynchronous read.

Subsequent [implementation findings](67-owned-read-milestone.md) record the executed restricted profile and its limits separately from this source audit.

## Rust and Linux constraints

The concrete `UnixStream` implementation matters more than the general `Read` trait. At the pinned Rust revision, `UnixStream::read` delegates to the socket implementation, which passes a temporary buffer borrow to synchronous `recv`. `set_nonblocking` uses the OS socket setting. No detached kernel request keeps that Rust buffer after the syscall returns. This last statement is a source/API inference about this synchronous path, not a property of every `Read` implementation or asynchronous I/O backend. [Concrete read](https://github.com/rust-lang/rust/blob/48a229ceaefd4985c50990b14116b6d856af0985/library/std/src/os/unix/net/stream.rs#L610-L635), [socket syscall](https://github.com/rust-lang/rust/blob/48a229ceaefd4985c50990b14116b6d856af0985/library/std/src/sys/net/connection/socket/unix.rs#L289-L308), [nonblocking setting](https://github.com/rust-lang/rust/blob/48a229ceaefd4985c50990b14116b6d856af0985/library/std/src/sys/net/connection/socket/unix.rs#L594-L598).

The result contract should be explicit:

- A positive result transfers exactly that many initialized bytes, even if smaller than the requested capacity. Do not repeatedly read to fill a buffer inside one dispatch.
- A zero result means EOF for this stream only because admission rejects zero-capacity requests. A zero-length destination is otherwise an independent reason for zero.
- `WouldBlock` retains the same request for another readiness attempt. `Interrupted` is retryable, but a retry must return through driver control processing rather than form an unbounded inner loop.
- Other read errors settle the request once, with an explicit failed result. A finite public `Failed` variant may deliberately omit platform errno detail; record that loss of detail.

These are applications of the [pinned Rust read contract](https://github.com/rust-lang/rust/blob/48a229ceaefd4985c50990b14116b6d856af0985/library/std/src/io/mod.rs#L723-L777) and Linux's [receive behavior](https://man7.org/linux/man-pages/man2/recv.2.html), not a claim that EOF, peer reset and local cancellation are interchangeable.

`poll` supplies readiness and exceptional bits, not a completed read. It can report `POLLHUP` together with readable data; drain the operation's bounded read before interpreting EOF. `POLLNVAL` is a failed registration/ownership condition, not a reason to keep polling forever. `POLLERR` should drive a qualified read/error path. Nonblocking mode remains necessary because readiness can become stale. Keep each descriptor owner alive across the poll snapshot and subsequent dispatch; closing it from another thread is not the wakeup protocol. [poll contract](https://man7.org/linux/man-pages/man2/poll.2.html), [close concurrency](https://man7.org/linux/man-pages/man2/close.2.html).

Consuming a `UnixStream` transfers one handle. It cannot prove the host did not previously clone it: clones share the stream and options. The host must preserve the admitted endpoint's nonblocking setting and avoid competing reads through aliases. Keeping the opposite endpoint of `UnixStream::pair` to supply test data is a different case. [Pinned clone contract](https://github.com/rust-lang/rust/blob/48a229ceaefd4985c50990b14116b6d856af0985/library/std/src/os/unix/net/stream.rs#L176-L198), [pair](https://github.com/rust-lang/rust/blob/48a229ceaefd4985c50990b14116b6d856af0985/library/std/src/os/unix/net/stream.rs#L155-L175).

## Recommended bounded adapter and cancellation boundary

The proposed first profile uses one dedicated readiness thread, a wake socketpair, at most **16 admitted operations**, at most **4096 bytes per operation**, and one host-installed input consumed once per actor. These are proposed implementation limits, not limits derived from BEAM or measured capacity. A checked `read_input` can return `Data(ReadBytes)`, `Eof`, `Failed` or `Unavailable`. It need not admit arbitrary sockets, callbacks, futures, user-supplied `Read` implementations or foreign code.

Each operation should own its endpoint, initialized buffer, cancellation state, full recipient identity and unique request identity. Separate actor execution stopped, request claimed, syscall returned, result accepted/discarded and storage released. A private operation record, rather than an application future's borrowed local buffer, carries the lifetime. Admission accounting must include ready-but-unconsumed results as well as requests waiting for readiness; otherwise completion releases the cap while still retaining storage.

Cancellation before claim can prevent execution. Once the driver has claimed the record, cancellation requests abandonment and eventual disposal; it must not free the record while `read` borrows it. Even an atomic cancellation check immediately before the syscall leaves a check-to-read race. Accordingly **an already-claimed read may consume bytes after actor death, and those bytes may then be discarded**. That is an accepted external-operation boundary if documented, not rollback. It must never resume application code or route data to a replacement process. Exact process namespace/slot/generation and request identity must be validated as part of completion settlement, with duplicate settlement rejected.

A poll-based driver does not have an epoll interest list to deregister. It retires an entry from subsequent snapshots and keeps any current snapshot's endpoint owner alive until that poll call and use finish. A wake channel makes changed admission/cancellation/shutdown visible to a blocked poll. A full nonblocking wake socket may mean a wake is already pending; the queued control state remains authoritative. Race qualification must establish that no control update is stranded between draining wake bytes and taking the next snapshot. A later epoll backend would add persistent registration and cached-event obligations described in [report 42](42-linux-readiness-and-registration-lifetime.md); replacing poll is not just changing one syscall.

Shutdown should seal admission, cancel/dispose accepted records, wake the driver and join it from the host after scheduler work has stopped. Application stop must not synchronously join the driver or wait for its syscall. Joining proves the thread returned only after actual completion; it does not provide a latency bound. Nonblocking I/O prevents waiting for peer input but does not make allocation, locks, kernel execution or OS scheduling take bounded wall-clock time.

## Evidence required from implementation

Use controlled phases and event counts, not sleeps or elapsed-time assertions. Required cases are normal data, partial data, buffered data followed by peer closure, EOF, pending/no-data peer progress, defined read failure, missing input, admission exhaustion including unconsumed results, stop before registration, stop while claimed, completion before stop, stale/duplicate completion, process-slot reuse, and shutdown with pending and completed requests. A synthetic dispatch gate can qualify otherwise difficult orderings; label it separately from real socket behavior. Instrument exactly-once buffer/descriptor retirement and outstanding-operation accounting.

The useful Rust opportunity is an owned transfer into a private typed result instead of copying into an actor frame and maintaining a lifetime-erased native callback. OTP already reuses buffers and sometimes transfers a full binary, so a blanket “Rust avoids copying, BEAM copies” claim would be false. Its partial-buffer branch can shrink or allocate/copy depending on retained size. [BEAM buffer reuse/transfer/copy](https://github.com/erlang/otp/blob/ad05823719d77c8faee87348ea39513d4e2f99c5/erts/emulator/nifs/unix/unix_socket_syncio.c#L9820-L9871). Whether a fixed Rust buffer plus length improves memory use, allocations or service responsiveness remains unmeasured and requires a separately authorized environment.

This report approves the direction as a bounded design inference. It does not certify the implementation, a multi-worker protocol, general OS portability, borrowed asynchronous operations, arbitrary dependencies or a complete BEAM socket API. The historical native-callback issue is addressed by changing ownership; no claim that cancellation has become universally safe follows.
