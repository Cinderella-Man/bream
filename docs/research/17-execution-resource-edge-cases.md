# Execution and resource guarantees: remaining edge cases

Reviewed 2026-10-07 against Erlang/OTP `OTP-29.1.1`, commit `ad05823719d77c8faee87348ea39513d4e2f99c5`. **Exact behavior has not been established for every case.** The source establishes particular reference paths; upstream tests supply concrete regression scenarios; neither is an exhaustive specification or a proof of Bream. No tests were run for this audit. [Scheduling trace](11-beam-scheduling-source.md), [memory/native trace](14-beam-memory-native-io-source.md).

“Reference known” below means supported by the cited contract or inspected implementation. “Bream unproven” means a required safety or behavior qualification remains, not that the user should redesign an already clear BEAM rule. The first scope remains local process primitives and the accepted checked native-Rust investigation. Priority APIs, distribution, dirty jobs, additional VM services and OTP behaviours do not become milestone requirements merely because BEAM offers them.

## Scheduling: renewable work is not elapsed time

**Reference known.** BEAM's interpreter charges dispatch boundaries; its x86 JIT generates ingress checks. Both save a known continuation before returning to the scheduler. The normal reduction allowance is 4,000 in this checkout, but it is accounted work, not a CPU-instruction count or time deadline. Signal/system work can consume part of a turn before application code runs. [Interpreter checks](https://github.com/erlang/otp/blob/ad05823719d77c8faee87348ea39513d4e2f99c5/erts/emulator/beam/emu/macros.tab#L154-L232), [JIT checks](https://github.com/erlang/otp/blob/ad05823719d77c8faee87348ea39513d4e2f99c5/erts/emulator/beam/jit/x86/instr_common.cpp#L3201-L3250), [allowance](https://github.com/erlang/otp/blob/ad05823719d77c8faee87348ea39513d4e2f99c5/erts/emulator/beam/erl_vm.h#L49-L58), [signal accounting](https://github.com/erlang/otp/blob/ad05823719d77c8faee87348ea39513d4e2f99c5/erts/emulator/beam/erl_process.c#L10320-L10383).

Priority semantics qualify fairness: the reference describes round-robin scheduling within a priority, interleaved normal/low work, and preference for runnable high/max work. High-priority busy loops can prevent lower-priority selection. The contract warns against relying on today's exact policy and supplies no general priority-inheritance mechanism. The upstream `low_prio` test checks an approximate ratio with substantial tolerance, not an exact latency bound. [Priority contract](https://github.com/erlang/otp/blob/ad05823719d77c8faee87348ea39513d4e2f99c5/erts/preloaded/src/erlang.erl#L8198-L8256), [test](https://github.com/erlang/otp/blob/ad05823719d77c8faee87348ea39513d4e2f99c5/erts/emulator/test/process_SUITE.erl#L2138-L2182).

**Bream unproven.** The existing probe establishes forced suspension at each loop head for its closed grammar, not renewable budget accounting or exhaustive coverage of future admitted helpers. Qualify every execution cycle, long straight-line segment and transitive operation; verify repeated resumption preserves state; measure peer and control progress under sustained application and runtime work. Later workers add execution-ownership and queue races. Normal-priority single-worker qualification is sufficient initially; priority parity and global exact round-robin order are not implied. Measured worst latency remains an observation, not a universal bound.

## Runtime work: GC, copying and cleanup have different boundaries

**Reference known.** Potentially large GC can be moved to dirty system execution. That does not show every collection is interruptible. Binary copying can share reference-backed bytes while copying descriptors and updating ownership. Final deletion calls queue/off-heap cleanup and frees heaps; the inspected final loops do not expose a yielding continuation. [Large-GC decision](https://github.com/erlang/otp/blob/ad05823719d77c8faee87348ea39513d4e2f99c5/erts/emulator/beam/erl_gc.c#L688-L715), [binary-copy branch](https://github.com/erlang/otp/blob/ad05823719d77c8faee87348ea39513d4e2f99c5/erts/emulator/beam/copy.c#L812-L848), [final deletion](https://github.com/erlang/otp/blob/ad05823719d77c8faee87348ea39513d4e2f99c5/erts/emulator/beam/erl_process.c#L13393-L13482).

The [`binary_SUITE:trapping`](https://github.com/erlang/otp/blob/ad05823719d77c8faee87348ea39513d4e2f99c5/erts/emulator/test/binary_SUITE.erl#L1927-L1975) regression kills processes during resumable conversions, sometimes alongside GC. Its stated target is avoiding crashes, not proving all interruption boundaries or bounded cleanup. Likewise, timer cleanup's [yielding cancellation test](https://github.com/erlang/otp/blob/ad05823719d77c8faee87348ea39513d4e2f99c5/erts/emulator/test/timer_bif_SUITE.erl#L712-L730) waits for cleanup before comparing accounting.

**Bream unproven.** Membership collection growth, payload allocation/freezing, matching, copying, fanout and teardown need individual ownership and scheduling accounts. Charging cost after a helper returns cannot make that helper interruptible. Test kill at every resumable phase, including partially constructed values and ownership transfer, then verify exactly-once release and survivor progress. Exercise large nonmatching mailboxes and large final-reference releases. Incremental Bream teardown is a proposed qualification goal, not a discovered universal BEAM property. No tracing GC implementation is required merely to follow process ownership.

## Termination: stopping execution and reclaiming storage differ

**Reference known.** Dirty native work can outlive logical process death: resources and relationships can be handled while the native invocation continues, with some process storage retained. The upstream test receives `DOWN`/`EXIT`, finds the process absent, and still observes its binary reference until the NIF returns. [Native contract](https://github.com/erlang/otp/blob/ad05823719d77c8faee87348ea39513d4e2f99c5/erts/doc/references/erl_nif.md#L461-L489), [test](https://github.com/erlang/otp/blob/ad05823719d77c8faee87348ea39513d4e2f99c5/erts/emulator/test/dirty_nif_SUITE.erl#L247-L305). Native resource destructors are another callback boundary; auxiliary scheduling does not make arbitrary callback execution preemptible. [Destructor path](https://github.com/erlang/otp/blob/ad05823719d77c8faee87348ea39513d4e2f99c5/erts/emulator/beam/erl_nif.c#L2961-L3029).

**Bream unproven.** Accepted [ADR 0009](../adr/0009-death-and-reclamation-observation.md) makes `Down` stronger than that dirty-NIF exception: application execution has stopped and the incarnation is no longer addressable, while tracked reclamation may follow. This is a recorded Rust conflict resolution, not unqualified BEAM equivalence. Prove no poll/continuation can resume after that observation, no active execution is dropped concurrently, and no stale wakeup accesses freed or reused state. Separately prove shared immutable bytes survive a publisher's death and are physically freed only after their final owner releases them. Notification correctness alone proves none of these properties.

Native dependencies cannot silently enter the guaranteed process subset. Reduction charging does not interrupt a running native function; dirty execution is explicitly a separate contract. Offloading an infinite Rust call protects some worker capacity but supplies no forced-stop proof. Approved helper dependencies need transitive qualification; any future escape facility needs a distinct guarantee. [Native charging](https://github.com/erlang/otp/blob/ad05823719d77c8faee87348ea39513d4e2f99c5/erts/emulator/beam/erl_nif.c#L3341-L3359).

## Capacity failures: three different reference cases

**Reference known.** Process-table exhaustion, a configured process heap limit and host allocation failure are not interchangeable:

- Process creation has a `SYSTEM_LIMIT` path when allocating a process slot fails. [`erl_create_process` path](https://github.com/erlang/otp/blob/ad05823719d77c8faee87348ea39513d4e2f99c5/erts/emulator/beam/erl_process.c#L12524-L12540). [`iter_max_procs`](https://github.com/erlang/otp/blob/ad05823719d77c8faee87348ea39513d4e2f99c5/erts/emulator/test/node_container_SUITE.erl#L909-L965) tests repeated exhaustion and release with a small process limit.
- `max_heap_size` is checked when GC is triggered; zero disables it. Accounting and shared-binary inclusion are defined explicitly, and killing can be disabled. This is not an instantaneous cap on every physical byte associated with a process. [Contract](https://github.com/erlang/otp/blob/ad05823719d77c8faee87348ea39513d4e2f99c5/erts/preloaded/src/erlang.erl#L8105-L8167), [kill/no-kill test](https://github.com/erlang/otp/blob/ad05823719d77c8faee87348ea39513d4e2f99c5/erts/emulator/test/process_SUITE.erl#L3264-L3306).
- Ordinary ERTS allocation helpers terminate the emulator if memory cannot be obtained; `_fnf` variants return null. Process isolation therefore does not imply universal recoverable OOM. [Allocator contract](https://github.com/erlang/otp/blob/ad05823719d77c8faee87348ea39513d4e2f99c5/erts/emulator/beam/erl_alloc.h#L199-L215).

**Bream unproven.** Specify and fault-inject failures during spawn, queue growth, payload construction, monitor registration and cleanup bookkeeping. Define which failures are representable without another allocation and verify partial construction leaves no published orphan or leaked ownership. The accepted growing-mailbox rule removes waiting for consumption/capacity; it does not promise infinite memory or recoverable host exhaustion. Process quotas are not silently added. Rust's default standard-library allocation-error handler can abort the host; `catch_unwind` is not an OOM-isolation strategy. [Rust allocation contract](https://doc.rust-lang.org/std/alloc/fn.handle_alloc_error.html), reviewed 2026-10-07.

## Rust-specific panic and runtime shutdown gaps

BEAM source cannot supply a complete embedding contract for dropping a Rust runtime, unwinding across an admitted helper, host panic hooks, or a worker panicking while owning scheduler state. `catch_unwind` catches unwinding panics rather than aborts; hooks run before the catch, and dropping a panic payload can itself panic. [Rust panic contract](https://doc.rust-lang.org/std/panic/fn.catch_unwind.html), reviewed 2026-10-07.

Required local qualifications include: a helper panics after partial mutation; cleanup encounters failure; runtime shutdown races spawn/send/kill; external addresses outlive the runtime; delayed wakeups arrive after scheduler teardown; and shutdown encounters pending reclamation. Define ownership and observable outcomes without claiming rollback of external effects. The [current probe](../../experiments/generated-process/README.md) explicitly lacks panic containment and a public admission boundary. Its ten negative compilation fixtures and one tracked buffer drop do not establish these broader properties. These are Rust integration gaps, not missing GenServer or supervisor behavior.

## Three strongest risks of false completeness

1. **“The loop yields automatically, therefore every admitted process is preemptible.”** This omits uninstrumented callees, expensive runtime operations and the public admission boundary.
2. **“Kill produced `Down`, therefore termination is safe and complete.”** This conflates execution ownership, address removal, native work, shared ownership and final reclamation.
3. **“It has BEAM-owned processes and growing mailboxes, therefore failures stay inside one process.”** This omits capacity exhaustion, allocator failure, panic/abort behavior and runtime teardown.

Close these gaps with bounded invariants, explicit failure traces and reproducible experiments for the admitted initial surface. Do not claim every BEAM edge case, every Rust program, or an elapsed-time guarantee from a finite source review or test suite.
