# BEAM mailboxes, signals and selective receive: source review

Inspected 2026-10-07 at Erlang/OTP **OTP-29.1.1**, commit `ad05823719d77c8faee87348ea39513d4e2f99c5`. Local checkout: `/home/bat/projects/bream/upstream/otp`, clean at inspection. This is a source audit, not a built-runtime test or a proof of all ERTS interleavings.

Bream's accepted direction is typed protocols, a growing ordinary mailbox, selective receive with timeout, BEAM-style exits/trapping, and a raw room/session fixture. The central lesson is that **mailbox consumption, runtime signal handling and process scheduling are three separate operations**. A typed channel alone does not supply these semantics.

## Scope and source map

The traced path is ordinary local process-to-process messaging with ordinary mailbox priority. It follows C runtime functions, interpreter instruction templates and the x86 JIT equivalents. Optional sender buffers, priority messages and distribution are identified where they change the path; their full correctness is outside this review. ## 1. The mailbox is one stage of a signal pipeline

`Process.sig_inq` is incoming transport. `sig_qs.cont` is the receiver-private middle queue, mixing ordinary messages and runtime signals. `sig_qs.first` is the inner application mailbox; `sig_qs.save` points to the current selective-receive position. The header explicitly distinguishes still-in-transit signals from messages already received. It also warns against treating internal accounting fields as a public queue-length snapshot. [Queue representation](https://github.com/erlang/otp/blob/ad05823719d77c8faee87348ea39513d4e2f99c5/erts/emulator/beam/erl_message.h#L337-L405).

```text
sender → incoming signal queue/buffers
                   ↓ fetch under queue ownership rules
           receiver-private middle queue
                   ↓ runtime handles control signals
           inner application mailbox
                   ↓ selective receive cursor
           selected owned application value
```

`erts_proc_sig_fetch` requires both MAIN and MSGQ locks. `erts_proc_sig_fetch__` can append a message-only incoming batch directly to the inner mailbox if no middle queue/tracing prevents it; otherwise it preserves a middle-stage sequence. The handler moves the eligible prefix to the inner queue. This avoids making application matching responsible for link, monitor, exit or other runtime operations. [Fetch contract](https://github.com/erlang/otp/blob/ad05823719d77c8faee87348ea39513d4e2f99c5/erts/emulator/beam/erl_proc_sig_queue.h#L1996-L2027), [fetch implementation](https://github.com/erlang/otp/blob/ad05823719d77c8faee87348ea39513d4e2f99c5/erts/emulator/beam/erl_proc_sig_queue.c#L1365-L1433), [prefix transfer](https://github.com/erlang/otp/blob/ad05823719d77c8faee87348ea39513d4e2f99c5/erts/emulator/beam/erl_proc_sig_queue.c#L7038-L7104).

**Borrow:** define separate internal signal and public inbox representations, and explicit ownership transitions. **Do not copy blindly:** Bream does not need ERTS's exact three linked lists, tracing offsets or queue-buffer heuristics to implement the same externally visible rules. A simpler state machine may be easier to qualify first.

## 2. Ordinary local send: ownership before publication

`do_send` resolves a local PID; the ordinary path calls `erts_send_message`. A nonexistent local PID returns through the ordinary success path. This is not a receiver acknowledgement. `erts_send_message` calculates term size and copies non-immediate data into storage allocated for the message/receiver, except for its self-send optimization. `erts_alloc_message_heap_state` honors off-heap mailbox mode; otherwise `erts_try_alloc_message_on_heap` tries the receiver's MAIN lock and usable heap, falling back to a message fragment. It does not wait for the receiver to execute `receive`. [PID dispatch](https://github.com/erlang/otp/blob/ad05823719d77c8faee87348ea39513d4e2f99c5/erts/emulator/beam/bif.c#L2469-L2480), [send call](https://github.com/erlang/otp/blob/ad05823719d77c8faee87348ea39513d4e2f99c5/erts/emulator/beam/bif.c#L2676-L2686), [copy path](https://github.com/erlang/otp/blob/ad05823719d77c8faee87348ea39513d4e2f99c5/erts/emulator/beam/erl_message.c#L821-L886), [allocation selection](https://github.com/erlang/otp/blob/ad05823719d77c8faee87348ea39513d4e2f99c5/erts/emulator/beam/erl_process.h#L2878-L2897), [heap attempt/fallback](https://github.com/erlang/otp/blob/ad05823719d77c8faee87348ea39513d4e2f99c5/erts/emulator/beam/erl_message.c#L622-L690).

`queue_messages` publishes under MSGQ unless a buffer path succeeds, rechecks exiting state, disposes messages for a receiver already exiting, and notifies scheduling after publication. It also flushes relevant buffered traffic to preserve ordering when paths change. This send is asynchronous with respect to consumption, not necessarily lock-free, allocation-free or constant-time. Copy work is charged reductions after the copy; this source does not establish a hard bound on one large copy's uninterrupted duration. [Publication and exit race](https://github.com/erlang/otp/blob/ad05823719d77c8faee87348ea39513d4e2f99c5/erts/emulator/beam/erl_message.c#L397-L459), [copy accounting](https://github.com/erlang/otp/blob/ad05823719d77c8faee87348ea39513d4e2f99c5/erts/emulator/beam/erl_message.c#L881-L886).

For Bream, moving an admitted Rust payload may replace BEAM's term copy. The invariant is one accountable owner across sender, in-flight operation, queue and receiver. A successful send must not be described as consumption or durable processing. Sender death after ownership transfer must not reclaim receiver-owned bytes. Receiver death must reclaim queued payloads through their approved cleanup contract. The safe-kill boundary includes queue nodes and in-flight native operations, not only the generated function's locals.

## 3. Ordering survives multiple physical paths

The language guarantee is per sender and destination, not a universal order between concurrent senders. Sender-buffer hashing in `erts_proc_sig_queue_try_enqueue_to_buffer` deliberately maps a sender to one slot. The same machinery handles control signals and ordinary messages; `prepend_pending_sig_maybe` places a scheduler-held pending signal before a later message. These are reminders that two independent queues can accidentally reorder a message and a subsequent exit. [Buffered path](https://github.com/erlang/otp/blob/ad05823719d77c8faee87348ea39513d4e2f99c5/erts/emulator/beam/erl_proc_sig_queue.c#L10260-L10306) · [local](/home/bat/projects/bream/upstream/otp/erts/emulator/beam/erl_proc_sig_queue.c:10260), [pending-signal prepend](https://github.com/erlang/otp/blob/ad05823719d77c8faee87348ea39513d4e2f99c5/erts/emulator/beam/erl_message.c#L462-L479), [language ordering contract](https://www.erlang.org/doc/system/ref_man_processes.html#delivery-of-signals).

The upstream `xm_sig_order` test sends ordinary messages, then an abnormal exit, then more messages; consuming the latter causes test failure. Messages before the exit may or may not be consumed. Bream should port this observable scenario, not infer that kill must wait for every earlier message handler. [Signal ordering test](https://github.com/erlang/otp/blob/ad05823719d77c8faee87348ea39513d4e2f99c5/erts/emulator/test/signal_SUITE.erl#L155-L185) · [local](/home/bat/projects/bream/upstream/otp/erts/emulator/test/signal_SUITE.erl:155).

## 4. Runtime housekeeping consumes scheduling work

`erts_proc_sig_handle_incoming` has preferred and maximum reduction allowances. Its accounting weights signal operations; one reduction is not necessarily one signal. It may stretch the preferred allowance to make messages available, but checks the consumed work after operations and rounds the returned accounting, so the nominal maximum is not an exact upper bound on performed work. The receive helper charges fetch/handling work and returns one of three reasons when no message is available: wait, reschedule, or exit. In a release build it may choose at least the preferred handling amount, so these constants are not hard wall-clock deadlines. [Handler interface](https://github.com/erlang/otp/blob/ad05823719d77c8faee87348ea39513d4e2f99c5/erts/emulator/beam/erl_proc_sig_queue.h#L1203-L1256), [accounting and stretch](https://github.com/erlang/otp/blob/ad05823719d77c8faee87348ea39513d4e2f99c5/erts/emulator/beam/erl_proc_sig_queue.c#L7160-L7255), [receive helper](https://github.com/erlang/otp/blob/ad05823719d77c8faee87348ea39513d4e2f99c5/erts/emulator/beam/erl_proc_sig_queue.c#L7765-L7868) · [local](/home/bat/projects/bream/upstream/otp/erts/emulator/beam/erl_proc_sig_queue.c:7765).

Bream should budget scans, notification conversion and bulk queue cleanup as well as user loops. Otherwise the runtime itself becomes the hog that automatic user checkpoints were meant to contain. Start with a simple measurable work budget and separate latency measurements; do not import ERTS constants as Rust performance guarantees.

## 5. Selective receive preserves a cursor, not a second user-visible queue

`erts_msgq_peek_msg` reads through `save`. A failed match calls `erts_msgq_set_save_next`; the interpreter's `loop_rec_end` spends a reduction. `i_loop_rec` reschedules when reductions run out, retaining the receive position. The x86 JIT follows the same structure and decrement. It calls the shared receive helper when the private scan reaches its end. Unmatched messages remain linked in the mailbox. [Cursor helpers](https://github.com/erlang/otp/blob/ad05823719d77c8faee87348ea39513d4e2f99c5/erts/emulator/beam/erl_proc_sig_queue.h#L2301-L2394), [interpreter scheduling point](https://github.com/erlang/otp/blob/ad05823719d77c8faee87348ea39513d4e2f99c5/erts/emulator/beam/emu/msg_instrs.tab#L44-L112), [failed match](https://github.com/erlang/otp/blob/ad05823719d77c8faee87348ea39513d4e2f99c5/erts/emulator/beam/emu/msg_instrs.tab#L249-L261), [x86 equivalent](https://github.com/erlang/otp/blob/ad05823719d77c8faee87348ea39513d4e2f99c5/erts/emulator/beam/jit/x86/instr_msg.cpp#L268-L277).

Once selected, `remove_message` unlinks that message, resets the scan for the next receive, cancels the receive timer, and adopts the message data into process-owned storage. Timeout also resets the scan. Within one pending receive, a wakeup should continue past already rejected ordinary messages; the next receive must reconsider them under its new clauses. [Selection](https://github.com/erlang/otp/blob/ad05823719d77c8faee87348ea39513d4e2f99c5/erts/emulator/beam/emu/msg_instrs.tab#L227-L242), [timeout reset](https://github.com/erlang/otp/blob/ad05823719d77c8faee87348ea39513d4e2f99c5/erts/emulator/beam/emu/msg_instrs.tab#L264-L283).

The BEAM implementation temporarily delays GC during matching because some message data is outside the process heap. That is a VM-specific rooting requirement, not a suggested Rust `unsafe` shortcut. For Bream, matching should borrow approved payloads without moving or dropping unmatched messages. An arbitrary Rust `Fn(&M) -> bool` can loop, allocate, call dependencies or mutate external state; checking the scan loop alone would not satisfy mandatory preemption. Generated patterns and approved guards are the first credible experiment.

## 6. Waiting and timeout are part of the same race protocol

After finding no further message, `erts_proc_sig_receive_helper` returns holding the queue lock. The wait instruction clears ACTIVE unless already timed out, releases receive locks, and schedules out. Publication then arranges wakeup. Even the buffered enqueue path explicitly synchronizes with MSGQ before notifying when it creates the first nonempty buffer, preventing the producer's wakeup from being overwritten by the consumer's sleep transition. [Empty-scan handoff](https://github.com/erlang/otp/blob/ad05823719d77c8faee87348ea39513d4e2f99c5/erts/emulator/beam/erl_proc_sig_queue.c#L7739-L7798), [wait](https://github.com/erlang/otp/blob/ad05823719d77c8faee87348ea39513d4e2f99c5/erts/emulator/beam/emu/msg_instrs.tab#L371-L383), [buffered lost-wakeup prevention](https://github.com/erlang/otp/blob/ad05823719d77c8faee87348ea39513d4e2f99c5/erts/emulator/beam/erl_proc_sig_queue.c#L10381-L10418) · [local](/home/bat/projects/bream/upstream/otp/erts/emulator/beam/erl_proc_sig_queue.c:10381).

Timeout setup occurs on reaching the wait path, and its flags prevent rearming the timer after each unmatched wakeup. A zero timeout still follows message selection; it is not a constant-time queue-emptiness test. The initial scan can consume multiple turns before that path is reached. On expiry, the timer resumes the timeout continuation; it is not an ordinary message that must be matched from the mailbox. Exact timer firing internals and every tie interleaving belong to the companion timer review. [Interpreter timer setup](https://github.com/erlang/otp/blob/ad05823719d77c8faee87348ea39513d4e2f99c5/erts/emulator/beam/emu/msg_instrs.tab#L317-L368), [JIT timeout helper](https://github.com/erlang/otp/blob/ad05823719d77c8faee87348ea39513d4e2f99c5/erts/emulator/beam/jit/beam_jit_common.cpp#L1208-L1255).

Borrow the atomic relationship between scan exhaustion, wait registration, publish, timeout and kill. Rust atomics or a lock-based implementation may realize it differently, but a `check_empty(); register_waker();` design needs a recheck/handshake or it can sleep forever with a matching message already queued.

## 7. Receive markers are a compiler-proved optimization

The compiler can prove that a fresh reference could not occur in old messages, reserve a mailbox position, bind it to the reference and begin a later receive there. Reserving **before** reference/monitor creation matters: an immediate `DOWN` could otherwise arrive before the marker and be skipped. Missing/retired markers degrade to ordinary search, preserving semantics. [Compiler rationale](https://github.com/erlang/otp/blob/ad05823719d77c8faee87348ea39513d4e2f99c5/lib/compiler/src/beam_ssa_recv.erl#L27-L80).

Runtime marker insertion accounts for markers still in the middle queue; the save position can take effect only when the marker enters the application mailbox. Markers are not ordinary messages or a promise that an arbitrary user-provided ID is fresh. [Insertion](https://github.com/erlang/otp/blob/ad05823719d77c8faee87348ea39513d4e2f99c5/erts/emulator/beam/erl_proc_sig_queue.c#L4289-L4385), [marker API](https://github.com/erlang/otp/blob/ad05823719d77c8faee87348ea39513d4e2f99c5/erts/emulator/beam/erl_proc_sig_queue.h#L1653-L1730).

Bream should first qualify linear search with a resumable cursor. Add marker optimization only for runtime-created correlation tokens whose freshness and matching use are enforceable. A typed integer alone is not that proof.

## 8. Typed payloads must coexist with runtime notifications

Exit handling either acts on the process or converts an eligible trapped exit into a mailbox message. Monitor-down handling similarly converts an active monitor's signal. Ordinary conversion preserves its place among the signal stream; priority insertion is a separate branch. Thus a typed application protocol cannot replace runtime signaling. [Exit conversion](https://github.com/erlang/otp/blob/ad05823719d77c8faee87348ea39513d4e2f99c5/erts/emulator/beam/erl_proc_sig_queue.c#L4738-L4782), [down conversion](https://github.com/erlang/otp/blob/ad05823719d77c8faee87348ea39513d4e2f99c5/erts/emulator/beam/erl_proc_sig_queue.c#L4817-L4834), [active monitor check](https://github.com/erlang/otp/blob/ad05823719d77c8faee87348ea39513d4e2f99c5/erts/emulator/beam/erl_proc_sig_queue.c#L6355-L6378).

Q18 accepted a runtime-owned envelope, illustratively `InboxItem<M>` containing `Message(M)`, `Exit(...)` and `Down(...)`, all eligible for one selective receive. The shape is accepted; these exact names and signatures remain illustrative. Internal untrappable kill remains a runtime action and must not wait for the application to select a notification. Separate convenience methods may be possible, but implementing them as unrelated public queues would change cross-kind ordering and selection. [ADR 0007](../adr/0007-unified-runtime-envelope.md).

Priority messages, available in current ERTS, can be inserted ahead of ordinary messages while preserving signal delivery order. Distribution additionally has encoding, lazy decode and transport flow control. Neither belongs in the first ordinary local mailbox experiment merely because it exists below OTP behaviors. [Priority insertion](https://github.com/erlang/otp/blob/ad05823719d77c8faee87348ea39513d4e2f99c5/erts/emulator/beam/erl_proc_sig_queue.c#L9300-L9318), [external-message receive branch](https://github.com/erlang/otp/blob/ad05823719d77c8faee87348ea39513d4e2f99c5/erts/emulator/beam/emu/msg_instrs.tab#L119-L134), [documented priority distinction](https://www.erlang.org/doc/system/ref_man_processes.html#adding-messages-to-the-message-queue).

## Falsifiable next experiments

| Experiment | Required observation |
|---|---|
| Long unmatched prefix, target at tail | Scan spans multiple turns while an unrelated heartbeat advances. Instrument inspections: resumption continues rather than rescanning the prefix each turn. Every unmatched message remains available in original order for a later receive. |
| New messages during a pending selection | Already rejected messages are not repeatedly re-evaluated within the same receive. Newly appended matches wake and complete it. Selection/timeout reset permits the next receive to find an old message. |
| Sleep/publication handshake | Deterministically pause immediately before and after wait registration and publication. In every interleaving, either the message is selected or a wakeup remains pending; never asleep with eligible work and no future event. |
| Message/exit ordering | Port `xm_sig_order` locally with normal typed messages. Repeat with trap-exit enabled to check notification placement; with trap-exit disabled, later messages must not execute after the exit takes effect. |
| Timeout without sliding extension | Repeated unmatched sends cannot continually rearm a timeout. Test zero timeout on a large queue, match versus expiry, next-receive cursor reset and stale timeout events from the previous receive. |
| Kill during send, scan and queue cleanup | Race ownership transitions and stop at each phase. Count every tracked payload/node exactly once. Large abandoned queues must not monopolize a worker during reclamation. |
| Raw room/session | One room selectively handles typed join/chat/leave/query and runtime `Down`; queries carry fresh references. A hogging session remains killable; room and peer sessions progress. No GenServer, supervisor or implicit restart. |
| Optional marker optimization | Compare optimized and unoptimized traces over an old-message prefix. Include immediate monitored death, retired markers and multiple references. Only inspection counts may differ, not selected messages or lifecycle results. |

Upstream receive tests include huge queues, nested/recursive receives, marker clearing and stale-save regressions. They are useful scenario sources, but were not executed here. ## Questions worth settling before API design

Interview update: Q18 accepted the runtime envelope. Q21 subsequently instructed BEAM-compatible observable defaults, resolving ordinary dead-PID send and receive-timeout behavior in favor of the reference semantics. The alternatives below record the research rationale, not additional pending user questions.

1. **Matching surface:** May the first receive admit enum patterns and approved bounded guards while rejecting arbitrary predicate closures? Recommended: yes; otherwise one predicate can defeat scan fairness and killability.
2. **Runtime notifications:** Should typed payloads, trapped exits and monitor-down notifications share one typed receive envelope? Recommended: yes, preserving their combined mailbox order while keeping internal control signals inaccessible as user messages.
3. **Sending to a dead PID:** Should the normal fire-and-forget send silently dispose of the moved payload, like the local BEAM PID path, or return a distinct failure with ownership? Recommended for the stated familiarity goal: ordinary send should not masquerade as a delivery acknowledgement; any checked variant must state precisely what it checks and its race limits.
4. **Timeout meaning:** Should receive retain BEAM-style scan/wait behavior, or should an additional deadline API count initial scan time too? Recommended: preserve the familiar receive contract first and name a stricter deadline separately if useful. Neither implies a hard wall-clock scheduling guarantee.

Unqualified areas include complete memory reclamation under every signal combination, all compiler guard lowering, ARM JIT, priority-marker interleavings, distribution, dirty native execution and allocator latency. No production Bream queue algorithm, public enum or timer deadline contract is approved by this report.
