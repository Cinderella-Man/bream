# Persistent local reads: source contract

**2026-10-09. Source audit and design recommendation. No experiments, benchmarks or performance comparisons ran for this report.** OTP baseline: **29.1.1**, clean checkout at `ad05823719d77c8faee87348ea39513d4e2f99c5`. Rust baseline: **1.98.1**, `48a229ceaefd4985c50990b14116b6d856af0985`. Source links pin those commits; Linux manuals are live documentation checked on this date.

Subsequent implementation status: [milestone 15 passed](69-persistent-read-milestone.md). The proposals below retain their source-audit status; that report distinguishes executed controls from remaining limitations.

The [previous milestone](67-owned-read-milestone.md) separates actor lifetime from one read operation's storage lifetime. Persistence adds a third lifetime: the endpoint can outlive many successive operations while remaining owned by one actor. A process identity cannot distinguish two requests made by that same live process. This milestone should therefore qualify endpoint ownership, request identity and actor identity separately.

The Erlang wrapper confirms that a receive with a positive length and timeout can accumulate data until that length is reached. Its `select_read` option can even initiate another asynchronous receive when the previous operation completes. Bream's proposed contract is smaller: no automatic next read and no read-exactly loop. The next checked invocation admits the next request. [Public receive contract](https://github.com/erlang/otp/blob/ad05823719d77c8faee87348ea39513d4e2f99c5/lib/kernel/src/socket.erl#L5906-L5991).

Cancellation also has a notification side. `socket:cancel` calls the primitive and flushes select, completion and abort messages using the particular socket/reference pair. An obsolete operation handle is invalid rather than a request to cancel whichever operation happens to be active. [Public cancellation and flushing](https://github.com/erlang/otp/blob/ad05823719d77c8faee87348ea39513d4e2f99c5/lib/kernel/src/socket.erl#L7973-L8082). Bream need not reproduce those messages, but stale readiness must only trigger re-evaluation of current state; it cannot authorize acceptance of an old result as a new operation's result.

## Proposed Rust state and ownership rules

This is a design inference from the sources, not a claim about an implementation already qualified.

The proposed separate persistent-read profile keeps the preceding one-shot profile intact. Its checked `read_next` operation can return `Data(StreamBytes)`, `Eof`, `Failed`, `Unavailable` or `Busy`; `Busy` means the endpoint still has an outstanding request. Use a runtime-owned endpoint record with one owner PID, fixed read size, terminal state and at most one current request. Each request owns a separately identified operation and buffer. A private `Arc` operation can provide identity while an old holder retains that allocation; a numeric identity instead needs non-reuse and overflow handling. Do not replace exact identity with an FD number, table index, boolean pending flag or the owner's PID.

The state transitions should enforce the following:

- **Idle → Pending:** check live owner, open endpoint and admission under the relevant synchronization; allocate a fresh request identity. Merely retaining an endpoint should not initiate a read.
- **Pending → Running:** take owned request storage before releasing locks. Attempt at most one nonblocking read before returning through driver control processing.
- **Running → Ready(Data):** preserve the endpoint and publish only to the matching current request. The positive result completes that request regardless of buffer fullness.
- **Ready → Idle:** consume or discard that exact result and retire its request. A subsequent read gets a new identity. An old future's destructor must neither cancel nor clear the new request.
- **EOF/failure → terminal endpoint:** report the current result once, close admission for later requests and retire endpoint ownership safely. Cache the EOF/failure result so later reads can return it without allocating another request. This deliberately excludes stream half-close and retained write-half behavior.
- **Actor stop/shutdown:** seal endpoint admission, cancel the current request if any, retire the idle endpoint too, and prevent completion from resuming the actor or reaching its replacement.

**Cancellation requested is not cancellation completed.** If a request is already running, do not let another request read the same endpoint until the old syscall has returned and settled. Otherwise the supposedly cancelled read can consume input intended for the newer request. The actor worker need not wait: the endpoint can stay busy while the driver finishes. An old cancellation issued after retirement must be harmless to the newer request.

A cancelled request that passed its final cancellation check may still consume bytes and discard them. Retaining the endpoint does not restore those bytes or make cancellation transactional. The backend remains synchronous nonblocking `recv`: unlike a submitted asynchronous kernel operation, it does not retain the buffer borrow after syscall return. The concrete Rust path and its limitation were traced in [report 66](66-owned-read-source-contract.md#rust-and-linux-constraints). Linux permits a positive result shorter than requested and zero for orderly stream shutdown; request admission must still reject zero-sized destination buffers. [Receive contract](https://man7.org/linux/man-pages/man2/recv.2.html).

## Descriptor lifetime, admission and the Rust opportunity

A `pollfd` integer does not own the descriptor. A snapshot must retain its endpoint owners until `poll` and any associated dispatch finish, even if another thread removes the actor's endpoint meanwhile. An `Arc<Endpoint>` snapshot is one possible Rust implementation. Retaining the endpoint record also suffices if only the sole driver may actually close or move its descriptor, while other threads can only request retirement. Actor stop retires ownership and wakes the control channel; it must not forcibly close the raw descriptor under an in-flight snapshot. Linux warns about cross-thread descriptor closure and reuse. [Close concurrency](https://man7.org/linux/man-pages/man2/close.2.html).

A readiness event is not a read result. Keep nonblocking mode; handle stale readiness by attempting the current qualified request, not blocking. `POLLHUP` can accompany unread bytes: sequential reads must deliver those bytes before reporting EOF. `POLLNVAL` is an ownership/registration failure, not a reason to poll forever. Idle endpoints need no read interest. [Poll contract](https://man7.org/linux/man-pages/man2/poll.2.html).

OTP's corresponding resource rule is explicit: cancellation may lose to an already-sent notification, whereas `ERL_NIF_SELECT_STOP` establishes when closing the event is safe. The event/resource association retains the resource until the stop callback returns. Bream's poll snapshot has a different implementation but must uphold the same separation between suppressing delivery and safe resource destruction. [Pinned NIF contract](https://github.com/erlang/otp/blob/ad05823719d77c8faee87348ea39513d4e2f99c5/erts/doc/references/erl_nif.md#L3566-L3617).

Persistent endpoints require a bound even while idle. Retaining the previous sixteen-slot limit for endpoints, with one operation per endpoint and at most 4096 bytes per request, is a defensible initial policy. Count ready-but-unconsumed requests too. Delivered `ReadBytes` values can accumulate in actor-owned storage, so this is not a whole-runtime memory bound. Endpoint and buffer counters should distinguish logical admission retirement from actual final destruction; an old poll snapshot can temporarily retain a retired endpoint. A receipt intended only for observation must not itself keep sockets alive.

The Rust-specific opportunity is to retain one owned socket across successive requests and move each completed buffer into checked code without a second payload copy. This gives auditable ownership boundaries, not evidence of higher speed. It can also retain excess capacity after a short read and allocate a new buffer for every request; do not claim allocation-free reuse. OTP itself can reuse its descriptor buffer, transfer a full binary or shrink/copy a partial result. [OTP buffer branches](https://github.com/erlang/otp/blob/ad05823719d77c8faee87348ea39513d4e2f99c5/erts/emulator/nifs/unix/unix_socket_syncio.c#L9820-L9865). Host aliases remain a trust condition: cloned UnixStream handles share the underlying stream and options. [Pinned Rust clone contract](https://github.com/rust-lang/rust/blob/48a229ceaefd4985c50990b14116b6d856af0985/library/std/src/os/unix/net/stream.rs#L176-L198).

## Required correctness evidence

Use controlled phases and counts, never elapsed-time comparisons. Qualify multiple short reads on the same endpoint, data buffered before peer close followed by EOF, no prefetch between reads, independent peer progress during a pending read, and exactly-once request and endpoint retirement. Force old future drop/cancellation/readiness/completion after the next request exists. Separately hold a running cancelled request and prove another read cannot overlap it. Exercise stop while idle, pending, running, ready and while older returned buffers remain actor-owned; then reuse the process slot and reject stale completion. Hold an explicit snapshot owner through actor stop to demonstrate that descriptor destruction waits for the snapshot rather than actor cleanup. Cover admission exhaustion with idle endpoints, repeated request cycles, terminal reads, and shutdown with both idle and active resources.

Distinguish actual socket observations from synthetic completion/error controls. Keep the single-worker, trusted-host, local nonblocking UnixStream scope visible. Passing these controls would qualify the declared protocol; it would not establish arbitrary native cancellation, multi-worker execution, io_uring buffer lifetime, general networking or a performance improvement.
