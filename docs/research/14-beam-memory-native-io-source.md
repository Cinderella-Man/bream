# BEAM source: memory, native work, timers and I/O

Reviewed 2026-10-07 against the local official Erlang/OTP checkout, tag `OTP-29.1.1`, commit `ad05823719d77c8faee87348ea39513d4e2f99c5`. [Checkout provenance](../../evidence/beam-source-review/source-pin.json). This is source inspection, not an executed VM experiment, exhaustive audit, or proof about Rust. The scheduling, mailbox and lifecycle reports cover adjacent paths.

## Process isolation is a representation contract

`struct process` contains execution registers and program counter, young/old heap pointers, stack pointer, off-heap ownership lists, heap/message fragments, signal queues, timer state, locks and scheduler association. This is substantially more than a task callback plus an MPSC channel. ERTS knows how these representations are traced, moved and released because they belong to its term/runtime model. [Process representation](https://github.com/erlang/otp/blob/ad05823719d77c8faee87348ea39513d4e2f99c5/erts/emulator/beam/erl_process.h#L1043-L1175), [local source](/home/bat/projects/bream/upstream/otp/erts/emulator/beam/erl_process.h:1043).

Terms have explicit tags for immediate values, lists and boxed objects. This supplies information the VM's copying and garbage-collection routines can interpret. It is not a description of arbitrary Rust objects, native stack frames, interior pointers or destructor obligations. Bream can borrow the ownership boundary without copying Erlang's dynamic term representation or adding a tracing collector to its first typed protocol. [Term tags](https://github.com/erlang/otp/blob/ad05823719d77c8faee87348ea39513d4e2f99c5/erts/emulator/beam/erl_term.h#L70-L90).

**Bream implication:** every admitted value and operation needs an ownership, suspension and reclamation account. A marker such as `Send + 'static` does not provide that account. Keeping an operation in Rust does not by itself make it schedulable or safely killable.

## Per-process collection does not mean every collection is sliced

`garbage_collect` selects minor or major collection, manages process GC state, handles delayed collection, and charges work. Before a potentially large collection, `check_for_possibly_long_gc` estimates young heap, stack, old heap when relevant, and on-heap queue work; it can request dirty system execution. This is an explicit treatment of large runtime work, not evidence that a reduction counter interrupts any C loop. [GC decision path](https://github.com/erlang/otp/blob/ad05823719d77c8faee87348ea39513d4e2f99c5/erts/emulator/beam/erl_gc.c#L759-L898), [large-GC classification](https://github.com/erlang/otp/blob/ad05823719d77c8faee87348ea39513d4e2f99c5/erts/emulator/beam/erl_gc.c#L688-L715), [local source](/home/bat/projects/bream/upstream/otp/erts/emulator/beam/erl_gc.c:688).

**Bream implication:** growing a collection, copying a payload, matching a large value and freeing a mailbox are all work to qualify. Instrumenting application loop headers leaves those operations uncovered. Bream's current generated subset does not yet establish bounds or resumable implementations for them. No BEAM GC implementation is proposed for reuse here.

## Immutable binary sharing is different from shared mutable state

In `copy_struct_x`, the reference-backed binary path copies term descriptors, pins a writable binary as necessary, increments its reference count, and attaches a reference to the destination's off-heap list. `erts_pin_writable_binary` removes writable/active-writer flags under the expected single-reference condition. The referenced bytes need not be duplicated for each receiving process. This is a specific path, not a claim that every term or binary send is zero-copy. [Binary-copy branch](https://github.com/erlang/otp/blob/ad05823719d77c8faee87348ea39513d4e2f99c5/erts/emulator/beam/copy.c#L812-L848), [pinning](https://github.com/erlang/otp/blob/ad05823719d77c8faee87348ea39513d4e2f99c5/erts/emulator/beam/erl_bits.c#L2051-L2079), [local source](/home/bat/projects/bream/upstream/otp/erts/emulator/beam/copy.c:812).

`erts_cleanup_offheap_list` releases references to binaries and other off-heap entities. A process dropping its reference need not destroy bytes that another live process still owns. [Off-heap cleanup](https://github.com/erlang/otp/blob/ad05823719d77c8faee87348ea39513d4e2f99c5/erts/emulator/beam/erl_message.c#L165-L205).

**Bream choice, accepted Q19:** an opaque runtime-managed immutable byte buffer may make room fanout practical while preserving the exclusion of shared mutable application state. This still needs construction/freeze rules, audited final-reference cleanup, and physical-versus-per-process-reference accounting. It does not approve arbitrary `Arc<T>`, user destructors or interior mutability. Killing the publisher must release its ownership without invalidating a recipient's payload. Killing the final owner must eventually reclaim the storage exactly once. [ADR 0008](../adr/0008-immutable-buffer-sharing.md).

## Native functions are a separate execution contract

`enif_consume_timeslice` charges reductions and reports whether the allowance is exhausted; it does not interrupt the currently executing native function. It is a no-op on a dirty scheduler. `enif_schedule_nif` arranges another native invocation or chooses a dirty execution class. The regular wrapper eventually calls the function pointer and regains control when it returns. [Charging](https://github.com/erlang/otp/blob/ad05823719d77c8faee87348ea39513d4e2f99c5/erts/emulator/beam/erl_nif.c#L3341-L3359), [native wrapper and scheduling](https://github.com/erlang/otp/blob/ad05823719d77c8faee87348ea39513d4e2f99c5/erts/emulator/beam/erl_nif.c#L3485-L3583), [local source](/home/bat/projects/bream/upstream/otp/erts/emulator/beam/erl_nif.c:3341).

The matching first-party NIF reference explicitly describes splitting work, separate threads, and dirty schedulers as distinct strategies. It also states that killing a process does not stop an already-running dirty NIF; some process storage stays alive until that invocation finishes. The implementation's exit path sets `F_DELAYED_DEL_PROC` if dirty execution is still active. [Pinned NIF contract](https://github.com/erlang/otp/blob/ad05823719d77c8faee87348ea39513d4e2f99c5/erts/doc/references/erl_nif.md#L389-L489), [delayed deletion](https://github.com/erlang/otp/blob/ad05823719d77c8faee87348ea39513d4e2f99c5/erts/emulator/beam/erl_process.c#L14748-L14791).

**Bream implication:** placing an arbitrary Rust crate call on another thread protects some scheduler capacity but does not make that call forcibly stoppable. If Bream later offers such jobs, their lifetime and continued effects must be explicit, outside the guaranteed stoppable computation. A worker pool cannot silently satisfy the current safe-kill requirement. The conservative initial proposal is to reject these calls inside checked process code and qualify approved helpers transitively. This is a recommendation, not a new accepted architecture decision.

## Cleanup has multiple owners and multiple phases

After exit signaling, `delete_process` cleans pending queues, off-heap references and heaps. `erts_cleanup_messages` walks a list; `erts_cleanup_offheap_list` walks references. These inspected loops do not carry the yielding continuation used by the earlier process-exit relationship traversal. Therefore “BEAM exit cleanup is incremental” must be qualified: important phases yield, but this inspection does not establish a bounded duration for all final reclamation. [Final process deletion](https://github.com/erlang/otp/blob/ad05823719d77c8faee87348ea39513d4e2f99c5/erts/emulator/beam/erl_process.c#L13393-L13482), [message-list cleanup](https://github.com/erlang/otp/blob/ad05823719d77c8faee87348ea39513d4e2f99c5/erts/emulator/beam/erl_message.c#L239-L249).

Native resource destructors introduce another boundary. `nif_resource_dtor_prologue` schedules auxiliary work so callbacks run in a known lock context. `run_resource_dtor` coordinates remaining monitor references before invoking the resource callback and releasing storage. This solves a context/lifetime problem; it does not automatically make arbitrary callback code short or preemptible. [Resource destructor path](https://github.com/erlang/otp/blob/ad05823719d77c8faee87348ea39513d4e2f99c5/erts/emulator/beam/erl_nif.c#L2961-L3029), [local source](/home/bat/projects/bream/upstream/otp/erts/emulator/beam/erl_nif.c:2961).

**Bream choice, accepted Q20:** separately observe execution stop, identity removal, required resource invalidation, monitor delivery and completion of accounted cleanup. `Down` means execution has stopped and the process is no longer addressable; final tracked reclamation can follow. This is stronger than BEAM's dirty-NIF logical-death exception. It does not permit freeing memory still accessed by a native operation or discarding Rust destruction obligations. Cleanup pressure belongs in fairness experiments, not only leak checks. [ADR 0009](../adr/0009-death-and-reclamation-observation.md).

## Timers wake execution; receive timeout is not an ordinary message

The high-level timer service contains time/BIF timer trees, a next timeout, a cancellation queue and yielding service state. Process timer installation and cancellation update the process timer field; cancellation clears timeout/sleep flags. `proc_timeout_common` atomically claims the expected timer, synchronizes with receive state and makes an inactive non-exiting process runnable. [Service state](https://github.com/erlang/otp/blob/ad05823719d77c8faee87348ea39513d4e2f99c5/erts/emulator/beam/erl_hl_timer.c#L639-L654), [process timer operations](https://github.com/erlang/otp/blob/ad05823719d77c8faee87348ea39513d4e2f99c5/erts/emulator/beam/erl_hl_timer.c#L2785-L2846), [timeout wakeup](https://github.com/erlang/otp/blob/ad05823719d77c8faee87348ea39513d4e2f99c5/erts/emulator/beam/erl_hl_timer.c#L692-L705).

The mailbox report traces when receive instructions arm/cancel the timer. Bream must preserve the selected receive semantics rather than implement timeout as an ordinary user message that may sit behind nonmatches. Test arrival versus timeout versus kill at the transition into waiting. Timer data-structure optimization can wait until the correctness contract is established.

## I/O readiness and port work have runtime integration

`erts_check_io` performs poll waits with managed-thread progress transitions and processes descriptor events under their associated locks. `send_select_msg` either sends a NIF-select process signal or queues a prepared message, and clears the event if the target no longer exists. Ports have a separate scheduled-task path, including lifetime protection during lookup. [Polling path](https://github.com/erlang/otp/blob/ad05823719d77c8faee87348ea39513d4e2f99c5/erts/emulator/sys/common/erl_check_io.c#L1933-L2016), [select notification](https://github.com/erlang/otp/blob/ad05823719d77c8faee87348ea39513d4e2f99c5/erts/emulator/sys/common/erl_check_io.c#L836-L858), [port task entry](https://github.com/erlang/otp/blob/ad05823719d77c8faee87348ea39513d4e2f99c5/erts/emulator/beam/erl_port_task.c#L1451-L1491).

**Bream implication:** runtime-aware I/O requires a lifetime protocol for registrations, wakeups, buffers and late completion after process death. It does not require cloning Erlang's entire port/driver model. The current room/session fixture can stay in memory; later I/O qualification must distinguish cancelling interest, stopping an operation and preventing delivery to a stale incarnation.

## Allocation, reclamation and inspection are shared runtime costs

ERTS initializes different allocator families with scheduler/dirty-instance preferences and carrier policies. Thread progress tracks controlled states of managed threads; registered unmanaged threads can request wakeups but do not thereby participate in the global progress barrier. Native/dirty readers require their separate lifetime protections. This separates process-owned logical state from allocator retention and concurrent-reader lifetime. [Allocator setup](https://github.com/erlang/otp/blob/ad05823719d77c8faee87348ea39513d4e2f99c5/erts/emulator/beam/erl_alloc.c#L697-L725), [thread-progress contract](https://github.com/erlang/otp/blob/ad05823719d77c8faee87348ea39513d4e2f99c5/erts/emulator/beam/erl_thr_progress.c#L33-L72).

Even inspection can require runtime communication: one `process_info` path sends a signal with a reference, positions the receive cursor and traps awaiting a result. Thus a cross-process snapshot is not necessarily an immediate unsynchronized field read. [Inspection request](https://github.com/erlang/otp/blob/ad05823719d77c8faee87348ea39513d4e2f99c5/erts/emulator/beam/erl_bif_info.c#L1480-L1501).

**Bream implication:** retain separate counters for owned state, referenced shared bytes, queued messages, pending reclamation and host memory. A smaller generated future is not the whole process footprint. Keep inspection requests serviceable during a CPU hog, and state whether each snapshot is approximate or synchronized. Do not copy ERTS lock-free mechanisms without their progress/lifetime assumptions; simpler correct structures are appropriate for early experiments.

## Experiments added by this review

1. **Transitive runtime work:** make a checked process perform large allocation, copy, scan and teardown operations while a peer runs. Identify every longest indivisible segment; charge-after-return alone does not prove schedulability.
2. **Fanout ownership:** if Q19 accepts immutable sharing, publish one buffer to many recipients, kill sender and selected recipients, and verify validity plus exactly-once physical release after the final owner.
3. **Death and reclamation traces:** kill a process with a large mailbox and many owned resources; record stop, invalidation, DOWN and final tracked reclamation separately while a peer continues.
4. **Native negative control:** demonstrate outside the guaranteed process API that moving an infinite native call to a worker does not stop it on owner death. Its continued work must never be counted as successful process cancellation.
5. **Timer/wakeup model:** enumerate match, timeout, registration cancellation and death interleavings before optimizing the timer implementation. Add late I/O completion only in the later I/O phase.
