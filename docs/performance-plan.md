## What makes an optimization admissible

**User-selected priority (Q24, 2026-10-08): responsiveness first.** Predictable peer-ready delay and safe-stop latency take priority over aggregate throughput in the first service experiments. Report the throughput cost; a throughput increase with an unresolved responsiveness regression is not an accepted improvement. A numeric SLO and hard deadline are still unset.

Each candidate must preserve automatic scheduling with no handwritten yields, safe forced stop, owned-state cleanup, process identity, same-sender signal ordering, earliest matching receive, timeout race outcomes and relationship semantics. An optimization cannot become a bounded mailbox, lossy admission policy, hostile-code sandbox or opaque native escape without a separately accepted scope change.

Measure both throughput and interference. A larger batch that increases messages/second while materially worsening peer progress or kill-to-stop latency is a tradeoff to report, not an unconditional win. First establish a correct baseline and its ownership argument; then change one policy at a time. No task authorizes copying ERTS memory-ordering tricks into Rust without a Rust-specific lifetime and synchronization argument.

All rows below inherit this completion rule:

1. Retain baseline/treatment source, compiler and executable identity, parameters, raw samples and a named workload. Keep semantic fixtures and negative controls alongside timing results.
2. Pass affected feature cases, then profile and compare repeated independent runs in alternating/randomized order. State the sample count, noise and uncertainty. Record cold and warmed behavior separately.
3. Report the target cost plus throughput, peer-ready delay, kill-to-stop, stop-to-cleanup and memory/backlog where affected. Set the experiment's regression allowance from baseline variability **before** assessing its treatment; a product SLO is still unset.
4. Accept only a repeatable improvement in the declared operating range with passing correctness/ownership gates and no undeclared regression. Otherwise reject, retain for a narrower workload, or record an explicit tradeoff. An inconclusive result is a valid outcome.

Sample maxima are not hard real-time guarantees. Reduction counts are internal work units, not elapsed time or comparable instructions across runtimes. BEAM's [profiling guidance](https://www.erlang.org/doc/system/profiling.html) motivates locating actual bottlenecks; its [benchmarking guidance](https://github.com/erlang/otp/blob/ad05823719d77c8faee87348ea39513d4e2f99c5/system/doc/efficiency_guide/benchmarking.md#L83-L113) distinguishes CPU/wall time, warm state and architecture. The service workload additionally needs distributions and overload accounting, not only best-case timing.

The [persistent-read milestone](research/69-persistent-read-milestone.md) adds a correctness prerequisite for W09 resource work: moving a completed buffer preserves its backing allocation, and old requests cannot mutate later requests. A storage refinement under PERF-104 can compare this allocation baseline with a bounded return pool, varying chunk size, short-read distribution, retained earlier results and cancellation. First prove that only released buffers return to the pool and that stop/shutdown cannot strand or reuse live storage. In a separately authorized environment, assess allocation count, retained capacity, total cost and peer/stop behavior; reject improvements that increase unaccounted retention or cleanup work. This is a planned refinement, not a completed performance task or a speed claim against BEAM.

## Order of work

Start with PERF-001's manifests and workload definitions alongside G1's public admission/termination proof. PERF-052/054 and the positive borrowed-state control in PERF-053 sharpen that proof for useful Rust state. Then evaluate PERF-002/003/004 and PERF-037 on the useful admitted body. G1 failure blocks production performance claims; it does not prevent independent reference/source investigations.

With a correct single-worker mailbox, prioritize PERF-007/008/010 and the correct full-scan baseline for PERF-014, because the room/session workload exercises them directly. Measure W04 and W07 together so reducing copying does not conceal reference retention or cleanup storms. PERF-006 should quantify observation overhead from the first implementation slice.

Trace PERF-017's complete timer-service loop and resolve PERF-031's ownership question before deriving fast-path safety or latency conclusions from those mechanisms. General timer structures and multi-worker adaptation come after their feature gates; allocation and instrumentation work follows measured bottlenecks. Finish each implemented slice with PERF-032 integration, retaining rejected variants and raw evidence rather than accumulating unexplained tuning knobs.

For the accepted runtime-aware I/O extension, establish owner-death/cancel/stop/close correctness before PERF-055–060. Use the Linux observations as backend controls, not as the Bream contract test. Minimal observation must remain cheap from the first slice; full snapshot/session optimizations PERF-061–065 follow the corresponding optional APIs. PERF-066–070 qualify resource integration only for the admitted handle/callback surface. Neither tracing nor a generic NIF compatibility layer is a prerequisite for the room/session process milestone.

Use report49's counterexamples when reviewing each future atomic change, with actual pointer/owner invariants added to the chosen protocol. PERF-076/079 can start with simple internal authority types; they do not require BEAM's lock layout. Introduce typed deadline/conversion checks with receive timeouts. Coordinator tuning and additional reclamation domains follow demonstrated host/multiworker needs, and provider correction experiments apply only when the supported clock path needs them.

Apply PERF-086/088/090 to whatever internal maintenance the first implementation admits; its control work still needs ownership and scheduling. PERF-091 can specialize proven static immutable bytes without code replacement. Name routing PERF-095–099 waits for the registry extension and a typed rebinding contract. PERF-092/094 only apply if replaceable data is added; static Rust need not reproduce literal evacuation.

## Remaining coverage

The source passes examine selected normal-CPU scheduler, message allocation, immutable-binary, timer, x86 checkpoint, collector-root, process-publication, allocator-ownership, Linux polling and observer/native-resource lifetime branches. They do not cover every allocator strategy, NUMA policy, CPU architecture, compiler optimization, polling failure/migration product or weak-memory interleaving. Those remain possible later performance investigations where the process scope and profiling justify them. Bundled ZIP/crypto algorithms and OTP behaviours remain outside this work.
